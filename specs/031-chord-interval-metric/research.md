# Research: Chord Interval Metric

No `NEEDS CLARIFICATION` remains in the spec. The questions below are about how to build it.

## Decision 1: A new library module, nothing wired

- **Decision**: Add `backend/app/services/chords.py` with a pure function `measure_chords(values, chord_types, note_count=None, threshold=None)` returning a `ChordSeries`. No job field, response key, page control or picture uses it (spec FR-011).
- **Rationale**: The user asked for "the code to record the data for now". Local Peaks (023) is the precedent: a measurement module with a finished result object and nothing calling it. A pure function of the note strengths is also what makes the record depend on its own window only (FR-008).
- **Alternatives considered**: running it inside the job and storing it in the job result (changes the response and the stored job, which FR-011 forbids); a class that holds state across windows (the record must not depend on neighbours).

## Decision 2: Matching with a 12-bit mask of the steps above the lowest note

- **Decision**: For one chord type with `n` intervals and one choice of letters: take the representative notes of the `n + 1` letters (Decision 3), sort their numbers, take `offset = (note - lowest) % 12` for each, and set bit `offset` in a mask. The window matches the type when the mask equals the mask of one of its inversions (which have exactly `n + 1` bits, so no separate test is needed that the notes fall on different steps). The inversion masks are made once per type: for a chord with notes `c = (0, t1, ..., tn)`, inversion `k` is `((c[k], c[k+1], ..., c[n], c[0] + 12, ..., c[k-1] + 12) - c[k]) % 12` set as bits.
- **Rationale**: Taking the offset modulo 12 from the lowest note is exactly "divide the higher frequencies by 2 until they are less than an octave above the lowest" (the notes of a choice are of different letters, so their offsets differ and the mask always has `n + 1` bits). A mask comparison is a single integer comparison, so the whole file can be matched with array operations. The inversion definition reproduces the user's examples: `(4)` gives 0,4 and 0,8; `(4, 7)` gives 0,4,7 / 0,3,8 / 0,5,9.
- **Alternatives considered**: comparing sorted offset tuples (a Python loop per window, much slower for long files); comparing frequency ratios (floating point, and the user's notes are exact semitones anyway).

## Decision 3: Which notes are matched, and what is recorded

- **Decision** (revised 2026-11-07, after the user looked at real files): the allowed notes of a window are combined into 12 **letters**: the strength of a letter is its 7 octaves added up from the lowest (an explicit loop, so the sum is always done in the same order), and a letter stands for its **loudest octave** (`argmax`, the lowest on a tie). The notes have been through the noise floor first (feature 033; it replaced a first, weaker floor of `1e-6` of the window's loudest letter). The 6 loudest letters are found once per window by a stable sort on `-strength` (ties to the lower letter); a type with `n` intervals uses its first `n + 3` of them (`EXTRA_LETTERS = 2` beyond its `n + 1` notes: 4, 5 or 6, the user's "4 for a single interval, 6 for a 3-interval", five for two being interpolated; the 6 is the user's limit and is reached by the 3-interval types), and tries every choice of `n + 1` of them (`itertools.combinations`: 6, 10 or 15 choices). The record keeps the representative note of each letter (0 to 83, 0 = A1 at 55 Hz), sorted from lowest to highest.
- **Rationale**: A real file gave a chord in only 22 to 23 percent of the windows at the default window: a doubled bass note (the same letter in two octaves), the overtones of a note, or one louder note that is in no chord each defeat "the `n + 1` loudest notes". On the files measured the letters rule alone roughly doubled the tonal matches, and "any `n + 1` of the 6 or 8 loudest notes" found a chord in 72 to 98 percent (too permissive to say anything). The user chose the letters and the 4/5/6 reach; mistaking an overtone for a fifth is accepted. A noise floor is needed: the analysis of a pure tone leaves values around 1e-9 in the other notes, and with six letters looked at those make longer chords of their own (feature 033).
- **Alternatives considered**: keeping the `n + 1` loudest notes (the old rule); "any `n + 1` of the loudest notes" without combining the octaves (very permissive, and a doubled bass fills the places); no noise floor (a pure triad could come out as a seventh chord).

## Decision 4: Selection by a packed integer score

- **Decision** (revised 2026-11-07): for each (window, type, choice of letters) that matches, the score is the five numbers `(n, loudness, widest, -inversion, -index)`: `n` the number of intervals (1 to 3), `loudness` the strengths of the letters of the choice added up from the lowest letter, `widest` the largest interval of the type (1 to 11), `inversion` 0 to 3 (the lowest that matches, for a symmetrical chord) and `index` the place of the choice among the combinations of the louder letters. They are compared one after the other by `_greater` (the first that differs decides) and a candidate replaces the one found only if its score is greater.
- **Rationale**: Larger `n` wins (the user's rule 1). With only one choice of notes the next rule was the widest interval; with several choices that lets a faint note that makes a wide interval beat the real chord (C E G with a faint B: `(4, 11)` is wider than `(4, 7)`). So the loudest choice decides second. For the same letters the loudness is equal, so the widest still decides (the user's `(4)` against `(8)` and `(5)` against `(7)` examples are unchanged). The inversion and the choice order are the tie rules. Two different types never tie on all five: the same letters at the same inversion and the same widest interval is the same type, so the order of the list given never decides. This is a deliberate change to the order of the user's rules, to be reported to them; it is one line to take out. (Float sums of the same letters are done in the same order everywhere, so equal choices give bit-equal loudness.)
- **Alternatives considered**: sorting candidate tuples per window in Python (slow and no clearer); doing the rules one after another with several passes (the same result, more code).

## Decision 5: Reuse the picture's limits instead of copying them

- **Decision**: With a **number of notes**, the allowed notes are `note_selection.top_energy_notes(values[:, :84], count)` (the same choice for every window; its message `The number of notes must be a whole number from 12 to 84.`). With a **threshold**, a note is not allowed in a window when `frame_rendering.hidden_below(values[:, :84], peak, threshold)` says it is hidden, with `peak` the largest value of the whole array given (all columns, as the picture's `hidden_notes` does; its message `The threshold must be a number from 0 to 10.`). A note that is not allowed is given strength 0 before the loudest are found. `hidden_below` is imported when the function runs, not at the top of the module.
- **Rationale**: "Only those notes would be used" is only true if the choice is the picture's choice; calling the same functions makes it true by construction and gives the same ranges and messages (FR-013). The late import keeps `chords.py` light and lets `frame_rendering` import it later without a cycle.
- **Alternatives considered**: copying the two rules into the new module (could drift); making the caller pass an "allowed" mask only (the caller would repeat the picture's logic).
- **Note**: the picture spreads the chosen notes over the whole grid (`spread_notes`); the interval search does not, because spreading would change the intervals. The measurement uses the chosen notes at their own pitch.

## Decision 6: How the result is stored and read

- **Decision**: `ChordSeries` is a frozen dataclass holding `chord_types` (the tuple of tuples, in the order given) and three arrays of length `W`: `type_index` (int16, index into `chord_types`, -1 for none), `inversion` (int8, -1 for none) and `notes` (int16, shape `(W, 4)`, original note numbers lowest first, -1 padding). It offers `window_count`, `record(i) -> ChordRecord | None` and `records() -> list`. `ChordRecord` is a frozen dataclass of `chord_type`, `inversion`, `notes`.
- **Rationale**: Arrays the same length as the windows are how the bins and (through `frame_positions`) the beat are already stored; a later feature can index them by window with no conversion. The readable record is for tests and for people.
- **Alternatives considered**: a Python list of records (slow to build and to index for long files); structured numpy arrays (harder to read in tests, no gain).

## Decision 7: Parameter checks

- **Decision**: `check_chord_types(types)` takes an iterable of chord types and returns a tuple of tuples of ints. A chord type is a tuple or list of 1 to 3 whole numbers from 1 to 11 in strictly increasing order; a bare whole number is the one-interval type. Booleans, floats (even `4.0`), strings and `None` are refused (numpy integers are accepted). The list must not be empty and must not hold the same type twice. Messages: `The chord types must be a list of one or more chord types.`, `A chord type must be 1 to 3 intervals, each a whole number of steps from 1 to 11, in increasing order (got ...).`, `The chord type (...) is given more than once.`
- **Rationale**: The spec's FR-009 list, with messages in the style of the other `check_*` functions of the project.
- **Alternatives considered**: sorting out-of-order intervals instead of refusing (hides a mistake, and the spec says refuse); accepting 12 or more steps (an octave is the same note: the spec limits a chord to less than an octave).
