# Research: Image Type (Blended Tiles)

No `NEEDS CLARIFICATION` items remained in the spec; the assumptions and the blend width setting were confirmed by the user on 2026-10-10. These are the design decisions the plan rests on. The numbers in Decision 5 come from throwaway prototypes run while planning (not kept in the repository).

## Decision 1: Weights by distance from the nearest inner edge, Gaussian feather, separable

- **Amendment (2026-10-10)**: the first implementation used a straight-line ramp (`0.5 + d / (2B)`). On real frames it looked too blurry, so it was replaced by a Gaussian feather: `F(d) = (Φ(4d / B) − Φ(−4)) / (1 − 2·Φ(−4))`, i.e. a Gaussian blur of the sharp edge with `σ = B / 4`, cut off at the reach and renormalised (data-model.md has the exact form). It is still separable, still 0.5 at the edge, still exactly 1 at the reach, and the blend width keeps its meaning and range; at the default 25% the feather is about 10 pixels across. The text of this decision below describes the original ramp; everything else in it (separability, the 2 × 2 mix, flat border, no overlap) is unchanged. Viewed side by side on one real frame, the straight ramp at 25% was visibly blurry while the Gaussian feather at 25% kept crisp tile cores with soft edges; σ = B / 4 was chosen over B / 3 and B / 2 because it kept the tiles crispest while still giving a smooth edge.

- **Decision**: For one axis (columns with tile width 21, or rows with tile height 24), a pixel with center position `p + 0.5` has the distance `d` to the nearest *inner* tile edge on either side. With `B = blend width / 100 × 21` (pixels): if `d < B`, the pixel's own tile has weight `0.5 + d / (2B)` and the tile across that edge `0.5 − d / (2B)`; otherwise own weight 1. A pixel's final color is the sum over the 2 × 2 tiles of (vertical weight × horizontal weight × tile color), then rounded to 8 bits. The first and last tile columns and rows have no inner edge on their outer side, so nothing is blended there.
- **Rationale**: Gives exactly what the spec says: 50/50 at the edge itself (the pixels at distance ±0.5 average to exactly 0.5 each), weights summing to 1, a linear change over the band, exact tile colors beyond `B`, a convex combination (no overshoot, FR-009), 25% each at a corner, no blending at the picture's border, and a fade width that is continuous in the percentage (every width from 10 to 25 gives a slightly different picture). Because the largest `B` (5.25 px) is less than half of either tile dimension, only the nearest edge can matter for a pixel and bands never overlap.
- **Alternatives considered**: A fixed integer pixel band (cannot express a 10 to 25 percent setting). Smoothstep or cosine weights (not "linear alpha-blend"). Interpolating between tile centers over the whole picture (a different look: no flat middles). Blending in a perceptual color space (spec: plain 8-bit RGB).

## Decision 2: Two numpy passes, float32

- **Decision**: `blend_tile_colors(colors, blend_width, tile_width, tile_height)` takes the `(rows × columns, 3)` colors, reshapes to `(rows, columns, 3)`, expands the columns first (each of the 7 tile rows to 252 pixels: `own_w · grid[:, c] + (1 − own_w) · grid[:, c_neighbor]`), then expands the rows (`own_h · horiz[r] + (1 − own_h) · horiz[r_neighbor]`), rounds with `np.rint` and returns `uint8` of shape `(168, 252, 3)`. The per-axis index and weight arrays depend only on the blend width, so they are computed once per job (a small helper that returns a ready function), not per frame.
- **Rationale**: Separability turns the per-frame cost into two small passes. A prototype of the straightforward four-term formula over the whole picture took 5.8 ms per frame; the two-pass form took 0.54 ms and differed from it by at most 1 level (float32 against float64 rounding). Weights of exactly 1 and 0 outside the bands make those pixels exact (`1·x + 0·y` is exact in float32 for 8-bit values), which satisfies SC-002 and SC-009.
- **Alternatives considered**: The one-pass four-term form (10 times slower). Processing many frames at once with a 4-D array (a possible later speed-up; adds memory use and complexity, and `write_frames` already works frame by frame). Integer fixed-point arithmetic (more code for a small gain).

## Decision 3: Where the image type is applied and how the file is written

- **Decision**: `write_frames` computes the finished `colours` for each frame exactly as today, then: for `tiles` calls the existing `_palette_frame(colours).save(..., compress_level=6)`; for `blended` calls `Image.fromarray(blend(colours), "RGB").save(..., compress_level=1)`. File names, directory and the endpoint that serves them are unchanged.
- **Rationale**: Leaving the tiles branch untouched is what guarantees byte-identical output (FR-002, SC-001). A true-color picture cannot use the 84-entry palette trick, so the blended files are RGB PNGs. In the prototype, compression level 1 cost 1.44 ms per frame in total and level 6 cost 1.77 ms for a file only 4 percent smaller (22.6 KB against 14.4 KB per frame), so level 1 is used for the blended type.
- **Alternatives considered**: One writer for both (changes the tiles files). JPEG or WebP (lossy or a different media type; the server serves `image/png` and the player expects it). Storing blended frames as palette images when they happen to have at most 256 colors (rarely true, and a second code path).

## Decision 4: Validation and the API

- **Decision**: `image_type` is an optional form field whose value must be exactly one of `tiles`, `blended` (case-sensitive, no trimming). Not sent: `tiles`. Sent but empty or any other text: HTTP 400 `The image type must be one of tiles, blended.` `blend_width` is an optional form field, a number from 10 to 25 (decimals accepted; the page steps by 1); not sent: 25; sent but empty, not a number, `nan`, `inf`, or out of range: HTTP 400 `The blend width must be a number from 10 to 25.` Both are checked before any audio is read. The response always carries both values used (`blend_width` as an integer when it is a whole number), also for `tiles`, where `blend_width` has no effect on the pictures. In the library, `write_frames` checks both up front (before anything is written) with `ValueError` carrying the same messages.
- **Rationale**: Same handling as `smoothing`, `threshold` and `energy` (`_sent_fields` tells "not sent" from "sent empty"). Strict names keep the contract unambiguous and make future types additions rather than behavior changes. Accepting a `blend_width` together with `tiles` follows the spec (scenario 6 of Story 2).
- **Alternatives considered**: Case-insensitive names or trimming (the spec says exact lowercase). Refusing `blend_width` with `tiles` (the spec says it is accepted and ignored).

## Decision 5: Performance, measured before building

- **Measurements** (300 random frames with about 60 percent lit tiles, this machine): tiles frame 0.33 to 0.36 ms (palette PNG, level 6); naive blend plus RGB PNG 6.0 ms; two-pass blend 0.54 ms of arithmetic and 1.44 ms in total with a level 1 RGB PNG. A tiles job for a 60 s file (1,800 frames) takes about 1.0 s in total, of which about 0.6 s is writing the frames.
- **Consequence**: A blended job for the same file should take about 1.0 − 0.6 + 1,800 × 1.44 ms ≈ 3.0 s, about three times the tiles job. That is above the "no more than twice" in SC-006. The floor is the PNG encoder (about 0.9 ms per RGB frame), not the arithmetic, so the target cannot be reached by tuning the blend alone.
- **Decision**: Build it with the two-pass blend and level 1 compression, measure the real code on the 60 s test file as the first task after the function exists (T002) and again at the end. If the measured job time is more than twice the tiles job, do not change the spec silently: report the measured numbers to the user and propose a realistic bound (for example "a 60-second file at 30 frames per second finishes within 5 seconds, and no more than four times the tiles job"), and let the user decide. Speeding the PNG step further (for example writing frames on several threads, since Pillow releases the lock while compressing) is possible but is a larger change and is left unless the user wants it.
- **Outcome (recorded after implementation)**: The real code matched the prototype (0.61 ms of arithmetic and 1.39 ms in total per blended frame against 0.25 ms for a tiles frame), and a first whole-job measurement on the 60 s file gave 3.1 times (blend width 10) and 3.8 times (width 25) the tiles job, as predicted. Because each frame is independent and numpy and the PNG encoder release the interpreter lock, blending and encoding the frames on a small pool of threads (`min(4, cpu count)` workers) cut the 1,800-frame writing step from 2.51 s to 0.76 s in a prototype, and the whole job to 1.02 times (width 10) and 1.33 times (width 25) the tiles job. SC-006 (at most twice) is therefore met without changing the spec, on this 24-core machine; on a machine with fewer cores the gain is smaller (with one core the job is about 3 times the tiles job). The files are identical whatever the number of threads (tested against a plain single call of the blend).
- **Alternatives considered**: Relaxing SC-006 now (it is the user's requirement and the real figure is not yet known); lowering compression to 0 (stored PNGs of 127 KB per frame: 230 MB for a 60 s file); reducing the picture size (the spec fixes 252 × 168).

## Decision 6: The page controls

- **Decision**: An **Image type** `<select>` with `Tiles` and `Blended tiles` (values `tiles` and `blended`, starting at `tiles`), and a **Blend width** range input (10 to 25, step 1, starting at 25) with the readout `n% of a tile`, both with info buttons. The slider is disabled when `tiles` is selected and while a job runs; its value is still sent. The summary shows `Image type: Tiles | Blended tiles` and, for blended, `Blend width: n%`. Both controls are placed together in a new group after Threshold.
- **Rationale**: Matches the spec (Story 2) and the existing patterns (a dropdown like Window size, a slider like Smoothing/Threshold).
- **Alternatives considered**: Hiding the slider for Tiles (layout jumps; the spec says disabled); radio buttons (a dropdown scales to more types).

## Decision 7: Tests that already exist

- **Decision**: No existing test encodes behavior that changes: the tiles path is untouched. The only required change in existing tests is the expected response keys in `test_energy_api.py` (two new keys). A stored reference hash of the frames from the 4 s test file (the one used in the earlier features) is compared after the work to show the tiles output is unchanged.
