## Note analysis

`backend/app/services/note_analysis.py` reduces stereo audio to 88 musical-note values per window (55 Hz, one semitone apart). Left and right spectra are averaged, and each note reads the spectrum at `int((window_size / sample_rate) * freq)`.

```python
from app.services.note_analysis import NoteBinAnalyzer, analyze_wav

result = analyze_wav("audio/song.wav", sample_rate=44100, window_size=2048)
result.frames                 # shape (windows, 88), lowest note first
result.window_start_times()   # seconds

analyzer = NoteBinAnalyzer(44100, 2048)
values = analyzer.analyze(left_buffer, right_buffer)   # shape (88,)
```

Notes: neighbouring low notes share a spectrum position at small window sizes (about 28 of 88 at 2048 samples and 44.1 kHz), so use a larger window if you need them separated. The sample rate must be at least about 16.75 kHz. Put sample files in `backend/audio/` (git-ignored).

## Local peaks

`backend/app/services/local_peaks.py` is a second measurement, next to the note analysis: it follows the **overall** loudness of a file (not only its notes) and finds the periodic local maxima in it, the beats and pulses that come round again and again. It is a backend library; the job endpoint uses it for the **Beat coloring** of Tiles and Blended tiles (below), and nothing else uses it yet.

- **Impulse energy**: the file is cut into windows of 32 samples; the energy of a window is the average of the left channel's standard deviation and the right channel's (each on its own; a mono file has two equal channels). Integer samples are scaled to about -1 to 1, so the bit depth does not matter.
- **Peaks window**: a running window of 4096 impulse energies (about 3 seconds at 44.1 kHz; the size is the `window` argument and its exact value is not important) that moves through the file by half its length. `scipy.signal.find_peaks` is called on every window with `distance` (the minimum distance converted to impulse samples, `round(ms / 1000 * rate / 32)`, at least 1) and `prominence` (the prominence percentage of the window's largest energy). Each window owns its central half (the first window also the start of the file, the last its end), so a peak is judged once, with at least a quarter window of context on each side, and is neither lost nor reported twice; a last pass keeps the minimum distance across the borders between windows (the stronger of two close peaks stays).
- **Settings**: `min_distance` in milliseconds, 100 to 2000, default 100; `prominence` in percent, 0 to 100, default 50 (a bump must stand out by at least that share of the loudest impulse energy in its window; at 100 only a peak standing on exact silence qualifies). Anything else is refused with `The minimum distance must be a number from 100 to 2000 milliseconds.` or `The prominence must be a number from 0 to 100 percent.` before anything is measured.
- **What a peak records** (`LocalPeak`): `sample` (the first sample of the impulse window where the maximum is, so exact to 32 samples), `energy`, `window_min` and `window_max` (the smallest and largest impulse energy of the peaks window it was found in) and `rate` (peaks per minute, `60 * file rate / samples since the previous peak`; the first peak has no predecessor and gets the default of 60).
- **Asking the result** (`LocalPeaks`): `energy_at(sample)` is the straight line between the previous and the next peak's energy, 0 before the first peak and, after the last peak, a straight line from the last peak's energy down to 0 at the end of the file (the last beat is taken to last for whatever is left of the file, so the file ends on a down part of the beat; 0 past the end, and 0 for a file without peaks); `rate_at(sample)` is the rate of the last peak at or before the point, not interpolated, and 60 before the first peak. `energy_at_time(seconds)` and `rate_at_time(seconds)` take seconds. Each accepts a single point (and returns a `float`) or a list or array of them (and returns an array), so the values for every frame of a file are one call. A NaN or infinite point is refused. `position_at(sample)`, `position_at_time(seconds)` and `frame_positions(frame_rate, frames)` give the **place in the local energy peak** from 0 to 1: the interpolated energy between the interpolated smallest and largest energy of the neighbouring peaks' windows (the same straight line from the previous peak to the next), held within 0 and 1; 0 before the first peak, for a file without peaks and where the two leave no range; after the last peak the smallest and largest energy are those of the last peak's window and the energy falls to 0 at the end of the file, so the position falls to 0 and the file ends on a down part of the beat. `frame_positions` reads the middle of each frame.

```python
from app.services.local_peaks import measure_wav

peaks = measure_wav("audio/song.wav", min_distance=100, prominence=50)
peaks.peaks                    # LocalPeak(sample, energy, window_min, window_max, rate), in order
peaks.energy_at_time(12.5)     # interpolated energy 12.5 s into the file
peaks.rate_at_time(12.5)       # peaks per minute at that point
```

Tests: `backend/tests/test_local_peaks.py` (seeded click tracks and bursts in `tests/local_peaks_signals.py`).

## Noise floor

A note that is practically silent is not a note. The note analysis never gives exactly 0 for a note nobody plays (the spectrum leaks, recordings hiss), so, right after the analysis (`backend/app/services/noise_floor.py`, feature 033), **every note strength strictly below one thousandth of the largest strength in the file is set to 0**: 60 dB below the loudest note, the strengths being amplitudes. It is cut once, before the frames are averaged and smoothed, so every picture, the Notes and Threshold settings and the chords see the same notes, and a note that is cut is not counted as a note or as part of a chord.

- **Fixed**: there is no setting, request field or control. It applies to every image type, whether or not the image type has a Threshold; with a Threshold the stricter of the two decides (a Threshold of 0 does not switch the floor off).
- **The reference is the loudest value of the whole file**, the four notes above the 84 piano notes included (the same reference as the Threshold), because the analysed strengths have no absolute decibel scale. A note exactly at the floor still counts. A very loud click therefore raises the floor for the whole file and can silence quiet music around it.
- **The chord measurement applies the same cut itself** (to any array it is given, before combining the octaves of a letter), so a faint note never completes a chord. The beat (local peaks) is measured from the audio, not from the note strengths, and does not change.
- It does not tell tonal from non-tonal sound: noise, speech and percussion above the floor are notes, and so are their chords.
- Tests: `backend/tests/test_noise_floor.py` (the cut, with an independent oracle and mutation checks) and `tests/test_noise_floor_api.py` (every image type through the job, with and without a Threshold).

## Chord intervals

`backend/app/services/chords.py` is a third measurement, built on the note analysis (feature 031): for every analysis window it says **which chord the loudest letters form**, from a list of chord types that the caller asks for. It is **the measurement only**: nothing uses it yet (no job field, response key, page control or picture), so how it is used is a later feature.

- **A chord type** is a tuple of **1 to 3 intervals**, each a whole number of steps (half steps) from 1 to 11, in increasing order, above an **implied root**: `(4,)` is the notes 0 and 4 (a major third), `(4, 7)` the notes 0, 4 and 7 (a major triad), `(3, 7, 10)` a minor seventh. A bare number is a one-interval type (`((5), (7))` in Python is the two types `(5,)` and `(7,)`). The types are always parameters; none is built in.
- **What is matched**: the 84 piano notes of a window are first combined into the **12 letters**: the strengths of a letter in all its octaves are added up (C2, C3 and C4 are one note) and a letter stands for its loudest octave. A type with `n` intervals then looks at the **`n + 3` loudest letters** (4 for one interval, 5 for two, 6 for three: never more than 6; a letter with no strength does not count; ties go to the lower letter) and tries **every choice of `n + 1` of them**. The notes of a choice are moved **down by whole octaves** until they are less than an octave above the lowest (C3 and E4 become C3 and E3: 4 steps), and the steps are compared with **every inversion** of the type: moving the lowest note up an octave and counting from the new lowest one. `(4,)` is 0, 4 in root position and 0, 8 in first inversion (E4 and C5); `(4, 7)` is 0, 4, 7, then 0, 3, 8, then 0, 5, 9. So a louder note that is in no chord does not hide a chord among the other loud letters, and the overtones of a note (its fifth, its third) can be taken for chord notes; that is accepted, because the chords are meant to be aggregated later (tonal center, modes...).
- **Which match is recorded** when several fit (a fourth is an inverted fifth): the one with **the most intervals**, then **the loudest letters** (their strengths added), then **the largest interval**, then the **lowest inversion**, then the first choice of the louder letters. So `(4, 7)` wins over `(4)`; with `(4)` and `(8)` asked for, notes 8 steps apart are `(8)` in root position and notes 4 steps apart are `(8)` in first inversion; and C E G with a faint B is the triad `(4, 7)`, not `(4, 11)` on C E B, although `(4, 11)` is wider (the loudness comes before the widest interval so that a faint note cannot win by making a wide interval; for the same letters the widest interval still wins). Two different types never fit the same letters at the same inversion with the same widest interval, so the list order never decides.
- **What is recorded** for each window (`ChordRecord`): the chord type as given, the **inversion** (0 is root position) and the **original notes** (0 to 83, 0 being A1 at 55 Hz), lowest to highest: the loudest octave of each letter of the chord, as it sounds. The result (`ChordSeries`) has one entry per window, in window order, like the note strengths: the arrays `type_index`, `inversion` and `notes` (`-1` for no chord), and `record(i)`, `records()`.
- **The pictures' limits** are optional and are the pictures' own functions: `note_count` (the Notes setting: only the notes with the most total energy over the file, each in its own pitch) and `threshold` (the Threshold setting: a note strictly below that percentage of the largest value is hidden in its window). With neither, all 84 notes can be used.

```python
from app.services.chords import measure_chords
from app.services.note_analysis import analyze_wav

analysis = analyze_wav("audio/song.wav", 44100, 8192)
chords = measure_chords(analysis.frames, [(4,), (7,), (4, 7), (3, 7)], note_count=None, threshold=None)
chords.record(120)             # ChordRecord(chord_type=(4, 7), inversion=1, notes=(31, 34, 39)), or None
chords.type_index              # one entry per window, -1 where no chord was found
```

Tests: `backend/tests/test_chords.py` (an independent oracle that works from frequencies and explicit permutations; every one of the 231 chord types in every inversion) and `tests/test_chords_audio.py` (synthesized chords through the real note analysis).

## Audio frames UI

**Layout** (since feature 008): the page has two columns. The left column holds the audio file chooser at the top, then the progress and error messages and the result: the frame preview with its playback controls (play/pause, loop, position slider), followed by the result summary. The right column holds the settings and the *Create frames* button, so new settings can be added there without moving the preview. Window size, frame rate and window spacing share one row. Each setting's explanation sits behind a small info (*i*) button that opens a popover (Escape or a click elsewhere closes it); validation errors and the below-minimum spacing notice stay visible under their field. Below 960 px wide the columns stack, with the chooser and preview first and the settings after. The components are `FilePicker.vue`, `SettingsForm.vue` and `InfoPopover.vue` in `frontend/src/components/`, and the text of the explanations is in `frontend/src/utilities/help.ts`.

Open the frontend, choose a `.wav`, pick the window size from the dropdown (a power of 2: 4096, 8192, 16384 or 32768; default 4096), set the frame rate (1–60, default 30), and press *Create frames*. The server reads the sample rate from the file, runs the note analysis, averages the windows within each frame period, and writes one color PNG per frame. By default (the `tiles` image type, see **Image type** below) it is an indexed-colour file that decodes to exact RGB values: a 12 × 7 grid of tiles spread over a **600 × 400** frame (exactly 3:2; it was 252 × 168 with tiles of 21 × 24 pixels before feature 021): columns of 50 pixels and rows of 57 or 58 pixels, since 400 does not divide into 7 whole rows with one row per octave and one column per note name, so the tile directly below a note is the same note an octave higher (double the frequency). The lowest note (55 Hz) is the top-left tile, and only the first 84 notes are drawn (up to about 6645 Hz); the four highest of the 88 analyzed notes are left out of the picture but still count when the colors are scaled to the loudest value in the file. Each tile's color is the color of the chosen colormap at the strength of its own note (see **Colormap** below). The page then plays the frames as an animation (play/pause, loop, position slider).

- `POST /api/jobs` (multipart: `file`, `window_size`, `frame_rate`) creates the frames. `GET /api/jobs/{job_id}/frames/{index}` returns one PNG. Errors are `{"detail": "..."}`.
- Uploaded audio goes to `<system temp>/music-visualizer/audio/<job_id>/audio.wav` and frames to `<system temp>/music-visualizer/frames/<job_id>/`. Override with `MV_AUDIO_TEMP_DIR` and `MV_FRAMES_TEMP_DIR`. Old submissions are not cleaned up automatically.
- Limits are settings in `backend/app/config.py` and can be overridden with `MV_` environment variables: 200 MB upload (`MV_MAX_AUDIO_BYTES`) and 30,000 frames (`MV_MAX_FRAMES`).
- **Window spacing** sets how far apart windows start, as a multiple of the window size: with a window of 8192 and a spacing of 0.25, windows start at samples 0, 2048, 4096 and so on. Below 1 the windows overlap; 1 is consecutive windows; above 1 there are gaps. The field defaults to one frame period in samples divided by the window size (rounded down to 6 decimals), so each frame gets its own window. It is recalculated whenever the window size, frame rate or file changes (replacing anything typed), using the chosen file's sample rate read from its header, or 44.1 kHz before a file is chosen. A spacing that would give a step under one sample is raised to exactly one sample and the page says so. In the API it is the optional `window_spacing` field (omitted means the default), and the response adds `window_spacing`, `step_samples`, `window_count` and `spacing_raised`.
- **Colormap** (since feature 014) chooses how each tile is colored. It replaces the earlier color rules (a hue moved by related notes, a saturation and a per-frame brightness from the loudness of the sound, and the Brightness, Saturation, Hue steps, Saturation steps and Brightness steps settings), which made the animation "blinky" and have been removed. The choices are four of matplotlib's named colormaps: `summer` (green to yellow), `autumn` (red to yellow), `hot` (the default: dark red through red and yellow to white) and `cool` (cyan to magenta), with exactly matplotlib's 8-bit colors (the 256-entry table of each, read from `matplotlib.colormaps`; matplotlib is now a requirement). A tile's color is the table entry at the position `sqrt(value / peak)`, rounded to one of 256 steps, where `value` is that note's smoothed value in the frame and `peak` the largest smoothed value anywhere in the file (all 88 notes count, as before): a note with no strength has the first color of the scale, the strongest note of the file the last, and a stronger note never has an earlier color. A tile's color therefore depends only on its own note's strength and the file's peak: not on any other note, not on the loudness of the frame, and not on the frame number, so a steady note keeps one color and the picture is no longer dimmed or brightened as a whole. A silent file has every tile in the first color of the scale (a very dark red for `hot`). Hidden tiles (see Threshold) are black; `hot` starts at a very dark red (10, 0, 0), so with `hot` a quiet tile and a hidden one look much alike, which the other three colormaps avoid. On the page it is the **Colormap** dropdown (Summer, Autumn, Hot, Cool, starting at Hot) with an info button and a line in the result summary. In the API it is the optional `colormap` form field (exactly `summer`, `autumn`, `hot` or `cool`, lowercase; leave it out for `hot`; anything else, including an empty value, `viridis` or `hot_r`, is refused with a 400 saying "The colormap must be one of summer, autumn, hot, cool."), and the response adds `colormap`. A request that still sends the removed fields (`energy`, `brightness`, `hue_step`, `saturation_step`, `brightness_step`) is accepted and they are ignored; the response no longer reports them. The definition is in `specs/014-colormap-colors/data-model.md`.
- **Smoothing** is a slider from 0.00 to 0.80 (steps of 0.01, default 0). Since feature 012 it works together with the **Smoothing window** below: each frame is mixed with the frames before it. With `s` the smoothing and `w` the window, frame `t` becomes `( A[t] + s*A[t-1] + s*A[t-2] + ... + s*A[t-k] ) / ( 1 + s*k )`, where `A` are the *unsmoothed* values and `k = min(t, w)` is the number of earlier frames that exist. The current frame has weight 1 and each earlier frame in the window has the same weight `s`; the weights are divided by their sum, so a value that is the same in all of these frames stays that value, and the first frame (which has no earlier frames) is left as it is. Smoothing 0 is no smoothing, whatever the window is. Only the frame itself and earlier frames are used, and the earlier frames are the raw values, not earlier smoothed results, so the memory is finite: a note that stops is exactly gone `w` frames after its last frame (it does not keep an endless faint trace as the running average of features 006 to 011 did), and a note that starts reaches its full value after `w` frames. For example, with `w = 2` and `s = 0.5` the values 8, 4, 2 become 8, 5.33 and 4; with `w = 3` and `s = 0.5` a note that sounds in one frame is 0.4 of its value in that frame, 0.2 in each of the next three frames and exactly 0 after that. It is applied to the note values before they are turned into colors (each note from its own history only), so the colors are scaled against the loudest smoothed value and the Threshold works on the smoothed values. It works per frame, so the same settings span less real time at a higher frame rate. Frames made with a Smoothing above 0 look different from those made before feature 012, because the meaning of the setting changed. Changing it means submitting again. In the API it is the optional `smoothing` field (leave it out for 0; an empty value or one outside 0.0 to 0.8 is refused with a 400), and the response adds `smoothing`. The definition is in `specs/012-smoothing-window/data-model.md`.
- **Smoothing window** (since feature 012) is how many earlier frames are mixed into each frame: a whole number from **1 to 20**, default 1. With 1 each frame is blended with the one before it, with 20 with the twenty before it; it has no effect while Smoothing is 0. On the page it is the **Smoothing window (frames)** number field directly above the Smoothing slider, with an info button and a line in the result summary; a value that is not a whole number from 1 to 20 shows an error under the field and nothing is sent. In the API it is the optional `smoothing_window` form field (leave it out for 1; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The smoothing window must be a whole number from 1 to 20."), and the response adds `smoothing_window`.
- **Image type** (since feature 013) chooses which kind of picture is made from a frame's note values. The choices are **Tiles** (`tiles`, the default: the picture described above, flat tiles with hard edges, written as an indexed-colour PNG), **Blended tiles** (`blended`), since feature 015 **Contour** (`contour`, described in the next paragraph) since feature 019 **Circles** (`circles`, no grid at all, described after Contour) since feature 022 **Circles paint** (`circles_paint`, the same circles with no memory, described after Circles) since feature 025 **Concentric** (`concentric`, described after Circles paint) since feature 027 **Decay** (`decay`, described after Concentric) since feature 030 **Decay Exp** (`decay-exp`, described after Decay) since feature 032 **Polar Chords** (`polar-chords`, described after Decay Exp), since feature 034 **Energy Graphs** (`energy-graphs`, described after Polar Chords) and, since feature 035, **Chromatic Decay** (`chromatic-decay`, described after Energy Graphs). Everything that decides the 84 tile colors (analysis, smoothing and window, the colormap and the threshold) works the same for both. A blended frame has the same size (600 × 400), the same 12 × 7 grid of 50 × 57 or 58 pixel tiles, the same frame count and timing, but the colors of neighbouring tiles fade into each other: across every edge that two drawn tiles share there is a Gaussian feather (a Gaussian blur of the edge confined to a band that reaches the **blend width** on each side of the edge, with a standard deviation of a quarter of the reach, so the edge itself stays fairly sharp and only the tails are soft; at the default width the feather is about 25 pixels across, 12.5 on each side of an edge) with an even 50/50 mix at the edge itself. A pixel is the mix of up to four tiles, weighted by the product of its horizontal and vertical weights (a corner where four tiles meet is 25% each); pixels outside every band have exactly their tile's color, so the middle of each tile stays flat. The blend works on the finished colors and on where the tiles are in the picture, not on which notes they stand for: tiles are neighbours only if they touch in the grid (the end of one row and the start of the next do not blend), the picture's outer border is not blended (it does not fade to black), and a tile that the threshold hides is not a tile of its own: it is the background, the middle color of the colormap, and a drawn tile fades into it like into any other color (with the threshold off no tile is hidden, so the pictures are as they were; the flat Tiles type still shows a hidden tile as black). The colormap and the threshold decide the tile colors before the blend, so the in-between colors at the edges are blends of colormap colors (and black). Blended frames are true-color PNGs (many more than 84 colors), so their files are larger (about 15 to 25 KB against about 1 KB) and they take longer to create (about 1.4 ms per frame against 0.3 ms on the development machine). On the page it is the **Image type** dropdown (Tiles, Blended tiles, Contour or Circles, starting at Tiles) with an info button and a line in the result summary. In the API it is the optional `image_type` form field (exactly `tiles`, `blended` or `contour`, lowercase; leave it out for `tiles`; anything else, including an empty value, is refused with a 400 saying "The image type must be one of tiles, blended, contour, circles."), and the response adds `image_type`. The definition is in `specs/013-image-type-blended-tiles/data-model.md`.
- **Contour** (since feature 015) is the third image type: instead of tiles, the 12 × 7 grid of smoothed note values is drawn as a **filled contour map**, bands of color that flow from one note to the next like the elevation map of a landscape in which every note is a point on the grid and its strength is the height. It is drawn by matplotlib: `contourf` on the coordinates `np.linspace(0, top, 12)` by `np.linspace(0, top, 7)` (`top` is the largest value of the frame being drawn, worked out again for every frame; with the axes off this changes no pixel, the colors come from the scale below), with the selected colormap, the axis decorations off (`set_axis_off`), saved with `pyplot.savefig` from a figure that is exactly 600 × 400 pixels, so the contour fills the whole picture with no axes, border or margin. The picture has the same orientation as the tiles (lowest octave at the top, lowest note name at the left), the same frame count and timing, and is an opaque RGBA PNG (about 1 to 2 KB). **Directional smoothing** (`directionalSmoothing` in `backend/app/services/contour.py`) softens the hard edges: the grid of the frame (first row at the bottom, as it is drawn) is visited point by point, row by row, and each point, the first two rows and the first two columns excluded, is averaged with its predecessors in the first of three directions in which the last step is larger than the step before it: along the **diagonal** (the point, the diagonal neighbour and the one before it: the average of **three** values), along the **columns** (the point and its neighbour before it in the row: **two** values) or along the **rows** (the point and the neighbour above it: **two** values); if no direction qualifies the point is left as it is. The changes are made in place, so a point sees the smoothed values before it. The smoothing works on a copy of the frame's values (an earlier version smoothed the caller's own array, so drawing the same array twice smoothed it twice), the colors are those of the colormap at the smoothed value, and the scale still ends at the frame's largest value *before* the smoothing, so a lone loud note is drawn a little lower than its raw value. Things worth knowing: **the contour has 12 level edges (11 bands), evenly spaced from the smallest to the largest value of the smoothed grid of the frame being drawn** (`np.linspace(Z.min(), Z.max(), 12)`; matplotlib chose the levels before the number was raised), and **the color scale runs from 0 to the largest value of the frame being drawn** (so the loudest note of every frame is at the end of the colormap, and a given strength can have a different color in different frames; until 2026-10-12 it ran to `max`, the largest smoothed note value anywhere in the file, the four undrawn notes included, for the whole file); **the scale is linear** in the strength, unlike the tiles, which take the square root of the share of the peak, so a quiet note is closer to the start of the colormap in a contour than in the tiles; Smoothing, its window, the Threshold and the Colormap apply as for the other types (a note hidden by the Threshold counts as 0, so it does not raise the contour); a frame in which every value is the same (a silent file, a quiet moment, every note hidden) is one flat picture of the colormap's color for that value (the first color for 0), because matplotlib has no contour to draw there; the **Blend width does not apply** (a value sent with `image_type=contour` is accepted and ignored). A contour job takes longer than a tiles job: about 14 ms per frame on the development machine (a 60 second file, 1,800 frames, in about 25 s; 300 frames in about 4 s) while a whole tiles job of the same 60 second file, analysis included, takes about 1 s and a blended one about 1.3 s. matplotlib's `pyplot` is imported only when a contour is drawn (windowless Agg backend) and holds global state, so contour drawing runs one job at a time. The code is in `backend/app/services/contour.py`; the definition is in `specs/015-contour-image-type/data-model.md`.
- **Frame size** (since feature 021): every frame of every image type is **600 × 400 pixels** (3:2), where it was 252 × 168. The old frames were shown by the page at up to about 660 pixels with pixelated scaling, so every pixel was blown up more than two and a half times and the pictures looked blotchy; the pictures are now **drawn** at the larger size, not enlarged: the tile grid is spread over the whole frame (50-pixel columns, rows of 57 or 58 pixels, at every oversampling within one pixel), the soft edge of blended tiles keeps its width in proportion to a tile, a contour is drawn as a 600 × 400 figure and the circles have smooth edges at their real size. The frame count, the file names, the timing, the notes and the colors do not change (the colors at the centers of the tiles are exactly as before); the size is fixed, not a setting; frames that already exist are not converted. The frame player shows a frame at its own size, up to 600 pixels (a 1 pixel outline, no border, no pixelated scaling), and scales it down smoothly keeping 3:2 on a narrower window. Measured for a 60 second file (1,800 frames) at 252 × 168 and at 600 × 400: tiles 0.6 s and 1.0 s (7.1 s at oversampling 5), blended tiles 1.0 s and 6.4 s, contour 15 s and 20 s, circles 3.8 s and 18 s at the defaults and 9.6 s and 50 s at the largest settings; the frames take 1.3 to 3.6 times the room (blended tiles the most: 18 to 67 MB). The size is defined once, `IMAGE_WIDTH` and `IMAGE_HEIGHT` in `backend/app/services/frame_rendering.py` (with `REFERENCE_WIDTH`, the 252 pixels the circles are measured against); the definition is in `specs/021-wider-frames/`.
- **Circles** (since feature 019) is the fourth image type, `circles`: no grid at all, but circles that **wander as the music plays**. In every frame the **strongest notes of that frame** (5 to 12 of them: the **Notes** setting of the Circles group, `circle_notes`; by smoothed value, ties to the lower note) are sorted from the strongest down, and each puts down one circle; a note with no energy puts nothing down. The circle of rank r is placed relative to the **circle that rank r had in the previous frame** ("the last note at that index"), moved by an **angle** and a **distance** that come from the note: the angle is the note's name counted from C (C = 0, C# = 1 ... B = 11) times **30 degrees**, mirrored (360 minus the angle) for octaves below 4, with 0 degrees pointing right and angles growing counter-clockwise on the screen; the distance is **1 + |octave - 4|** units (octave 4 is 1 unit, every octave above or below it adds one; the notes run from octave 1, 4 units, to octave 8, 5 units), a unit being the **Movement** setting (`circle_unit`) in pixels. So an F5 (150 degrees, 2 units), an F3 (210 degrees, 2 units) and an A4 (270 degrees, 1 unit) move the way those numbers say. The angle and the octave are those of the **real note**, not of the application's grid (whose first column is A, 55 Hz, so F5 is in grid column 8): the note index `i` is MIDI note `33 + i`, its name `midi % 12` and its octave `midi // 12 - 1`. A rank whose note is the **same note at the same volume** as the last note of that rank does **not move**: its new circle is put on the same place as the last one (it is still added to the memory, so the older circle under it is covered by the newer, opaque one). "The same note" is the same note index (so the same name and octave); "the same volume" is the same color index, the volume as the picture shows it, 0 to 255 on the tiles' square-root scale, so two values that round to one color count as the same and exact equality of the floating-point values is not needed. The last note of a rank is kept across frames in which the rank has no note, and the first circle of a rank has no note before it, so it moves. Every rank starts from the **middle of the picture**, a rank that gets no note keeps its place, and the places **wrap around** the 600 × 400 picture's edges (a circle near an edge is cut off by it, not drawn again on the other side). A circle's color is the colormap's at the note's strength on the same scale as the tiles (the square root of the share of the file's loudest smoothed value), so the same strength has the same color in every frame. The picture **remembers** the last *memory* circles (100 to 500) in a circular buffer and draws all of them in every frame, as **smooth, anti-aliased** discs (each picture is drawn at 4 times its size and averaged down, so an edge pixel is a mix of the circle and what is under it and a circle can sit between pixels; the factor is `SUPERSAMPLE` in `circles.py`) on a background of the colormap's **middle color** (the entry halfway along its 256-color table, row 128, so it changes with the colormap), oldest first and newest on top, each with an **opacity that falls with its age**: the newest circle is fully opaque and a circle `age` places back in a memory of m circles (0 for the newest) has the opacity (m - age) / m, so the oldest, just before it is dropped, has only 255 / m of full opacity (1 to 3 parts in 255 for the memory sizes allowed) and is barely visible (the fade is a straight line, a circle halfway back is half opaque, and where circles overlap their colors blend); within a frame the weakest is added first, so the strongest is on top and the last to be dropped. **Resize by volume** (the optional setting `circle_resize`, a boolean, **off** by default): when on, the radius of each circle is multiplied by a factor that goes in a straight line from **1 for the faintest note to 3 for the loudest note of the file** (it was first 1/2 to 2; the user changed it to 1 to 3 so that a circle is never smaller than the radius setting) (factor = 1 + 2 c / 255, c being the circle's color index on the tiles' square-root scale, so the energy and the color follow the same scale; a note of no energy puts no circle down at all). A circle keeps the size it was given when it was put down, so a trail shows the volume of the music as a trail of sizes; places, colors and opacities do not change, and the **Radius** setting is the smallest radius a circle gets (and the scale is the square root of the share, which lifts quiet notes: a note with a quarter of the file's loudest value has a color index of 128 and a factor of about 2, one with 1% of it about 1.2). Movement and Radius are measured in pixels of a **252-pixel-wide reference frame** (the frame size before feature 021) and are scaled by 600 / 252 (about 2.38) when the circles are drawn on the 600 × 400 frame, the Resize by volume factor, the start in the middle and the wrap-around included, so the same settings give the same picture in proportion to the frame, only sharper (a Radius of 4 is a disc about 9.5 pixels in radius; the help texts say so; the readouts still say "px"). The four numeric settings only for circles are the **Movement** (called Unit until feature 020; 1 to 10 pixels, default 4: the length of one step, which does not set how big a circle is), the **Radius** (called Size until feature 020, when it stopped being a circumference: the radius of a circle in whole pixels, **4 to 8**, default 4; before, the circumference was 25 to 50 pixels, a radius of 3.98 to 7.96, so the sizes that can be chosen are the same, as five whole-pixel steps, and a default circle looks the same but is not byte-identical to the files made before), the **Memory** (100 to 500 circles, default 300) and the **Notes** (called Circles per frame until feature 020; 5 to 12, default 8); in the API `circle_unit`, `circle_radius` (the old `circle_size` is gone: a request that still sends it is accepted and the field ignored), `circle_memory` and `circle_notes` (and `circle_resize`, `true`, `false`, `1` or `0` in any case, refused with 400 and "The circle resize must be true or false."), refused with 400 and "The circle movement must be a whole number from 1 to 10.", "The circle radius must be a whole number from 4 to 8.", "The circle memory must be a whole number from 100 to 500." or "The number of circle notes must be a whole number from 5 to 12." (they are validated for every image type and only have an effect for circles), and all five (with `circle_resize`) are in every response. Smoothing and its window and the Colormap apply. **Interpolate, Oversampling, Notes (the 12 to 84 choice), Threshold and Blend width have no meaning for circles**: a frame depends on the frames before it, so none can be skipped, and the others describe a grid of tiles; the server accepts them and ignores them, and the page does not show them while Circles is chosen (before feature 020 it greyed them out). On the page, Circles is the fourth choice of the Image type dropdown (Circles paint is the fifth); choosing it shows the Circles group (see the settings page below) with the sliders Movement ("4 px"), Radius ("4 px"), Memory ("300 circles") and Notes ("8 notes") and the **Resize by volume** checkbox ("Off" or "On"), each with an info button, and the result summary shows those values under those names and hides the lines that do not apply. A steady note draws a straight line of circles (and wraps around), a melody wanders in a cluster, and the largest settings (movement 10, radius 8, memory 500, 12 notes) fill the picture with overlapping, fading discs. The work is cheap: a 60 second file (1,800 frames) takes 2.40 s at the smallest settings (a tiles job takes 0.76 s), 3.59 s at the defaults and 9.51 s at the largest, radius 8 included (measured when the setting was still a circumference of 50, the same size of disc) (about 1.3 to 5.3 ms a frame, the analysis included; the smooth edges and the fading discs made it slower than the 0.74 to 1.65 s of the first version's hard, solid discs; at 8 times the size the largest took 31 s for hardly any gain). The code is in `backend/app/services/circles.py`; the definition is in `specs/019-generative-circles/data-model.md`.
- **Circles paint** (since feature 022) is the fifth image type, `circles_paint`: **the circles of Circles with no memory**, painted onto a copy of the previous picture, like a painter's canvas that the music builds up. Which circles are put down in a frame (the strongest notes and their ranks), where (from the rank's previous place, by the angle of the note's name and the distance of its octave, with the stay-in-place rule and the wrap-around), in which color and with which radius (Movement, Radius, Resize by volume, scaled to the 600 × 400 frame) are **exactly those of Circles**, because the same plan is used (`plan_circles` with no memory: nothing is kept and nothing is dropped). What differs is the picture: the first frame is the background (the colormap's middle color) with its circles painted on it, and **every later frame is a copy of the previous frame with this frame's circles painted on top**, weakest first, so the strongest is on top. A circle is **solid** (a pixel well inside it has exactly its color, whatever was under it) with the **same smooth edge** as the circles of Circles: it is drawn on a patch four times larger, averaged down into a coverage mask of 0 to 255, and the canvas is mixed with the circle's color through the mask (Pillow's `paste`), so an edge pixel is a mix of the color and what was there; a circle that sticks out of the picture is cut off by the edge and is not painted again on the opposite side. The paint **never fades and is never cleared**: it stays until a later circle covers it, so on a long file the canvas becomes dense layers of the latest circles, and a note held at one volume repaints the same circle, which only makes its one-pixel edge a little harder. A silent stretch gives exact copies of the frame before. The settings are those of Circles **except Memory**: Movement, Radius, Resize by volume and Notes (`circle_unit`, `circle_radius`, `circle_resize`, `circle_notes`, with the same ranges, defaults and messages), Smoothing, its window and the Colormap; `circle_memory` is still checked like every circle setting (refused with 400 and the usual message if it is not a whole number from 100 to 500) and then ignored, and Interpolate, Oversampling, Threshold, the 12 to 84 Notes and Blend width are accepted and ignored. The request value is `circles_paint` (a name that is not one of the five is refused with 400 and the message that lists them). On the page it is the fifth choice, labelled "Circles paint"; choosing it shows the group **Circles paint** with Movement, Radius, Resize by volume and Notes (two to a row, no Memory), Data smoothing and no Image smoothing; the values of the four shared controls are kept when switching between Circles and Circles paint; the result summary shows those four values and no Memory line. Frames depend on the earlier frames, so none can be skipped. Measured for a 60 second file (1,800 frames of 600 × 400): **4.4 s** at the default settings and 2.2 s at the largest (movement 10, radius 8, 12 notes, resize on), against 17 s and (resize off) 45 s for Circles, and the frames take 300 MB and 73 MB (Circles: 109 and 220 MB): the canvas keeps all its detail, so its files are larger at the default settings. The code is in `backend/app/services/circles_paint.py`; the definition is in `specs/022-circles-paint/`.
- **Concentric** (since feature 025) is the sixth image type, `concentric` (`backend/app/services/concentric.py`): **a circle for each of the 84 notes**, centered on the tiles of the 12 × 7 grid (the first note top left, the lowest octave at the top). The **size** of a circle comes from how loud its note is compared with the others of the same frame: it has a **step** from 1 to 12, `max(1, ceil(12 × sqrt(value ÷ the loudest of the frame's 84 notes)))` (the square root is the scale of the tile colors), and a radius of `step / 12` of the **full radius**, 25 pixels (half the width of a cell, so full-size circles in a row just touch; the rows are about 7 pixels apart). The loudest note of every frame is full size, a note with no energy is a dot of one ring (so all 84 circles are always drawn), and a silent frame is 84 dots. A circle of step `s` is **`s` flat rings**: ring `k` (1 in the center, 12 outermost) fills the radii from `(k − 1) / 12` to `k / 12` of the full radius, so a full circle looks like twelve concentric circles and a smaller one is a full one without its outer rings. The **colors** of the rings follow the **beat**: the same position in the local energy peak as the Beat coloring (0 at the minimum of the local peak, 1 at its maximum, read in the middle of the frame, 0 when no beat is known), and ring `k` is the colormap's table entry at `rint((k − 1) / 11 × (0.5 + 0.5 × position) × 255)`. At the top of the peak the twelve rings of a full circle run through **the whole colormap**, from its first color to its last; at the bottom only **half way**; every circle of a frame has the same ring colors. The **background** is the colormap's middle color (table row 128), so at position 0, where ring 12 is also row 128, the outermost ring of a full circle looks like the background. The edges are smooth. Only the **Local peaks** settings (Minimum distance and Prominence, with no Beat coloring checkbox: the beat is always measured for Concentric) and **Data smoothing** apply; Threshold, Notes, Oversampling, Interpolate, Gaussian smoothing, the blend width and the circle settings are checked as always and ignored. On the page Concentric shows the groups Analysis, Colormap, Image type, **Local peaks** (the group id is `concentric-peaks`, the two sliders only) and Data smoothing, and its result summary lists the two values. The geometry is worked out once (for every pixel its cell and the share of its 4 × 4 sub-pixels in each ring) and a frame is then two table lookups and a blend, identical to drawing the rings on a four times larger canvas and averaging it down: a minute of music at 30 frames a second (1,800 frames) takes about 9 seconds.
- **Decay** (since feature 027) is the seventh image type, `decay` (`backend/app/services/decay.py`): **the same 84 circles as Concentric, in the same places and with the same Note layout, but each circle is one flat disc that keeps points from frame to frame**. Every circle has **0 to 64 points**, 0 before the first frame. The points set the **size** (the smallest circle, one twelfth of the full radius, at 0 points; full size, just touching its neighbours, from 24 points on; linear in between) and the **color** (the colormap's first color at 0 points, its last color at 32 points; the disc is flat up to there). From **32 to 64 points the circle gets the 12 concentric rings** of Concentric: ring `k` (1 at the center) is at `b − s × (k − 1) / 11` of the way along the colormap, with `b = min(points, 32) / 32` and `s = (points − 32) / 32`, so at 32 points every ring is the last color and at **64 points the 12 rings run from the last color (the center) to the first (the edge)**; as a circle fades the outer rings come back to the last color first, so the decay is seen all the way down from 64. In every frame the **5 loudest notes** (the smoothed values, ties to the lower note, a note with no energy does not count) **gain** 24, 20, 16, 12 and 8 points in order of loudness, plus **8 × the frame's position in the local energy peak** (8 at the top of the beat, 0 at the bottom; the Local peaks measurement is made for every Decay job); the points are added to what the circle has and held between 0 and 64. Every **decay rate** frames (a number from **0.25 to 4** in steps of 0.25, default **1**; below 1 several smaller steps are taken in every frame, which is smoother, above all at higher frame rates; the one setting of this image type, counted from frame 1) there is a **decay step**: every circle gives points to each of the circles around it (the up to 8 cells around it on the grid, diagonals included, no wrap-around). **The rate depends on the points** (since 2026-11-01), per neighbour and per frame; **the four amounts are settings of the Decay group** (since 2026-11-01: **Low saturation**, **Medium saturation**, **High saturation** and **Saturated**, sliders from 0.5 to 3 in steps of 0.5; request fields `decay_low`, `decay_medium`, `decay_high`, `decay_saturated`; each checked for every image type before the file is read, `The <level> saturation decay must be a number from 0.5 to 3.`, and echoed in the response; the page calls the categories saturation levels and does not list their points), with the defaults: a circle with **1 to 8 points gives 0.5** (1 every 2 frames), **above 8 and up to 20 points 1**, **above 20 and below 64 points 2**, and a **saturated circle (64 points) 3** (24 in all), so a held note spreads faster the fuller its circle is. **A step moves `decay rate` frames' worth** (the setting says how often the decay happens, not how much: the average rate is the same at any setting; with a rate above 1 a circle with plenty of points gives most of what it has away in one step, so the spots disappear in jumps, and a rate below 1, which takes several smaller steps in every frame (0.25 takes four), is the smoothest). A circle on an edge or in a corner **decays as if it had 8 neighbours**: it gives the same amount to each neighbour it has (5 on an edge, 3 in a corner) and the rest is lost, so every circle loses the same total whatever its place. A circle with fewer points than it would give only gives what it has, in the same proportions, so no points appear from nothing; all circles give and receive at the same time from the points before the step; and a circle left with less than a hundredth of a point has none, so a faded circle is really at 0. The size and the color are antialiased. The settings that apply are the colormap, the analysis settings, **Decay rate**, **Note layout**, **Local peaks** (Minimum distance and Prominence, no checkbox) and **Data smoothing**; Threshold, Notes, Oversampling, Interpolate and Gaussian smoothing are accepted by the request and ignored. The request field is `decay_rate` (a whole number from 1 to 10, checked for every image type before the file is read, `The decay rate must be a number from 0.25 to 4 in steps of 0.25.`) and it is echoed in the response. The frames are 600 × 400, with the count, names and timing of the other image types; the other six image types are unchanged.
- **Decay Exp** (since feature 030) is the eighth image type, `decay-exp` (`backend/app/services/decay_exp.py`): **Decay with a different rate at which the circles take on and give away points**. Everything else is Decay: the same 84 circles, their size, color and rings by points, the 0 to 64 points, the 5 loudest notes of a frame gaining points with the beat bonus, the decay steps every **decay rate** frames (the same slider, 0.25 to 4, default 1, the one setting of this image type; request field `decay_rate`), the neighbours, the edge and corner rule, the Note layout and the Local peaks settings (measured for every Decay Exp job). Two amounts change. **The gain**: a note that would gain `g` points in Decay (24, 20, 16, 12 or 8 by rank, plus `8 × position`) gains `g × e^(−g/taper)`, so about 1.19, 1.64, 2.17, 2.68 and 2.94 points with no beat at the start, when the taper is 8: **the loudest note gains the least**. **The taper is not fixed**: it starts at 8, **rises by 0.01 in every frame up to 12** (the cut gets gentler, so the gains grow: at 12 they are about 3.25, 3.78, 4.22, 4.41 and 4.11), and **as soon as more than 10 circles have more than 32 points it falls by 0.01 in every frame until it is back at 8**, and then rises again; it never leaves 8 to 12. It changes the gain only. **The loss**: instead of the amounts of the four saturation levels, a circle with `p` points before a step gives **each neighbour** `sin²(π/2 × p/64)` points per frame (0 with no points; about 0.0006 at 1 point, 0.04 at 8, 0.31 at 24, 0.5 at 32, 0.85 at 48 and 1 at 64, so **the fuller a circle is the faster it drains**: 8 points a frame in all at 64), a step moving `decay rate` frames' worth and a circle never giving more than it has. The four decay amounts (`decay_low`, `decay_medium`, `decay_high`, `decay_saturated`) are still accepted, checked and echoed, and have no effect; they are not shown for Decay Exp. **What this looks like**: a single steady note starts at about 1.2 points a frame and its circle grows for a long time as the taper rises (about 20 points at frame 100, 32 at frame 400), settling near 34; a group of notes close together fills more than 10 circles over 32 points, which turns the taper down, so it swings between 8 and about 10 while the biggest circle reaches about 57 and settles near 50; nothing reaches 64. After the sound stops the charged circles drain quickly, but a faint circle hardly drains at all (the loss falls with the square of the points), so the tail is long: after a loud passage the largest circle is under 1 point after about 3,100 frames (1 minute 43 seconds at 30 frames a second) and exactly 0 only after about 228,700 (about 2 hours); by then it has long looked like the smallest dot. The request value is `decay-exp` (with a hyphen); the frames are 600 × 400, with the count, names and timing of the other image types; the other seven image types are unchanged.
- **Polar Chords** (since feature 032) is the ninth image type, `polar-chords` (`backend/app/services/polar_chords.py`): **a polar bar graph of the notes and the chord**, bars that start at the center of the circle and reach outward, on the colormap's middle color. Angles are measured from straight up. The notes have **84 equal arcs** (about 4.29 degrees each). **Clockwise, each of the 84 piano notes has its arc** (with the **Note layout** Rows, the default, A1 first in order of pitch; with Spiral the arc of a note is the cell in which the spiral layout of feature 026 draws it, so middle C is in arc 29 instead of 27), and the **loudest notes of the frame get a bar** that fills their arc: how many is the one setting of the image type, **Notes shown**, a whole number from **5 to 8**, default **5** (request field `polar_notes`, checked for every image type before the file is read, `The number of notes shown must be a whole number from 5 to 8.`, and echoed in the response; a note with no strength never gets a bar and ties go to the lower note). **Counterclockwise, the chord ring has 84 arcs (as wide as a note's), one for each root letter and chord type: the 7 chord types of A, then the 7 of A#, and so on through the 12 letters (a letter is a note without its octave)**; the types are `(7)`, `(4, 7)`, `(3, 7)`, `(4, 10)`, `(4, 11)`, `(3, 7, 10)` and `(4, 6)`, in this order, found with the chord interval measurement of feature 031 (one chord at most per frame: the longest that fits among the 4 to 6 loudest letters of the frame, octaves combined, then the loudest and then the widest; the notes of the chord are not always among the drawn note bars). The root letter and the type decide the arc (`7 x letter + type`, letters from A: a C major triad is arc 22, E major arc 50); the octave and the inversion do not matter, and a fourth is the fifth of its upper note (C with F above it is the fifth of F: it is recorded as an inverted fifth). **Every bar reaches out to `0.5 + 0.5 x p` of the full radius** (190 pixels on 600 x 400), `p` being the frame's place in the local energy peak (0 at the bottom of the beat, 1 at the top, 0 when no beat is known), so the picture breathes with the beat and all the bars of a frame are equally long; the loudness is shown by the color. **The note bars follow their notes**: every volume (the loudest note, the second loudest, ...) keeps its own bar, and when the note of a volume changes between frames the bar moves **one arc (2 pi / 84) a frame**, the shorter way round the circle, toward the arc of the new note instead of jumping there (clockwise when both ways are equal), which smooths the animation; the first frame, and a volume that comes back after a frame without a note, are in the arc of the note, the color is the new note's at once, and where two bars meet in an arc the louder one is shown. The chord bar and the lengths are not smoothed. **Colors**: the notes run from the **middle of the colormap (a faint note) to its start (the loudest)**, the chord from the **middle to its end**, by the square root of the strength as a share of the largest value of the file (for the chord the average of its notes); with a colormap with two different ends, such as Cool Warm, the notes and the chord have a color family each, and a faint bar is close to the background color. The chord is drawn over the notes where they cover the same angles. The edges of the bars are smooth. The settings that apply are the colormap, the analysis settings, **Notes shown**, **Note layout** (it changes only the arcs of the notes; the chord does not depend on it), **Local peaks** (Minimum distance and Prominence, no checkbox) and **Data smoothing**; Threshold, Notes, Oversampling, Interpolate and Gaussian smoothing are accepted by the request and ignored. The frames are 600 x 400, with the count, names and timing of the other image types; the other eight image types are unchanged.
- **Energy Graphs** (since feature 034) is the tenth image type, `energy-graphs` (`backend/app/services/energy_graphs.py`): **a running histogram of the 84 piano notes with two data sets**, on the colormap's middle color, in the usual 600 x 400 frame, with a title, a legend and the octave labels A1 to A7. Each note has a **pair of thin bars**, the lowest note (A1) on the left: the **frequency** bar (the start color of the colormap) and the **amplitude** bar (the end color). **Frequency**: in every analysis window the 84 notes are ranked by strength and each adds its **rank score** to its own total, **84 for the loudest, 83 for the second loudest, and so on down to 1**; a note with no strength (under the noise floor of feature 033) adds nothing, and neither do the notes ranked below it; equal strengths rank the lower note first. **Amplitude**: in every window each note adds its **quasi-decibel** value, `20 log10(amp) / (20 log10(max))`, where `max` is the largest amplitude of any of the 84 notes in any window of the whole file: 1 for the loudest note of the file and less for fainter ones; a silent note adds 0, a negative value (an amplitude under 1) is clamped to 0, and a file whose loudest amplitude is 1 or less adds nothing (the ratio of logarithms is meaningless there). Both totals **accumulate** from the start of the file to the frame (a window is counted once, in the frame it starts in, so the last frame holds the sum over every window). **They are not drawn as totals** (a total grows with the length of the file, and the two have different sizes): each data set is divided by its own largest total, so that it runs from 0 to 1, and then put through a **softmax** over the 84 notes (`exp(x) / sum(exp(x))`), which puts the two on the same scale, each adding up to 1. A softmax is never 0 and its values are close to each other, so **the smallest share of each data set is then taken off all its shares**: the smallest bar of each data set has height 0 (a note that has not sounded has no bar when others have) and the clear winners stand out. The bars are then scaled by the largest remaining value of the frame, so **the tallest bar is always the same height** (336 pixels). A data set with no total yet (before the first sound, or the amplitude of a file that is never above 1) or with all totals equal has no bars. It has **no setting of its own, no request field and no response field**: the analysis settings and the colormap apply; the Data smoothing group is not shown for it on the page, and every other setting (smoothing, threshold, notes, oversampling, interpolate, Gaussian smoothing, note layout, Local peaks, Notes shown, decay) is accepted by the request, checked as for every type, and ignored; the beat is not measured for it. The frames have the count, names and timing of the other types and can be made into a movie (feature 029). The job costs about what Tiles costs plus the drawing (about 1.3 s for `backend/audio/sonata.wav`, 190 s at 5 frames per second). The definition is in `specs/034-energy-graphs/`; the first version of this type also had two pies (harmonic against non-harmonic energy, and loudness against the loudest window), which were removed on 2026-11-08.
- **Chromatic Decay** (since feature 035) is the eleventh image type, `chromatic-decay` (`backend/app/services/chromatic_decay.py`): **Decay Exp for the 12 chromatic tones only**. There are **12 circles, one for each letter** (a letter is a note without its octave, with its accidental, counted from A: A, A#, B, C, C#, D, D#, E, F, F#, G, G#, as in Polar Chords), on a **ring in circle-of-fifths order, clockwise from the top: C, G, D, A, E, B, F#, C#, G#, D#, A#, F**, 30 degrees apart, centered in the 600 x 400 picture (ring radius 150.9 pixels), with the full radius that lets two neighbouring full circles just touch (39.1 pixels). **The energy of a letter in a frame is the largest of the strengths of its 7 octaves** (not their sum), and the points are added as in Decay Exp with the 12 letters in the place of the 84 notes: the five loudest letters (ties to the lower letter, a letter with no energy not counting) gain 24, 20, 16, 12 and 8 points plus the beat bonus of up to 8, each cut back by `exp(-g / taper)` with the moving taper of Decay Exp (8 to 12). **The point levels (0 to 64), the size of a circle (one twelfth of the full radius at 0 points, full from 24), the colors and the twelve rings (from 32 points) are those of Decay and Decay Exp**, on the colormap's middle color. **The decay goes only to the two letters 5 and 7 semitones above** (letter `n` gives to `(n + 5) mod 12` and `(n + 7) mod 12`: C to F and G, F to A# and C, G to C and D), which on the ring are **the two neighbours of the circle's place** (7 above is the next one clockwise, 5 above the next one counterclockwise). A fourth and a fifth add up to an octave, so the receivers give back to the giver: a note decays to itself to some extent through the round trip (there is no direct share kept). **(Since 2026-11-10 the 8 below is `PRETEND_NEIGHBORS`, a constant of `chromatic_decay.py` that is 6: a circle gives away 6 times the loss, one sixth to each receiver and four sixths lost, instead of 8, one eighth and six eighths; Decay and Decay Exp keep `decay.NEIGHBOURS`.)** **How much is given is Decay Exp's**: a circle with `p` points gives away `8 x sin^2(pi/2 x p/64)` points per frame (the total a circle of Decay Exp gives, never more than it has), split as if it had 8 neighbours: **each of the two receivers gets one eighth of it, what a neighbour gets in Decay Exp, and the other six eighths are lost**, as for an edge or corner circle there (the ring has no edge: without this nothing would ever vanish, and the points would circulate and settle to an even level). All circles give and receive at the same time from the points before the step; points are held between 0 and 64 and a circle under a hundredth of a point has none, so a silent file ends with every circle at 0. **The decay rate of this type is a whole number of frames from 1 to 10** (default 1): a step falls at every rate-th frame and moves that many frames' worth of decay, so the average rate is the same whatever the setting (the levels are of the same order, not identical, because the loss is not a straight line of the points). It keeps the request field `decay_rate`, which is **validated for the image type**: a whole number from 1 to 10 for `chromatic-decay` (a value such as 2.5, 0, 11 or text is refused with 400 `The decay rate must be a whole number from 1 to 10.` before the file is read; 3 and 3.0 are accepted; the response echoes an integer) and, for every other type, 0.25 to 4 in steps of 0.25 as before. On the page it has its own control, **Decay rate** (1 to 10, in the group **Chromatic Decay**), whose value is kept separately from the Decay rate of Decay and Decay Exp. The settings that apply are the colormap, the analysis settings, the decay rate, **Local peaks** (the beat always charges it, no checkbox) and **Data smoothing**; the Note layout (it has no meaning for a ring of letters), the four decay amounts and every grid setting are accepted by the request, checked as for every type, and ignored. No new field in the request or the response. **The rings of the beat (since feature 036)**: in the empty middle of the ring of letters there is a **target of 12 concentric rings, 140 pixels across** (a radius of 70 pixels on 600 x 400, scaled with the picture size, 5.8 pixels a ring) that shows where the music is in its beat. For each frame the beat gives its position in the local peak (0 far from a peak or between peaks, 1 at the top of one, the measurement of the Local peaks settings that already charges the circles) and the distance from the peak is `1 - position`. **The center ring is the distance of the current frame `t`; ring `k` outward, from 2, is the average of the distances of the two frames `t - (2k - 3)` and `t - (2k - 2)`** (ring 2 is frames `t - 1` and `t - 2`, ring 3 is `t - 3` and `t - 4`, ring 12 is `t - 21` and `t - 22`), so the newest moment is in the middle and a flash at the top of a beat spreads outward one ring every two frames; the moments before the first frame count as far from a peak. A ring is colored from the colormap by its distance, **from the first (left) color at the top of the beat to the last (right) color at the bottom of the beat, using the whole colormap**: the position in the local peak is 0 to 1 in principle but inside the peaks of real music it hardly goes below about 0.55, so the distance is **stretched over the range of the beat of the file** (`beat_distances`: the highest position is distance 0 and the 1st percentile of the positions inside the peaks, `PEAK_BOTTOM_PERCENTILE`, is distance 1, in a straight line between and held at the ends; a frame outside every peak is 1), the colors between at the same share. The rings are always drawn for Chromatic Decay, with no setting and no new request or response field (the Local peaks settings change them as they change the charging); with no beat known (`write_chromatic_frames(..., beat=None)`) no target is drawn. The middle of the ring of letters is 224 pixels across, so the target never touches a circle. **Known consequence of keeping the point levels**: the taper only falls when more than 10 circles have more than 32 points, which with 12 circles hardly ever happens (in tests with five letters fed at the top of the beat the largest circle reaches about 33 points), so in practice the taper rises to 12 over 400 frames and stays there, and the circles are mostly small and in the first half of the colormap; the user asked to keep the levels for now, so it is a candidate for a later change. The frames have the count, names and timing of the other types and can be made into a movie (feature 029). The definition is in `specs/035-chromatic-decay/`.
- **Note layout** (since feature 026) says **which note is drawn in which cell of the 12 × 7 grid**, for the pictures with one shape for each note: **Tiles**, **Blended tiles**, **Concentric**, **Decay** and **Decay Exp**, and, as the arc of each note, **Polar Chords** (Contour, Circles and Circles paint ignore it). **Rows** (`rows`, the default) is the layout that always was: the notes in order like text, twelve to a row, the lowest note (A1) at the top left. **Spiral** (`spiral`, `backend/app/services/note_layout.py`) is a fixed arrangement around **middle C** (C4, the 28th of the 84 notes), which is in the **3rd row and the 6th column**: the next note up is in the cell to its right and the next note down in the cell to its left, the notes above C wind **clockwise** outward from it and the notes below it **counterclockwise**. It is made by two walkers that start at C's cell, each on a square spiral (legs of 1, 1, 2, 2, 3, 3, … cells): the high one goes east first and turns right after every leg, the low one goes west first and turns left; they take turns (the high one first), each putting its next note in the next cell of its own spiral that is on the grid and not yet taken, and the high walker (56 notes) goes on alone when the low one (27 notes) is done. The result, as the distance in semitones from middle C (`C`), is:

```text
 49 -21 -13  11  12 -12 -11 -10  13  22  36  50
 48 -22 -14  -5   4  -4  -3   5  14  23  37  51
 47 -23 -15  -6  -1   C   1   6  15  24  38  52
 46 -24 -16  -7  -2   3   2   7  16  25  39  53
 45 -25 -17  -8  -9  10   9   8  17  26  40  54
 44 -26 -18 -19 -20  21  20  19  18  27  41  55
 43 -27  35  34  33  32  31  30  29  28  42  56
```

Thirteen semitone steps are not between neighbouring cells, where a walker had to skip a cell that is off the grid or taken: -21/-20, -13/-12, -10/-9, -5/-4, -3/-2, 3/4, 4/5, 10/11, 12/13, 21/22, 35/36, 42/43 and 49/50. The layout is **a reordering of the 84 values of every frame into cell order** (`arrange_notes`), applied after the note selection and before the grid is interpolated (Tiles, Blended tiles) or before the circles are drawn (Concentric): the threshold hides the same notes, Notes keeps the same strongest notes (spread in pitch order along the spiral), the colors, the beat, the smoothing, Interpolate and Gaussian smoothing work on the notes as before, and **Oversampling blends the tiles that are next to each other on the screen**. With Rows the frames are exactly those made before this feature. The request field is `note_layout` (exactly `rows` or `spiral`, default `rows`; otherwise 400 "The note layout must be one of rows, spiral.", checked before the file is read for every image type), echoed in the response. On the page it is the dropdown **Note layout** (Rows, Spiral) in a group of its own, titled "Note layout", shown for Tiles, Blended tiles and Concentric after the group of the image type (after Image type for Concentric) and before Local peaks, and the result summary names it.
- **The settings page** (since feature 020) is a list of **titled groups**, each a section that can be folded and unfolded on its own (the browser's own disclosure element, so it works with the keyboard and tells assistive technology whether it is expanded; every group starts open, the state is not remembered, and a folded group keeps every value and still sends it). Inside a group the controls are laid out **two to a row** (a flex row that wraps; an odd last control takes the whole row; on a very narrow screen, below about 26 rem, one to a row), with the readout of a slider next to its label; labels and group titles are set in **Roboto Slab at 0.9 rem** (the variables `--label-font` and `--label-size` in `App.vue`; the font is loaded from Google Fonts by `index.html` and falls back to Georgia or another serif when offline). From the top: **Analysis** (Window size, Frame rate, Window spacing), **Colormap**, **Image type**, then the group of the chosen image type, then **Data smoothing** (Smoothing window, Smoothing) and **Image smoothing** (Oversampling, Interpolate, Gaussian smoothing; not shown for Circles). The group after Image type is **Tiles** or **Contour** (Threshold, Notes: the same controls for both), **Blended Tiles** (Threshold, Notes, Blend width) **Circles** (Movement, Radius, Resize by volume, Memory, Notes) or **Circles paint** (the same without Memory). A control that the chosen type does not use is **not shown** (before, it was greyed out); its value is kept, so choosing the type again finds it as it was, and it is still sent. A folded group that contains a value that is not allowed says "needs attention" in its title, and Create frames stays disabled as before. Four controls were renamed in the form, the info texts, the messages and the result summary: Unit to **Movement**, Size to **Radius** (now a real radius, see Circles), Circles per frame to **Notes** and Resolution to **Oversampling**; the request fields `circle_unit`, `circle_notes` and `resolution` keep their names, and `circle_size` became `circle_radius`. Nothing about how frames are made changed except the circles' radius. The group model is in `frontend/src/utilities/groups.ts`, the section in `frontend/src/components/SettingsGroup.vue`; the definition is in `specs/020-grouped-settings-ui/`. The layout was checked by tests of the group model, by server-side rendering of the form for each image type and by reading the styles; the look in a browser is the manual step of that feature's quickstart.
- **Blend width** (since feature 013) is how far the fade of the blended tiles reaches on each side of an edge, as a percentage of the tile width (50 pixels at the default grid): a number from **10 to 25**, default 25, so the reach is `percent × 50 / 100` pixels, from 5 at 10 to 12.5 at 25, the same distance in pixels for edges between tiles side by side and for edges between a tile and the one below it. Outside the reach the tile keeps its exact color, and the fades from opposite edges of a tile never meet (at most half of its width is faded), so a flat middle always remains. Only Blended tiles uses it: the Tiles and Contour pictures are the same for every blend width. On the page it is the **Blend width** slider (10 to 25 in steps of 1, starting at 25, with the readout "25% of a tile"), enabled only while Blended tiles is chosen (disabled for Tiles and for Contour, and while a job runs), and the summary shows it for Blended tiles. In the API it is the optional `blend_width` form field (a number from 10 to 25, decimals allowed; leave it out for 25; an empty, non-numeric or out-of-range value is refused with a 400 saying "The blend width must be a number from 10 to 25."; it is accepted and ignored with `image_type=tiles` or `image_type=contour`), and the response always adds `blend_width`.
- **Oversampling** (since feature 016, called Resolution until feature 020; the request field is still `resolution`) makes the picture finer without changing the music: a whole number from **1 to 5**, default 1. Every frame is drawn from a grid with one value per drawn note (12 columns by 7 rows); resolution *r* draws it from a grid of **12 r by 7 r** values instead (12 × 7, 24 × 14, 36 × 21, 48 × 28 or 60 × 35), made from the original one by linear interpolation: evenly spaced positions from the first to the last column and row (`np.linspace`) are read from the smoothed note values with `np.interp`, along every row and then along every column. The four corners keep their original values, every new value lies between the original values around it (never louder than the loudest note or quieter than the quietest one) and the end of one row never mixes with the start of the next. The interpolation comes **after** the smoothing, and the **Threshold and the colors work on the new values** (a tile is hidden when its own interpolated value is below the threshold's share of the file's loudest note; the colors' scale and that reference are the file's largest original smoothed value at every resolution, so at a higher resolution the strongest tile can be a step short of the colormap's last color when the loudest note falls between two sample positions, only the four corners are exact). The picture keeps its size, **600 × 400 pixels** (252 × 168 before feature 021), so a higher oversampling means smaller tiles: 50 × 57 or 58 pixels at 1×, 25 × 28 or 29 at 2×, 16 or 17 × 19 or 20 at 3×, 12 or 13 × 14 or 15 at 4× and 10 × 11 or 12 at 5×. **Tiles** are then up to 2,100 flat tiles; a Tiles frame has more colors than an indexed-colour PNG can hold above 1×, so frames at 2× and above are true-color PNGs (about 1.4 KB at 3× and 2.3 KB at 5×, against 0.9 KB at 1×) and a Tiles job takes about 2 to 3 times as long (a 60 second file: 0.8 s at 1×, 1.9 s at 3×, 2.3 s at 5×). **Blended tiles** keep the blend width as a share of the (now smaller) tile, so the fade shrinks with the tiles: at 5× a width of 25% is about one pixel at each edge (the reach is a quarter of the mean tile width, 4.2 pixels), and below about 24% at 5× (or 12% at 4×) it is narrower than the pixels' centers and changes nothing, so Blended looks like Tiles there; the middle of every tile stays flat. **Contour** is drawn from the finer grid (finer steps, a smoother outline) at the same cost per frame (about 8 to 15 ms). At resolution 1 everything is exactly as without the setting, byte for byte. On the page it is the **Oversampling** slider in the Image smoothing group (1 to 5 in steps of 1, starting at 1, with the readout "1×" or for example "3× (36 × 21)"), after the Blend width, with an info button and a line in the result summary; it works with every image type and is disabled while a job runs. In the API it is the optional `resolution` form field (a whole number from 1 to 5; leave it out for 1; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The oversampling must be a whole number from 1 to 5."), and the response adds `resolution`. The code is in `backend/app/services/resolution.py`; the definition is in `specs/016-interpolated-resolution/data-model.md`.
- **Notes** (since feature 017) builds the picture from only the strongest notes: a whole number from **12 to 84**, default 84 (all drawn notes). The **energy** of a note is the sum of its smoothed values over all frames of the file, and the **n notes with the most energy** are chosen **once for the whole file**, so the same notes are used in every frame (a choice made in every frame would flip at the margin); only the 84 drawn notes can be chosen, and notes of equal energy are ranked by pitch, the lower one first. The chosen notes keep their order of pitch, and for each frame their n values are **spread over the 84 values of the original grid**: evenly spaced positions from the first to the last chosen note (`np.linspace`) are read from the n values with `np.interp`, so the first chosen note keeps its value at the first position, the last at the last, and every value is between its neighbors. The 84 values then take the place of the 84 note values in everything else: the Oversampling step, the Threshold, the colors and the three grid image types (tiles, blended and contour) work on them as before, and with 84 notes the spread is the identity, so nothing changes, byte for byte. Smoothing comes first, so the energy and the values are the smoothed ones. Things worth knowing: **a note that is not chosen has no effect on any picture**, even in a frame where it is the loudest; with fewer than 84 notes **a position in the picture no longer stands for one fixed note** (it is a stretched view of the chosen notes from the lowest pitch to the highest, each covering a larger part of the picture); the **colors' scale and the Threshold's reference are still the largest smoothed value of the whole file over all 88 notes**, so the same strength has the same color at every number of notes, and a picture without the loudest note can look dimmer; the notes with no energy still count among the n when a file has fewer than n sounding notes. **It is not always steadier**: fewer notes remove the flicker of faint notes, but each remaining note covers more of the picture, so a note that changes now changes a larger area. Measured through the API on a 20 second synthetic file at 10 frames per second (Tiles, `hot`, the average change of the colors' position on the scale between consecutive frames, 84 / 48 / 24 / 12 notes): sustained tones with strong noise 0.058 / 0.056 / 0.053 / 0.045 (steadier: about 23% less at 12 notes), sustained tones with little noise 0.043 / 0.054 / 0.050 / 0.042 (about the same), and notes that start and stop twice a second 0.038 / 0.052 / 0.060 / 0.068 (less steady: about 77% more at 12 notes). The choice and the spread cost a few hundredths of a second, so job times do not depend on the number of notes (a 60 second file: tiles 0.8 s at 1× and 2.3 s at 5×, blended about 1.0 s and 1.5 s, contour about 16 s at 5×, at 84, 48 or 12 notes alike). On the page it is the **Notes** slider (12 to 84 in steps of 1, starting at 84, with the readout "All 84 notes" or for example "36 of 84 notes"), after the Threshold, with an info button and a line in the result summary ("Notes: All 84" or "Notes: 36 of 84"); it works with every image type and is disabled while a job runs. In the API it is the optional `note_count` form field (a whole number from 12 to 84; leave it out for 84; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The number of notes must be a whole number from 12 to 84."), and the response adds `note_count`. The code is in `backend/app/services/note_selection.py`; the definition is in `specs/017-top-energy-notes/data-model.md`.
- **Interpolate** (since feature 018) draws fewer pictures and makes the frames in between by **blending** their neighbors with the **Pillow** image library. It is a whole number from **1 to 5**, default 1 (every frame drawn): only every n-th frame is **drawn** from the music, and the others are **interpolated**. With the frames numbered from 1 as in the request (the files are `frame_000000.png` and up), interpolate 5 draws frames 1, 6, 11, 16 and so on and always the **last frame** of the file, so every frame in between has a drawn frame on each side (when the number of frames does not fit, the last gap is shorter). The drawn frames are made exactly as at interpolate 1, so their files are **byte-identical** to those of an uninterpolated job; the smoothing, the notes, the resolution, the threshold and the colors are still worked out for every frame and only the drawing is skipped, so everything else behaves as before. The number of frames, the file names, the size (600 × 400) and the timing do not change, so the player plays an interpolated job at the same speed. A frame at position k of a gap of g frames (g is n, or less at the end) is `Image.blend(earlier, later, k / g)`, the weighted mix of the two drawn pictures: frame 2 of 5 is four fifths of frame 1 and one fifth of frame 6. Only blend is made. (The first version also offered `soft_light`, `hard_light`, `overlay`, `screen` and `subtract`, the Pillow `ImageChops` operations, applied between the earlier frame and the blend, with a dropdown and an `interpolate_function` field; they were removed because they did not work well: they take no weight, `screen` brightened and the others darkened the frames in between so that the animation pulsed back to the plain frame at every drawn frame, and `subtract` gave almost black frames. A request that still sends `interpolate_function` is accepted and the field is ignored, like the other removed fields.) An event that happens between two drawn frames (a note that starts and stops within a gap) is not drawn at all. In-between frames are 8-bit RGB PNGs (the drawn ones keep their kind: indexed-colour Tiles at the original grid, true-color for finer Tiles and Blended tiles, RGBA for the contour) and are made from the drawn frames' files on a few threads. **The speed gain is real for the contour only**: for a 60 second file (1,800 frames, resolution 5) the contour job takes 15.7 s at interpolate 1, 6.2 s at 3 (0.39 of the time) and 4.0 s at 5 (0.26); Tiles and Blended tiles cost about as little to draw as to blend, so there is nothing to save there: a Tiles job at the original grid takes 0.79 s at 1, 1.00 s at 3 (1.25 times) and 0.86 s at 5, Blended tiles 0.93, 1.08 and 0.98 s, and at resolution 5 (where Tiles frames are the larger true-color pictures) Tiles take 2.29, 1.68 and 1.43 s and Blended tiles 1.36, 1.65 and 1.38 s. Peak memory is the same as without interpolation (about 315 MB for that file, set by the analysis). On the page it is the **Interpolate** slider (1 to 5 in steps of 1, starting at 1, with the readout "1" or for example "(1/5 frames)"), after the Oversampling, with an info button and a line in the result summary ("Interpolate: 1" or "Interpolate: 5"); it is disabled while a job runs. In the API it is the optional `interpolate` form field (a whole number from 1 to 5; leave it out for 1; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The interpolate value must be a whole number from 1 to 5."), and the response adds `interpolate`. The code is in `backend/app/services/frame_interpolation.py`; the definition is in `specs/018-interpolated-frames/data-model.md`.
- **Beat coloring** (since feature 024) is the group **Local peaks** of the settings page, shown for **Tiles**, **Blended tiles** and (since feature 028) **Contour** only (after their own group): a checkbox **Beat coloring** (off by default), **Minimum distance** (100 to 2000 ms, default 100, step 50 on the page) and **Prominence** (0 to 100 percent, default 50, step 5): the two settings of the Local peaks measurement above. **Off, the color of a tile is 100% determined by the harmonic energy of its note, exactly as before, and the beat is not even measured.** On, the place of a tile on the colormap is **half its note strength** (the square root of its share of the file's largest value, as before) **plus half the frame's position in the local peak**, `rint((0.5 * sqrt(share) + 0.5 * position) * 255)`: the strongest tile has the middle color of the colormap at position 0 (the minimum of the local peak) and the right-most color at position 1 (its maximum). The position of a frame is read in the middle of the interval the frame covers, from the measurement of the whole file; every tile of a frame uses the same position. With no known beat (before the first peak, a file with no peaks, a silent file) the position is 0, so the picture only uses the lower half of the colormap; every visible tile takes part, a tile with no energy included (it has half the position); tiles hidden by the threshold are drawn as before (black for Tiles, the middle color for Blended tiles). The contour and the circles do not use it. Worth knowing: the measured energy runs in a **straight line from one peak to the next**, so the position follows **how strong the beats are** (it rises and falls from beat to beat, relative to the smallest and largest energy of the surroundings), not a dip inside each beat: between two equally strong beats it stays near 1. The request has three optional fields: `beat_coloring` (`true`, `false`, `1` or `0` in any case; default `false`; otherwise 400 "The beat coloring must be true or false."), `peak_distance` (milliseconds, default 100) and `peak_prominence` (percent, default 50), checked before the file is read whether the box is on or off, with the messages of the measurement ("The minimum distance must be a number from 100 to 2000 milliseconds." and "The prominence must be a number from 0 to 100 percent."); the response adds the three values. `write_frames` and `colorize` take the positions as `beat` (one number from 0 to 1 per frame, or `None` for the old colors).
- **Beat wave** (since feature 028) lets the local peak show in the **Contour** picture. With the **Beat coloring** checkbox on (it is the one of the Local peaks group, which Contour now has too; off by default, and then **the Contour frames are exactly what they were**, with no beat measured), every frame's grid of values `Z` (7 × 12 values, or 7r × 12r at Oversampling `r`) is multiplied by a **modifier** before the contour is drawn: `Z = Z × (1 − pattern × sin(π × k))`. The `pattern` is a set of concentric rings, `(sin(waves × 2π × sqrt(distance ÷ largest)) + 1) ÷ 2`, a number from 0 to 1 (the square root makes the rings close together near the center and wider towards the outside): `distance` is the distance in grid points from the **center** of the grid (the center of `n` points on an axis is at `(n − 1) ÷ 2`, so it is half way, 0.5, at an exact center), `largest` is the larger of the grid's columns and rows (12 at the original grid), and `waves` is the **Wave count**. `k` is the frame's **position in the local energy peak** (feature 024: 0 at its minimum, 1 at its maximum, 0 when no beat is known), passed through a sine from 0 to π so that the effect swells and fades smoothly. **At the minimum of the beat the modifier is 1 everywhere and the frame is the plain contour** (nothing is multiplied: the file is byte for byte the same); as the beat rises the rings, where the pattern is 1, are dimmed by the factor `1 − sin(π × k)` and are cut away completely half way up the beat (`k = 0.5`), and as the beat goes on to its maximum they fade out again (at `k = 1` the frame is the plain one to within rounding), while the places between the rings are never touched. The color scale is still the one of the frame **before** the wave (from 0 to the frame's largest value), so the dimmed rings are drawn darker; a frame that the wave leaves with nothing to draw is one flat color. The pattern is worked out once per job (`backend/app/services/beat_wave.py`) and the wave is applied in `contour.py` after the grid smoothing and before the levels are chosen. **Wave count** (the request field `wave_count`, a whole number from **2 to 10**, default **4**, a slider at the end of the Contour group, echoed in the response and shown in the result summary when the beat coloring is on) is checked for every image type before the file is read (`The wave count must be a whole number from 2 to 10.`) and has no effect except for Contour with the box on. The beat is measured for a Contour job exactly when `beat_coloring` is true, with the Local peaks settings (`peak_distance`, `peak_prominence`). Interpolate and Gaussian smoothing work on the frames with the wave.
- **Gaussian smoothing** blurs the finished pictures: a number from **0 to 5**, default **0**, in steps of one half on the page. At 0 nothing is done and the frames are exactly what they were (the original tile grid keeps its indexed-colour files). Above 0 every drawn frame is blurred with Pillow's `ImageFilter.GaussianBlur`, whose radius is the standard deviation of the Gaussian in pixels; because the frame is 3:2 the radius is **3:2 as well**, so that the smoothing looks the same in both directions: a setting of *v* blurs by **1.5 *v* pixels across and *v* pixels down** (a setting of 4 is a radius of 6 in x and 4 in y, a setting of 5 is 7.5 and 5; the radii are in pixels of the 600 × 400 frame, not of the 252-pixel reference frame of the circles). It rounds off the edges of tiles, contour bands and the soft edges of blended tiles. It applies to **Tiles, Blended tiles and Contour** (it is in the Image smoothing group, which the two circle types do not show; the server accepts it for them and ignores it). The blur is applied to the frames that are **drawn**, after they are written and before the in-between frames of Interpolate are made, so an in-between frame is a blend of blurred frames; a flat-colored tile frame, which is saved with a palette, has many more colors once blurred and is saved as a true-color picture (compress level 1). In the API it is the optional `gaussian` form field (a number from 0 to 5, default 0; an empty, non-numeric, non-finite or out-of-range value is refused with 400 and "The gaussian smoothing must be a number from 0 to 5.", for every image type, before the file is read), and the response adds `gaussian`. On the page it is the **Gaussian smoothing** slider, the third control of Image smoothing (alone on its row), with the readout "Off" or its number, an info button and a line in the result summary. Measured for a 60 second file (1,800 frames of 600 × 400) at 0, 2.5 and 5: tiles 1.0, 5.9 and 7.2 s (the room of the frames 5, 51 and 107 MB), blended tiles 8.3, 15.6 and 15.9 s (67, 80 and 134 MB), contour 35, 43 and 42 s (10, 145 and 191 MB); the cost is about 5 to 8 s of time, but the **files grow a lot** because a smooth gradient compresses badly. The code is in `backend/app/services/gaussian.py`.
- **Threshold** (since feature 011) hides faint notes. It is a slider from **Off** (0, the left end, exactly as before) to 10 (the right end) in steps of 1: the percentage of the **largest note value in the whole file** (after smoothing; the same value the colors are scaled against, including the four undrawn notes) below which a note is not shown. A drawn note whose smoothed value in a frame is *strictly below* that level gets a black tile (RGB 0, 0, 0, HSV 0, 0, 0) with the image type **Tiles**; with **Blended tiles** (since a later change that has no feature number) it is **not drawn at all**: its place keeps the background, the **middle color of the colormap** (the entry at row 128 of its 256-color table, as for Circles), and the tiles that are drawn fade into that background across their edges; Contour is as before; a note exactly at the level is shown, and the note with the largest value is never hidden. Because a note with no value at all is below any positive threshold, every unlit tile also turns black (Tiles) or is left as the background (Blended tiles) as soon as the threshold is above 0 (otherwise it would have the first color of the colormap). The one exception is a silent file: no note is below a share of the zero largest value, so nothing is hidden and every tile keeps the first color. The level is one fixed level for the whole file, not one per frame, and the comparison is made on the unrounded smoothed value before it is turned into a color, so the colormap never changes which notes are hidden. Only the hidden note's own tile changes: the tiles that are shown are exactly what they would be with the threshold off. A fading note (with smoothing) turns black (Tiles) or disappears into the background (Blended tiles) once its smoothed value falls below the level. In the API it is the optional `threshold` form field (a number from 0 to 10, leave it out for 0; an empty, non-numeric or out-of-range value is refused with a 400 saying "The threshold must be a number from 0 to 10."), and the response adds `threshold`. The page shows it as the Threshold slider with a readout ("Off", or for example "5%"), an info button and a summary line. The definition is in `specs/011-note-threshold/data-model.md`.
- A submission may create at most 60,000 windows (`MV_MAX_WINDOWS`); a spacing that would create more is refused before any analysis.
- Frontend tests: `cd frontend && npm test`.

## Video (silent MP4 from the frames)

Since feature 029, under the frame player there is a **Create video** button. It joins the frames of the render, in order, into one **silent H.264 MP4** with ffmpeg (no audio: the uploaded file is not used) at the render's frame rate, so the video lasts as long as the music. The file is saved as `backend/output/<job_id>/video.mp4` (one directory per render; creating it again replaces it; `backend/output/` is git-ignored), and the page shows where and gives a **Download** link.

- `POST /api/jobs/{job_id}/video` makes the video and answers `{job_id, file_name, path, size_bytes, frame_count, frame_rate, duration_seconds, url}`; `GET /api/jobs/{job_id}/video` downloads it. Errors are `{"detail": "..."}`: 404 when the frames are gone (render again), 409 when a video is already being made for the render, 503 when ffmpeg is not found, 504 on a timeout, 500 otherwise. A failure leaves no partial file.
- ffmpeg must be on the PATH, or set `MV_FFMPEG_PATH` to its full path (for example `C:fmpeginfmpeg.exe`). `MV_OUTPUT_DIR` moves the output directory and `MV_VIDEO_TIMEOUT_SECONDS` (default 600) limits a conversion.
- To add the music afterwards: `ffmpeg -i video.mp4 -i song.wav -c:v copy -shortest with-music.mp4`.
- Tests: `backend/tests/test_video.py` (the service, with a fake ffmpeg), `backend/tests/test_video_api.py` (the endpoints; the tests with the real ffmpeg are skipped when ffmpeg and ffprobe are not installed), `frontend/src/components/VideoExport.test.ts`.
