# Music Visualizer

- `backend/` — Python + FastAPI (file and image processing via Pillow)
- `frontend/` — TypeScript + Vue 3, bundled with Vite

## Backend

```
cd backend
python -m venv .venv
.venv\Scripts\activate        # Windows; use `source .venv/bin/activate` elsewhere
pip install -r requirements-dev.txt
uvicorn app.main:app --reload  # http://localhost:8000 (docs at /docs)
pytest
```

## Frontend

```
cd frontend
npm install
npm run dev                    # http://localhost:5173, proxies /api to :8000
npm run build
```

## Note analysis

`backend/app/services/note_analysis.py` reduces stereo audio to 88 musical-note values per window (55 Hz, one semitone apart). Left and right spectra are averaged, and each note reads the spectrum at `int((window_size / sample_rate) * freq)`.

```python
from app.services.note_analysis import NoteBinAnalyzer, analyze_wav

result = analyze_wav("audio/song.wav", sample_rate=44100, window_size=2048)
result.frames                 # shape (windows, 88), lowest note first
result.window_start_times()   # seconds

analyzer = NoteBinAnalyzer(44100, 2048)
values = analyzer.analyze(left_buffer, right_buffer)   # shape (88,)
```

Notes: neighbouring low notes share a spectrum position at small window sizes (about 28 of 88 at 2048 samples and 44.1 kHz), so use a larger window if you need them separated. The sample rate must be at least about 16.75 kHz. Put sample files in `backend/audio/` (git-ignored).

## Audio frames UI

**Layout** (since feature 008): the page has two columns. The left column holds the audio file chooser at the top, then the progress and error messages and the result: the frame preview with its playback controls (play/pause, loop, position slider), followed by the result summary. The right column holds the settings and the *Create frames* button, so new settings can be added there without moving the preview. Window size, frame rate and window spacing share one row. Each setting's explanation sits behind a small info (*i*) button that opens a popover (Escape or a click elsewhere closes it); validation errors and the below-minimum spacing notice stay visible under their field. Below 960 px wide the columns stack, with the chooser and preview first and the settings after. The components are `FilePicker.vue`, `SettingsForm.vue` and `InfoPopover.vue` in `frontend/src/components/`, and the text of the explanations is in `frontend/src/utilities/help.ts`.

Open the frontend, choose a `.wav`, pick the window size from the dropdown (a power of 2: 4096, 8192, 16384 or 32768; default 4096), set the frame rate (1–60, default 30), and press *Create frames*. The server reads the sample rate from the file, runs the note analysis, averages the windows within each frame period, and writes one color PNG per frame. By default (the `tiles` image type, see **Image type** below) it is an indexed-colour file that decodes to exact RGB values: a 12 × 7 grid of 21 × 24 pixel tiles (252 × 168, exactly 3:2) with one row per octave and one column per note name, so the tile directly below a note is the same note an octave higher (double the frequency). The lowest note (55 Hz) is the top-left tile, and only the first 84 notes are drawn (up to about 6645 Hz); the four highest of the 88 analyzed notes are left out of the picture but still count when the colors are scaled to the loudest value in the file. Each tile's color is the color of the chosen colormap at the strength of its own note (see **Colormap** below). The page then plays the frames as an animation (play/pause, loop, position slider).

- `POST /api/jobs` (multipart: `file`, `window_size`, `frame_rate`) creates the frames. `GET /api/jobs/{job_id}/frames/{index}` returns one PNG. Errors are `{"detail": "..."}`.
- Uploaded audio goes to `<system temp>/music-visualizer/audio/<job_id>/audio.wav` and frames to `<system temp>/music-visualizer/frames/<job_id>/`. Override with `MV_AUDIO_TEMP_DIR` and `MV_FRAMES_TEMP_DIR`. Old submissions are not cleaned up automatically.
- Limits are settings in `backend/app/config.py` and can be overridden with `MV_` environment variables: 200 MB upload (`MV_MAX_AUDIO_BYTES`) and 30,000 frames (`MV_MAX_FRAMES`).
- **Window spacing** sets how far apart windows start, as a multiple of the window size: with a window of 8192 and a spacing of 0.25, windows start at samples 0, 2048, 4096 and so on. Below 1 the windows overlap; 1 is consecutive windows; above 1 there are gaps. The field defaults to one frame period in samples divided by the window size (rounded down to 6 decimals), so each frame gets its own window. It is recalculated whenever the window size, frame rate or file changes (replacing anything typed), using the chosen file's sample rate read from its header, or 44.1 kHz before a file is chosen. A spacing that would give a step under one sample is raised to exactly one sample and the page says so. In the API it is the optional `window_spacing` field (omitted means the default), and the response adds `window_spacing`, `step_samples`, `window_count` and `spacing_raised`.
- **Colormap** (since feature 014) chooses how each tile is colored. It replaces the earlier color rules (a hue moved by related notes, a saturation and a per-frame brightness from the loudness of the sound, and the Brightness, Saturation, Hue steps, Saturation steps and Brightness steps settings), which made the animation "blinky" and have been removed. The choices are four of matplotlib's named colormaps: `summer` (green to yellow), `autumn` (red to yellow), `hot` (the default: dark red through red and yellow to white) and `cool` (cyan to magenta), with exactly matplotlib's 8-bit colors (the 256-entry table of each, read from `matplotlib.colormaps`; matplotlib is now a requirement). A tile's color is the table entry at the position `sqrt(value / peak)`, rounded to one of 256 steps, where `value` is that note's smoothed value in the frame and `peak` the largest smoothed value anywhere in the file (all 88 notes count, as before): a note with no strength has the first color of the scale, the strongest note of the file the last, and a stronger note never has an earlier color. A tile's color therefore depends only on its own note's strength and the file's peak: not on any other note, not on the loudness of the frame, and not on the frame number, so a steady note keeps one color and the picture is no longer dimmed or brightened as a whole. A silent file has every tile in the first color of the scale (a very dark red for `hot`). Hidden tiles (see Threshold) are black; `hot` starts at a very dark red (10, 0, 0), so with `hot` a quiet tile and a hidden one look much alike, which the other three colormaps avoid. On the page it is the **Colormap** dropdown (Summer, Autumn, Hot, Cool, starting at Hot) with an info button and a line in the result summary. In the API it is the optional `colormap` form field (exactly `summer`, `autumn`, `hot` or `cool`, lowercase; leave it out for `hot`; anything else, including an empty value, `viridis` or `hot_r`, is refused with a 400 saying "The colormap must be one of summer, autumn, hot, cool."), and the response adds `colormap`. A request that still sends the removed fields (`energy`, `brightness`, `hue_step`, `saturation_step`, `brightness_step`) is accepted and they are ignored; the response no longer reports them. The definition is in `specs/014-colormap-colors/data-model.md`.
- **Smoothing** is a slider from 0.00 to 0.80 (steps of 0.01, default 0). Since feature 012 it works together with the **Smoothing window** below: each frame is mixed with the frames before it. With `s` the smoothing and `w` the window, frame `t` becomes `( A[t] + s*A[t-1] + s*A[t-2] + ... + s*A[t-k] ) / ( 1 + s*k )`, where `A` are the *unsmoothed* values and `k = min(t, w)` is the number of earlier frames that exist. The current frame has weight 1 and each earlier frame in the window has the same weight `s`; the weights are divided by their sum, so a value that is the same in all of these frames stays that value, and the first frame (which has no earlier frames) is left as it is. Smoothing 0 is no smoothing, whatever the window is. Only the frame itself and earlier frames are used, and the earlier frames are the raw values, not earlier smoothed results, so the memory is finite: a note that stops is exactly gone `w` frames after its last frame (it does not keep an endless faint trace as the running average of features 006 to 011 did), and a note that starts reaches its full value after `w` frames. For example, with `w = 2` and `s = 0.5` the values 8, 4, 2 become 8, 5.33 and 4; with `w = 3` and `s = 0.5` a note that sounds in one frame is 0.4 of its value in that frame, 0.2 in each of the next three frames and exactly 0 after that. It is applied to the note values before they are turned into colors (each note from its own history only), so the colors are scaled against the loudest smoothed value and the Threshold works on the smoothed values. It works per frame, so the same settings span less real time at a higher frame rate. Frames made with a Smoothing above 0 look different from those made before feature 012, because the meaning of the setting changed. Changing it means submitting again. In the API it is the optional `smoothing` field (leave it out for 0; an empty value or one outside 0.0 to 0.8 is refused with a 400), and the response adds `smoothing`. The definition is in `specs/012-smoothing-window/data-model.md`.
- **Smoothing window** (since feature 012) is how many earlier frames are mixed into each frame: a whole number from **1 to 20**, default 1. With 1 each frame is blended with the one before it, with 20 with the twenty before it; it has no effect while Smoothing is 0. On the page it is the **Smoothing window (frames)** number field directly above the Smoothing slider, with an info button and a line in the result summary; a value that is not a whole number from 1 to 20 shows an error under the field and nothing is sent. In the API it is the optional `smoothing_window` form field (leave it out for 1; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The smoothing window must be a whole number from 1 to 20."), and the response adds `smoothing_window`.
- **Image type** (since feature 013) chooses which kind of picture is made from a frame's note values. The choices are **Tiles** (`tiles`, the default: the picture described above, flat tiles with hard edges, written as an indexed-colour PNG), **Blended tiles** (`blended`), since feature 015 **Contour** (`contour`, described in the next paragraph) and, since feature 019, **Circles** (`circles`, no grid at all, described after Contour). Everything that decides the 84 tile colors (analysis, smoothing and window, the colormap and the threshold) works the same for both. A blended frame has the same size (252 × 168), the same 12 × 7 grid of 21 × 24 pixel tiles, the same frame count and timing, but the colors of neighbouring tiles fade into each other: across every edge that two drawn tiles share there is a Gaussian feather (a Gaussian blur of the edge confined to a band that reaches the **blend width** on each side of the edge, with a standard deviation of a quarter of the reach, so the edge itself stays fairly sharp and only the tails are soft; at the default width the feather is about 10 pixels across) with an even 50/50 mix at the edge itself. A pixel is the mix of up to four tiles, weighted by the product of its horizontal and vertical weights (a corner where four tiles meet is 25% each); pixels outside every band have exactly their tile's color, so the middle of each tile stays flat. The blend works on the finished colors and on where the tiles are in the picture, not on which notes they stand for: tiles are neighbours only if they touch in the grid (the end of one row and the start of the next do not blend), the picture's outer border is not blended (it does not fade to black), and a black tile (unlit or hidden by the threshold) fades with its colored neighbour like any other pair. The colormap and the threshold decide the tile colors before the blend, so the in-between colors at the edges are blends of colormap colors (and black). Blended frames are true-color PNGs (many more than 84 colors), so their files are larger (about 15 to 25 KB against about 1 KB) and they take longer to create (about 1.4 ms per frame against 0.3 ms on the development machine). On the page it is the **Image type** dropdown (Tiles, Blended tiles, Contour or Circles, starting at Tiles) with an info button and a line in the result summary. In the API it is the optional `image_type` form field (exactly `tiles`, `blended` or `contour`, lowercase; leave it out for `tiles`; anything else, including an empty value, is refused with a 400 saying "The image type must be one of tiles, blended, contour, circles."), and the response adds `image_type`. The definition is in `specs/013-image-type-blended-tiles/data-model.md`.
- **Contour** (since feature 015) is the third image type: instead of tiles, the 12 × 7 grid of smoothed note values is drawn as a **filled contour map**, bands of color that flow from one note to the next like the elevation map of a landscape in which every note is a point on the grid and its strength is the height. It is drawn by matplotlib: `contourf` on the coordinates `np.linspace(0, top, 12)` by `np.linspace(0, top, 7)` (`top` is the largest value of the frame being drawn, worked out again for every frame; with the axes off this changes no pixel, the colors come from the scale below), with the selected colormap, the axis decorations off (`set_axis_off`), saved with `pyplot.savefig` from a figure that is exactly 252 × 168 pixels, so the contour fills the whole picture with no axes, border or margin. The picture has the same orientation as the tiles (lowest octave at the top, lowest note name at the left), the same frame count and timing, and is an opaque RGBA PNG (about 1 to 2 KB). Things worth knowing: **the contour levels are chosen by matplotlib** for each frame (nothing about their number or positions is fixed in this program), and **the color scale runs from 0 to the largest value of the frame being drawn** (so the loudest note of every frame is at the end of the colormap, and a given strength can have a different color in different frames; until 2026-10-12 it ran to `max`, the largest smoothed note value anywhere in the file, the four undrawn notes included, for the whole file); **the scale is linear** in the strength, unlike the tiles, which take the square root of the share of the peak, so a quiet note is closer to the start of the colormap in a contour than in the tiles; Smoothing, its window, the Threshold and the Colormap apply as for the other types (a note hidden by the Threshold counts as 0, so it does not raise the contour); a frame in which every value is the same (a silent file, a quiet moment, every note hidden) is one flat picture of the colormap's color for that value (the first color for 0), because matplotlib has no contour to draw there; the **Blend width does not apply** (a value sent with `image_type=contour` is accepted and ignored). A contour job takes longer than a tiles job: about 14 ms per frame on the development machine (a 60 second file, 1,800 frames, in about 25 s; 300 frames in about 4 s) while a whole tiles job of the same 60 second file, analysis included, takes about 1 s and a blended one about 1.3 s. matplotlib's `pyplot` is imported only when a contour is drawn (windowless Agg backend) and holds global state, so contour drawing runs one job at a time. The code is in `backend/app/services/contour.py`; the definition is in `specs/015-contour-image-type/data-model.md`.
- **Circles** (since feature 019) is the fourth image type, `circles`: no grid at all, but circles that **wander as the music plays**. In every frame the **strongest notes of that frame** (5 to 12 of them: the *circles per frame* setting; by smoothed value, ties to the lower note) are sorted from the strongest down, and each puts down one circle; a note with no energy puts nothing down. The circle of rank r is placed relative to the **circle that rank r had in the previous frame** ("the last note at that index"), moved by an **angle** and a **distance** that come from the note: the angle is the note's name counted from C (C = 0, C# = 1 ... B = 11) times **30 degrees**, mirrored (360 minus the angle) for octaves below 4, with 0 degrees pointing right and angles growing counter-clockwise on the screen; the distance is **1 + |octave - 4|** units (octave 4 is 1 unit, every octave above or below it adds one; the notes run from octave 1, 4 units, to octave 8, 5 units), a unit being the *unit* setting in pixels. So an F5 (150 degrees, 2 units), an F3 (210 degrees, 2 units) and an A4 (270 degrees, 1 unit) move the way those numbers say. The angle and the octave are those of the **real note**, not of the application's grid (whose first column is A, 55 Hz, so F5 is in grid column 8): the note index `i` is MIDI note `33 + i`, its name `midi % 12` and its octave `midi // 12 - 1`. A rank whose note is the **same note at the same volume** as the last note of that rank does **not move**: its new circle is put on the same place as the last one (it is still added to the memory, so the older circle under it is covered by the newer, opaque one). "The same note" is the same note index (so the same name and octave); "the same volume" is the same color index, the volume as the picture shows it, 0 to 255 on the tiles' square-root scale, so two values that round to one color count as the same and exact equality of the floating-point values is not needed. The last note of a rank is kept across frames in which the rank has no note, and the first circle of a rank has no note before it, so it moves. Every rank starts from the **middle of the picture**, a rank that gets no note keeps its place, and the places **wrap around** the 252 × 168 picture's edges (a circle near an edge is cut off by it, not drawn again on the other side). A circle's color is the colormap's at the note's strength on the same scale as the tiles (the square root of the share of the file's loudest smoothed value), so the same strength has the same color in every frame. The picture **remembers** the last *memory* circles (100 to 500) in a circular buffer and draws all of them in every frame, as **smooth, anti-aliased** discs (each picture is drawn at 4 times its size and averaged down, so an edge pixel is a mix of the circle and what is under it and a circle can sit between pixels; the factor is `SUPERSAMPLE` in `circles.py`) on a background of the colormap's **middle color** (the entry halfway along its 256-color table, row 128, so it changes with the colormap), oldest first and newest on top, each with an **opacity that falls with its age**: the newest circle is fully opaque and a circle `age` places back in a memory of m circles (0 for the newest) has the opacity (m - age) / m, so the oldest, just before it is dropped, has only 255 / m of full opacity (1 to 3 parts in 255 for the memory sizes allowed) and is barely visible (the fade is a straight line, a circle halfway back is half opaque, and where circles overlap their colors blend); within a frame the weakest is added first, so the strongest is on top and the last to be dropped. The four settings only for circles are the **unit** (1 to 10 pixels, default 4: the length of one step; since the size became a setting of its own the unit no longer sets how big a circle is), the **size** (the circle's **circumference** in pixels, a whole number from 25 to 50, default 25, which is a radius of size / (2 pi): 4.0 to 8.0 pixels, the default about what the first version drew at unit 4), the **memory** (100 to 500 circles, default 300) and the **circles per frame** (5 to 12, default 8); in the API `circle_unit`, `circle_size`, `circle_memory` and `circle_notes`, refused with 400 and "The circle unit must be a whole number from 1 to 10.", "The circle size must be a whole number from 25 to 50.", "The circle memory must be a whole number from 100 to 500." or "The number of circle notes must be a whole number from 5 to 12." (they are validated for every image type and only have an effect for circles), and all four are in every response. Smoothing and its window and the Colormap apply. **Interpolate, Resolution, Notes (the 12 to 84 choice), Threshold and Blend width have no meaning for circles**: a frame depends on the frames before it, so none can be skipped, and the others describe a grid of tiles; the server accepts them and ignores them, and the page disables them while Circles is chosen. On the page, Circles is the fourth choice of the Image type dropdown; choosing it shows the four sliders (Unit with the readout "4 px", Size "25 px around", Memory "300 circles", Circles per frame "8 notes"), each with an info button, and the result summary shows the four values and hides the lines that do not apply. A steady note draws a straight line of circles (and wraps around), a melody wanders in a cluster, and the largest settings (unit 10, size 50, memory 500, 12 circles) fill the picture with overlapping, fading discs. The work is cheap: a 60 second file (1,800 frames) takes 2.40 s at the smallest settings (a tiles job takes 0.76 s), 3.59 s at the defaults and 9.51 s at the largest, size 50 included (about 1.3 to 5.3 ms a frame, the analysis included; the smooth edges and the fading discs made it slower than the 0.74 to 1.65 s of the first version's hard, solid discs; at 8 times the size the largest took 31 s for hardly any gain). The code is in `backend/app/services/circles.py`; the definition is in `specs/019-generative-circles/data-model.md`.
- **Blend width** (since feature 013) is how far the fade of the blended tiles reaches on each side of an edge, as a percentage of the tile width (21 pixels): a number from **10 to 25**, default 25, so the reach is `percent × 21 / 100` pixels, from 2.1 at 10 to 5.25 at 25, the same distance in pixels for edges between tiles side by side and for edges between a tile and the one below it. Outside the reach the tile keeps its exact color, and the fades from opposite edges of a tile never meet (at most half of its width is faded), so a flat middle always remains. Only Blended tiles uses it: the Tiles and Contour pictures are the same for every blend width. On the page it is the **Blend width** slider (10 to 25 in steps of 1, starting at 25, with the readout "25% of a tile"), enabled only while Blended tiles is chosen (disabled for Tiles and for Contour, and while a job runs), and the summary shows it for Blended tiles. In the API it is the optional `blend_width` form field (a number from 10 to 25, decimals allowed; leave it out for 25; an empty, non-numeric or out-of-range value is refused with a 400 saying "The blend width must be a number from 10 to 25."; it is accepted and ignored with `image_type=tiles` or `image_type=contour`), and the response always adds `blend_width`.
- **Resolution** (since feature 016) makes the picture finer without changing the music: a whole number from **1 to 5**, default 1. Every frame is drawn from a grid with one value per drawn note (12 columns by 7 rows); resolution *r* draws it from a grid of **12 r by 7 r** values instead (12 × 7, 24 × 14, 36 × 21, 48 × 28 or 60 × 35), made from the original one by linear interpolation: evenly spaced positions from the first to the last column and row (`np.linspace`) are read from the smoothed note values with `np.interp`, along every row and then along every column. The four corners keep their original values, every new value lies between the original values around it (never louder than the loudest note or quieter than the quietest one) and the end of one row never mixes with the start of the next. The interpolation comes **after** the smoothing, and the **Threshold and the colors work on the new values** (a tile is hidden when its own interpolated value is below the threshold's share of the file's loudest note; the colors' scale and that reference are the file's largest original smoothed value at every resolution, so at a higher resolution the strongest tile can be a step short of the colormap's last color when the loudest note falls between two sample positions, only the four corners are exact). The picture keeps its size, **252 × 168 pixels**, so a higher resolution means smaller tiles: 21 × 24 pixels at 1×, 10 or 11 × 12 at 2×, 7 × 8 at 3×, 5 or 6 × 6 at 4× and 4 or 5 × 4 or 5 at 5×, with every tile edge at the nearest whole pixel (neighbors differ by at most one pixel). **Tiles** are then up to 2,100 flat tiles; a Tiles frame has more colors than an indexed-colour PNG can hold above 1×, so frames at 2× and above are true-color PNGs (about 1.4 KB at 3× and 2.3 KB at 5×, against 0.9 KB at 1×) and a Tiles job takes about 2 to 3 times as long (a 60 second file: 0.8 s at 1×, 1.9 s at 3×, 2.3 s at 5×). **Blended tiles** keep the blend width as a share of the (now smaller) tile, so the fade shrinks with the tiles: at 5× a width of 25% is about one pixel at each edge (the reach is a quarter of the mean tile width, 4.2 pixels), and below about 24% at 5× (or 12% at 4×) it is narrower than the pixels' centers and changes nothing, so Blended looks like Tiles there; the middle of every tile stays flat. **Contour** is drawn from the finer grid (finer steps, a smoother outline) at the same cost per frame (about 8 to 15 ms). At resolution 1 everything is exactly as without the setting, byte for byte. On the page it is the **Resolution** slider (1 to 5 in steps of 1, starting at 1, with the readout "1×" or for example "3× (36 × 21)"), after the Blend width, with an info button and a line in the result summary; it works with every image type and is disabled while a job runs. In the API it is the optional `resolution` form field (a whole number from 1 to 5; leave it out for 1; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The resolution must be a whole number from 1 to 5."), and the response adds `resolution`. The code is in `backend/app/services/resolution.py`; the definition is in `specs/016-interpolated-resolution/data-model.md`.
- **Notes** (since feature 017) builds the picture from only the strongest notes: a whole number from **12 to 84**, default 84 (all drawn notes). The **energy** of a note is the sum of its smoothed values over all frames of the file, and the **n notes with the most energy** are chosen **once for the whole file**, so the same notes are used in every frame (a choice made in every frame would flip at the margin); only the 84 drawn notes can be chosen, and notes of equal energy are ranked by pitch, the lower one first. The chosen notes keep their order of pitch, and for each frame their n values are **spread over the 84 values of the original grid**: evenly spaced positions from the first to the last chosen note (`np.linspace`) are read from the n values with `np.interp`, so the first chosen note keeps its value at the first position, the last at the last, and every value is between its neighbors. The 84 values then take the place of the 84 note values in everything else: the Resolution step, the Threshold, the colors and the three grid image types (tiles, blended and contour) work on them as before, and with 84 notes the spread is the identity, so nothing changes, byte for byte. Smoothing comes first, so the energy and the values are the smoothed ones. Things worth knowing: **a note that is not chosen has no effect on any picture**, even in a frame where it is the loudest; with fewer than 84 notes **a position in the picture no longer stands for one fixed note** (it is a stretched view of the chosen notes from the lowest pitch to the highest, each covering a larger part of the picture); the **colors' scale and the Threshold's reference are still the largest smoothed value of the whole file over all 88 notes**, so the same strength has the same color at every number of notes, and a picture without the loudest note can look dimmer; the notes with no energy still count among the n when a file has fewer than n sounding notes. **It is not always steadier**: fewer notes remove the flicker of faint notes, but each remaining note covers more of the picture, so a note that changes now changes a larger area. Measured through the API on a 20 second synthetic file at 10 frames per second (Tiles, `hot`, the average change of the colors' position on the scale between consecutive frames, 84 / 48 / 24 / 12 notes): sustained tones with strong noise 0.058 / 0.056 / 0.053 / 0.045 (steadier: about 23% less at 12 notes), sustained tones with little noise 0.043 / 0.054 / 0.050 / 0.042 (about the same), and notes that start and stop twice a second 0.038 / 0.052 / 0.060 / 0.068 (less steady: about 77% more at 12 notes). The choice and the spread cost a few hundredths of a second, so job times do not depend on the number of notes (a 60 second file: tiles 0.8 s at 1× and 2.3 s at 5×, blended about 1.0 s and 1.5 s, contour about 16 s at 5×, at 84, 48 or 12 notes alike). On the page it is the **Notes** slider (12 to 84 in steps of 1, starting at 84, with the readout "All 84 notes" or for example "36 of 84 notes"), after the Threshold, with an info button and a line in the result summary ("Notes: All 84" or "Notes: 36 of 84"); it works with every image type and is disabled while a job runs. In the API it is the optional `note_count` form field (a whole number from 12 to 84; leave it out for 84; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The number of notes must be a whole number from 12 to 84."), and the response adds `note_count`. The code is in `backend/app/services/note_selection.py`; the definition is in `specs/017-top-energy-notes/data-model.md`.
- **Interpolate** (since feature 018) draws fewer pictures and makes the frames in between by **blending** their neighbors with the **Pillow** image library. It is a whole number from **1 to 5**, default 1 (every frame drawn): only every n-th frame is **drawn** from the music, and the others are **interpolated**. With the frames numbered from 1 as in the request (the files are `frame_000000.png` and up), interpolate 5 draws frames 1, 6, 11, 16 and so on and always the **last frame** of the file, so every frame in between has a drawn frame on each side (when the number of frames does not fit, the last gap is shorter). The drawn frames are made exactly as at interpolate 1, so their files are **byte-identical** to those of an uninterpolated job; the smoothing, the notes, the resolution, the threshold and the colors are still worked out for every frame and only the drawing is skipped, so everything else behaves as before. The number of frames, the file names, the size (252 × 168) and the timing do not change, so the player plays an interpolated job at the same speed. A frame at position k of a gap of g frames (g is n, or less at the end) is `Image.blend(earlier, later, k / g)`, the weighted mix of the two drawn pictures: frame 2 of 5 is four fifths of frame 1 and one fifth of frame 6. Only blend is made. (The first version also offered `soft_light`, `hard_light`, `overlay`, `screen` and `subtract`, the Pillow `ImageChops` operations, applied between the earlier frame and the blend, with a dropdown and an `interpolate_function` field; they were removed because they did not work well: they take no weight, `screen` brightened and the others darkened the frames in between so that the animation pulsed back to the plain frame at every drawn frame, and `subtract` gave almost black frames. A request that still sends `interpolate_function` is accepted and the field is ignored, like the other removed fields.) An event that happens between two drawn frames (a note that starts and stops within a gap) is not drawn at all. In-between frames are 8-bit RGB PNGs (the drawn ones keep their kind: indexed-colour Tiles at the original grid, true-color for finer Tiles and Blended tiles, RGBA for the contour) and are made from the drawn frames' files on a few threads. **The speed gain is real for the contour only**: for a 60 second file (1,800 frames, resolution 5) the contour job takes 15.7 s at interpolate 1, 6.2 s at 3 (0.39 of the time) and 4.0 s at 5 (0.26); Tiles and Blended tiles cost about as little to draw as to blend, so there is nothing to save there: a Tiles job at the original grid takes 0.79 s at 1, 1.00 s at 3 (1.25 times) and 0.86 s at 5, Blended tiles 0.93, 1.08 and 0.98 s, and at resolution 5 (where Tiles frames are the larger true-color pictures) Tiles take 2.29, 1.68 and 1.43 s and Blended tiles 1.36, 1.65 and 1.38 s. Peak memory is the same as without interpolation (about 315 MB for that file, set by the analysis). On the page it is the **Interpolate** slider (1 to 5 in steps of 1, starting at 1, with the readout "1 (every frame drawn)" or for example "5 (one frame in 5 drawn)"), after the Resolution, with an info button and a line in the result summary ("Interpolate: 1" or "Interpolate: 5"); it is disabled while a job runs. In the API it is the optional `interpolate` form field (a whole number from 1 to 5; leave it out for 1; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The interpolate value must be a whole number from 1 to 5."), and the response adds `interpolate`. The code is in `backend/app/services/frame_interpolation.py`; the definition is in `specs/018-interpolated-frames/data-model.md`.
- **Threshold** (since feature 011) hides faint notes. It is a slider from **Off** (0, the left end, exactly as before) to 10 (the right end) in steps of 1: the percentage of the **largest note value in the whole file** (after smoothing; the same value the colors are scaled against, including the four undrawn notes) below which a note is not shown. A drawn note whose smoothed value in a frame is *strictly below* that level gets a black tile (RGB 0, 0, 0, HSV 0, 0, 0); a note exactly at the level is shown, and the note with the largest value is never hidden. Because a note with no value at all is below any positive threshold, every unlit tile also turns black as soon as the threshold is above 0 (otherwise it would have the first color of the colormap). The one exception is a silent file: no note is below a share of the zero largest value, so nothing is hidden and every tile keeps the first color. The level is one fixed level for the whole file, not one per frame, and the comparison is made on the unrounded smoothed value before it is turned into a color, so the colormap never changes which notes are hidden. Only the hidden note's own tile changes: the tiles that are shown are exactly what they would be with the threshold off. A fading note (with smoothing) turns black once its smoothed value falls below the level. In the API it is the optional `threshold` form field (a number from 0 to 10, leave it out for 0; an empty, non-numeric or out-of-range value is refused with a 400 saying "The threshold must be a number from 0 to 10."), and the response adds `threshold`. The page shows it as the Threshold slider with a readout ("Off", or for example "5% of the loudest note"), an info button and a summary line. The definition is in `specs/011-note-threshold/data-model.md`.
