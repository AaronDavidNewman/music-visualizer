### Reading the backend code (documentation standard, spec 041)

The backend is meant to be read without rereading every function. Three rules (the project constitution, `.specify/memory/constitution.md`; their forms are in `specs/041-code-readability-docs/contracts/documentation-standard.md`):

- **Every function is typed** (every parameter and the return value, nested functions included). An array is annotated with a **named alias of its kind** from `backend/app/services/array_types.py` (`NoteStrengths`, `BeatPositions`, `CirclePoints`, `Pictures`, ...): search the name there to find what the numbers are, the shape with the meaning of each axis and which function makes them.
- **Every array is documented**: a function that takes or returns one says, in its docstring (`Arrays:` and `Returns:`), its alias, its concrete shape (for example `(frames, 88)`) and what it represents; classes with array fields have an `Attributes:` block.
- **Every processing module starts with its `Order of operations:`** (the steps in the order the data is transformed, the function that does each, and the data after it), or says `No data processing:`. `backend/app/services/image_types.py` has the **pipeline overview** of the eight image types, from the uploaded file to the saved frames, with the steps they share (READ, ANALYZE, FLOOR, MEASURE, AVERAGE, SMOOTH, DRAW, SAVE).

Two tests keep them from being forgotten: `backend/tests/test_type_hints.py` (no function without a complete type, no exceptions) and `backend/tests/test_documentation.py` (the documentation is there; a new module must be put in one of its two lists). Whether it is *true* is for review, with the tools of `specs/041-code-readability-docs/tools/`: `shape_probe.py` (the shapes a job really passes), `trace_pipeline.py` (the order in which a job first calls the functions of each image type) and `verify_frames.py` (the hash of every frame against a baseline: it proves that a change of types or documents moved no picture). When a function, an array or the steps of a module change, the documentation changes in the same piece of work.

## Note analysis

`backend/app/services/note_analysis.py` reduces stereo audio to 88 musical-note values per window (55 Hz, one semitone apart). Left and right spectra are averaged, and each note reads the spectrum at `int((window_size / sample_rate) * freq)`.

```python
from app.services.note_analysis import NoteBinAnalyzer, analyze_wav

result = analyze_wav("audio/song.wav", sample_rate=44100, window_size=2048)
result.frames                 # shape (windows, 88), lowest note first
result.window_start_times()   # seconds

analyzer = NoteBinAnalyzer(44100, 2048)
values = analyzer.analyze(left_buffer, right_buffer)   # shape (88,)
```

Notes: neighbouring low notes share a spectrum position at small window sizes (about 28 of 88 at 2048 samples and 44.1 kHz), so use a larger window if you need them separated. The sample rate must be at least about 16.75 kHz. Put sample files in `backend/audio/` (git-ignored).

## Local peaks

`backend/app/services/local_peaks.py` is a second measurement, next to the note analysis: it follows the **overall** loudness of a file (not only its notes) and finds the periodic local maxima in it, the beats and pulses that come round again and again. It is a backend library; the job endpoint uses it for the beat of Decay, Decay Exp, Polar Chords, Chromatic Decay, Chromatic Wireframe and Contour's beat wave, and for Rhythm Circles, which also makes a **current tempo** of its peaks (the local tempo finder, below).

- **Impulse energy**: the file is cut into windows of 32 samples; the energy of a window is the average of the left channel's standard deviation and the right channel's (each on its own; a mono file has two equal channels). Integer samples are scaled to about -1 to 1, so the bit depth does not matter.
- **Peaks window**: a running window of 4096 impulse energies (about 3 seconds at 44.1 kHz; the size is the `window` argument and its exact value is not important) that moves through the file by half its length. `scipy.signal.find_peaks` is called on every window with `distance` (the minimum distance converted to impulse samples, `round(ms / 1000 * rate / 32)`, at least 1) and `prominence` (the prominence percentage of the window's largest energy). Each window owns its central half (the first window also the start of the file, the last its end), so a peak is judged once, with at least a quarter window of context on each side, and is neither lost nor reported twice; a last pass keeps the minimum distance across the borders between windows (the stronger of two close peaks stays).
- **Settings**: `min_distance` in milliseconds, 100 to 2000, default **350** (it was 100 until the local tempo finder, spec 040); `prominence` in percent, 0 to 100, default **20** (it was 50; the job no longer lets the user set it: every measurement of a job uses 20, and the page and the request have no Prominence; a bump must stand out by at least that share of the loudest impulse energy in its window; at 100 only a peak standing on exact silence qualifies). Anything else is refused with `The minimum distance must be a number from 100 to 2000 milliseconds.` or `The prominence must be a number from 0 to 100 percent.` before anything is measured.
- **What a peak records** (`LocalPeak`): `sample` (the first sample of the impulse window where the maximum is, so exact to 32 samples), `energy`, `window_min` and `window_max` (the smallest and largest impulse energy of the peaks window it was found in) and `rate` (peaks per minute, `60 * file rate / samples since the previous peak`; the first peak has no predecessor and gets the default of 60).
- **Asking the result** (`LocalPeaks`): `energy_at(sample)` is the straight line between the previous and the next peak's energy, 0 before the first peak and, after the last peak, a straight line from the last peak's energy down to 0 at the end of the file (the last beat is taken to last for whatever is left of the file, so the file ends on a down part of the beat; 0 past the end, and 0 for a file without peaks); `rate_at(sample)` is the rate of the last peak at or before the point, not interpolated, and 60 before the first peak. `energy_at_time(seconds)` and `rate_at_time(seconds)` take seconds. Each accepts a single point (and returns a `float`) or a list or array of them (and returns an array), so the values for every frame of a file are one call. A NaN or infinite point is refused. `position_at(sample)`, `position_at_time(seconds)` and `frame_positions(frame_rate, frames)` give the **place in the local energy peak** from 0 to 1: the interpolated energy between the interpolated smallest and largest energy of the neighbouring peaks' windows (the same straight line from the previous peak to the next), held within 0 and 1; 0 before the first peak, for a file without peaks and where the two leave no range; after the last peak the smallest and largest energy are those of the last peak's window and the energy falls to 0 at the end of the file, so the position falls to 0 and the file ends on a down part of the beat. `frame_positions` reads the middle of each frame.

```python
from app.services.local_peaks import measure_wav

peaks = measure_wav("audio/song.wav", min_distance=350, prominence=20)
peaks.peaks                    # LocalPeak(sample, energy, window_min, window_max, rate), in order
peaks.energy_at_time(12.5)     # interpolated energy 12.5 s into the file
peaks.rate_at_time(12.5)       # peaks per minute at that point
```

Tests: `backend/tests/test_local_peaks.py` (seeded click tracks and bursts in `tests/local_peaks_signals.py`).

## Noise floor

A note that is practically silent is not a note. The note analysis never gives exactly 0 for a note nobody plays (the spectrum leaks, recordings hiss), so, right after the analysis (`backend/app/services/noise_floor.py`, feature 033), **every note strength strictly below one thousandth of the largest strength in the file is set to 0**: 60 dB below the loudest note, the strengths being amplitudes. It is cut once, before the frames are averaged and smoothed, so every picture, the Notes and Threshold settings and the chords see the same notes, and a note that is cut is not counted as a note or as part of a chord.

- **Fixed**: there is no setting, request field or control. It applies to every image type, whether or not the image type has a Threshold; with a Threshold the stricter of the two decides (a Threshold of 0 does not switch the floor off).
- **The reference is the loudest value of the whole file**, the four notes above the 84 piano notes included (the same reference as the Threshold), because the analysed strengths have no absolute decibel scale. A note exactly at the floor still counts. A very loud click therefore raises the floor for the whole file and can silence quiet music around it.
- **The chord measurement applies the same cut itself** (to any array it is given, before combining the octaves of a letter), so a faint note never completes a chord. The beat (local peaks) is measured from the audio, not from the note strengths, and does not change.
- It does not tell tonal from non-tonal sound: noise, speech and percussion above the floor are notes, and so are their chords.
- Tests: `backend/tests/test_noise_floor.py` (the cut, with an independent oracle and mutation checks) and `tests/test_noise_floor_api.py` (every image type through the job, with and without a Threshold).

## Chord intervals

`backend/app/services/chords.py` is a third measurement, built on the note analysis (feature 031): for every analysis window it says **which chord the loudest letters form**, from a list of chord types that the caller asks for. It is **the measurement only**: nothing uses it yet (no job field, response key, page control or picture), so how it is used is a later feature.

- **A chord type** is a tuple of **1 to 3 intervals**, each a whole number of steps (half steps) from 1 to 11, in increasing order, above an **implied root**: `(4,)` is the notes 0 and 4 (a major third), `(4, 7)` the notes 0, 4 and 7 (a major triad), `(3, 7, 10)` a minor seventh. A bare number is a one-interval type (`((5), (7))` in Python is the two types `(5,)` and `(7,)`). The types are always parameters; none is built in.
- **What is matched**: the 84 piano notes of a window are first combined into the **12 letters**: the strengths of a letter in all its octaves are added up (C2, C3 and C4 are one note) and a letter stands for its loudest octave. A type with `n` intervals then looks at the **`n + 3` loudest letters** (4 for one interval, 5 for two, 6 for three: never more than 6; a letter with no strength does not count; ties go to the lower letter) and tries **every choice of `n + 1` of them**. The notes of a choice are moved **down by whole octaves** until they are less than an octave above the lowest (C3 and E4 become C3 and E3: 4 steps), and the steps are compared with **every inversion** of the type: moving the lowest note up an octave and counting from the new lowest one. `(4,)` is 0, 4 in root position and 0, 8 in first inversion (E4 and C5); `(4, 7)` is 0, 4, 7, then 0, 3, 8, then 0, 5, 9. So a louder note that is in no chord does not hide a chord among the other loud letters, and the overtones of a note (its fifth, its third) can be taken for chord notes; that is accepted, because the chords are meant to be aggregated later (tonal center, modes...).
- **Which match is recorded** when several fit (a fourth is an inverted fifth): the one with **the most intervals**, then **the loudest letters** (their strengths added), then **the largest interval**, then the **lowest inversion**, then the first choice of the louder letters. So `(4, 7)` wins over `(4)`; with `(4)` and `(8)` asked for, notes 8 steps apart are `(8)` in root position and notes 4 steps apart are `(8)` in first inversion; and C E G with a faint B is the triad `(4, 7)`, not `(4, 11)` on C E B, although `(4, 11)` is wider (the loudness comes before the widest interval so that a faint note cannot win by making a wide interval; for the same letters the widest interval still wins). Two different types never fit the same letters at the same inversion with the same widest interval, so the list order never decides.
- **What is recorded** for each window (`ChordRecord`): the chord type as given, the **inversion** (0 is root position) and the **original notes** (0 to 83, 0 being A1 at 55 Hz), lowest to highest: the loudest octave of each letter of the chord, as it sounds. The result (`ChordSeries`) has one entry per window, in window order, like the note strengths: the arrays `type_index`, `inversion` and `notes` (`-1` for no chord), and `record(i)`, `records()`.
- **The pictures' limits** are optional and are the pictures' own functions: `note_count` (the Notes setting: only the notes with the most total energy over the file, each in its own pitch) and `threshold` (the Threshold setting: a note strictly below that percentage of the largest value is hidden in its window). With neither, all 84 notes can be used.

```python
from app.services.chords import measure_chords
from app.services.note_analysis import analyze_wav

analysis = analyze_wav("audio/song.wav", 44100, 8192)
chords = measure_chords(analysis.frames, [(4,), (7,), (4, 7), (3, 7)], note_count=None, threshold=None)
chords.record(120)             # ChordRecord(chord_type=(4, 7), inversion=1, notes=(31, 34, 39)), or None
chords.type_index              # one entry per window, -1 where no chord was found
```

Tests: `backend/tests/test_chords.py` (an independent oracle that works from frequencies and explicit permutations; every one of the 231 chord types in every inversion) and `tests/test_chords_audio.py` (synthesized chords through the real note analysis).

## Audio frames UI

**Layout** (since feature 008): the page has two columns. The left column holds the audio file chooser at the top, then the progress and error messages and the result: the frame preview with its playback controls (play/pause, loop, position slider), followed by the result summary. The right column holds the settings and the *Create frames* button, so new settings can be added there without moving the preview. Window size and frame rate share one row. Each setting's explanation sits behind a small info (*i*) button that opens a popover (Escape or a click elsewhere closes it); validation errors stay visible under their field. Below 960 px wide the columns stack, with the chooser and preview first and the settings after. The components are `FilePicker.vue`, `SettingsForm.vue` and `InfoPopover.vue` in `frontend/src/components/`, and the text of the explanations is in `frontend/src/utilities/help.ts`.

Open the frontend, choose a `.wav`, pick the window size from the dropdown (a power of 2: 4096, 8192, 16384 or 32768; default 4096), set the frame rate (1–60, default 30), and press *Create frames*. The server reads the sample rate from the file, runs the note analysis, averages the windows within each frame period, and writes one color PNG per frame. By default (the `contour` image type, see **Image type** below) it is a **600 × 400** picture (exactly 3:2): the 12 × 7 grid of the note values drawn as a filled contour map, with one row per octave and one column per note name, so the note directly below another is the same note an octave higher (double the frequency). The lowest note (55 Hz) is the top-left value, and only the first 84 notes are drawn (up to about 6645 Hz); the four highest of the 88 analyzed notes are left out of the picture but still count when the colors are scaled to the loudest value in the file. The page then plays the frames as an animation (play/pause, loop, position slider).

- `POST /api/jobs` (multipart: `file`, `window_size`, `frame_rate`, and the settings of the picture) creates the frames. `GET /api/jobs/{job_id}/frames/{index}` returns one PNG. Errors are `{"detail": "..."}`.
- Uploaded audio goes to `<system temp>/music-visualizer/audio/<job_id>/audio.wav` and frames to `<system temp>/music-visualizer/frames/<job_id>/`. Override with `MV_AUDIO_TEMP_DIR` and `MV_FRAMES_TEMP_DIR`. Old submissions are not cleaned up automatically.
- Limits are settings in `backend/app/config.py` and can be overridden with `MV_` environment variables: 200 MB upload (`MV_MAX_AUDIO_BYTES`) and 30,000 frames (`MV_MAX_FRAMES`).
- **Frequency buffers** (feature 043; this replaces the Window spacing, Smoothing and Smoothing window settings of features 003, 006 and 012, which were removed): the strength of the 88 notes is measured in a window of the chosen size every **60 ms** of the file, whatever the frame rate. 60 ms is shorter than a 32nd note at 120 beats per minute (62.5 ms), so even a very short note is measured. The step is `sample rate * 60 / 1000` samples (2646 at 44.1 kHz; it may be a fraction of a sample, and each start is rounded to the nearest sample), so neither the frame rate nor the window size changes it. The frame rate only decides how many pictures are made: each frame is the **average of the buffers that start in it**, which is the only smoothing of the note data (a low frame rate smooths more: at 10 frames a second a frame averages 1 or 2 buffers, at 2 frames a second 8 or 9), and a frame in which no buffer starts (above about 16.7 frames a second) repeats the latest earlier buffer. The frames are drawn as they are, with no blending with earlier frames. The window size stays a setting, and a window longer than 60 ms makes the buffers overlap. In the API the old fields `window_spacing`, `smoothing` and `smoothing_window` are ignored if they are sent (not refused) and are not echoed; the response keeps `step_samples` (always the 60 ms step) and `window_count`. A file that would give more than `MV_MAX_WINDOWS` buffers is refused ("Use a shorter file."). The definition is in `specs/043-decouple-frame-rate/`.
- **Held notes and Extra notes (k)** (feature 044) change which notes the pictures that take the n loudest notes of each frame count: Decay, Decay Exp, Polar Chords, Chromatic Decay, Chromatic Wireframe, Polychord, Spirograph and, for the starts of its voted tempos, Rhythm Circles (for the two Chromatic pictures the unit is the letter). A note that was among the n loudest in the frame before is *held*: it keeps its place while it is still among the loudest **n + k** of the frame and still sounds, so a note that is fading after its attack is not replaced by a new note that is louder. A louder new note (a *newcomer*) cannot displace a held note; it waits for a free place, which is a place that no held note occupies (at the start, when fewer than n notes sound, or when a held note falls below the loudest n + k) and goes to the loudest note that is not held. The selection is ordered by loudness (so the loudest held note still gains most, or has the first bar or link) and is made frame by frame on the averaged frames (module `backend/app/services/held_notes.py`, `hold_loudest()`; ties go to the lower note). With k = 0 it is exactly the old selection, so the library functions take `extra=0` by default and nothing changes for a caller that does not pass it; a steady chord (nothing displaced) gives the same pictures for every k. **Extra notes (k)** is a whole number from 1 to n (5 for Decay, Decay Exp, Chromatic Decay and Chromatic Wireframe; Notes shown for Polar Chords; Number of notes for Polychord), default 2, in the page's **Held notes** group (a slider whose maximum follows n) for those six pictures only; in the API the optional `extra_notes` field (not sent: 2; a value that is not a whole number from 1 to 8 is refused with a 400 "The extra notes must be a whole number from 1 to 8.", and above n for a picture that uses it with "... from 1 to {n}.", before the file is read; Contour, Energy graphs and Rhythm Circles accept 1 to 8 and ignore it) and the answer's `extra_notes` key. The chord bar of Polar Chords is not changed. The definition is in `specs/044-sustained-loudest-notes/`.
- **Colormap** (since feature 014) chooses how the pictures are colored (first the tiles, which were removed in feature 040; now the contour and the other pictures). It replaces the earlier color rules (a hue moved by related notes, a saturation and a per-frame brightness from the loudness of the sound, and the Brightness, Saturation, Hue steps, Saturation steps and Brightness steps settings), which made the animation "blinky" and have been removed. The choices are four of matplotlib's named colormaps: `summer` (green to yellow), `autumn` (red to yellow), `hot` (the default: dark red through red and yellow to white) and `cool` (cyan to magenta), with exactly matplotlib's 8-bit colors (the 256-entry table of each, read from `matplotlib.colormaps`; matplotlib is now a requirement). A tile's color is the table entry at the position `sqrt(value / peak)`, rounded to one of 256 steps, where `value` is that note's smoothed value in the frame and `peak` the largest smoothed value anywhere in the file (all 88 notes count, as before): a note with no strength has the first color of the scale, the strongest note of the file the last, and a stronger note never has an earlier color. A tile's color therefore depends only on its own note's strength and the file's peak: not on any other note, not on the loudness of the frame, and not on the frame number, so a steady note keeps one color and the picture is no longer dimmed or brightened as a whole. A silent file has every tile in the first color of the scale (a very dark red for `hot`). Hidden tiles (see Threshold) are black; `hot` starts at a very dark red (10, 0, 0), so with `hot` a quiet tile and a hidden one look much alike, which the other three colormaps avoid. On the page it is the **Colormap** dropdown (Summer, Autumn, Hot, Cool, starting at Hot) with an info button and a line in the result summary. In the API it is the optional `colormap` form field (exactly `summer`, `autumn`, `hot` or `cool`, lowercase; leave it out for `hot`; anything else, including an empty value, `viridis` or `hot_r`, is refused with a 400 saying "The colormap must be one of summer, autumn, hot, cool."), and the response adds `colormap`. A request that still sends the removed fields (`energy`, `brightness`, `hue_step`, `saturation_step`, `brightness_step`) is accepted and they are ignored; the response no longer reports them. The definition is in `specs/014-colormap-colors/data-model.md`.
- **Image type** (since feature 013) chooses which kind of picture is made from a frame's note values. **Since feature 046 there are ten: Contour** (`contour`, the default, since feature 015; described in the next paragraph), **Decay** (`decay`, since feature 027), **Decay Exp** (`decay-exp`, since feature 030), **Polar Chords** (`polar-chords`, since feature 032), **Energy Graphs** (`energy-graphs`, since feature 034), **Chromatic Decay** (`chromatic-decay`, since feature 035), **Rhythm Circles** (`rhythm-circles`, since feature 038), **Chromatic Wireframe** (`chromatic-wireframe`, since feature 039), **Polychord** (`polychord`, since feature 042) and **Spirograph** (`spirograph`, since feature 046), each described below. **Feature 040 removed the five that were not as useful: Tiles (`tiles`, which was the default), Blended tiles (`blended`), Circles (`circles`), Circles paint (`circles_paint`) and Concentric (`concentric`)**, with their code (`circles.py`, `circles_paint.py`, `concentric.py`, the blend and the tile writer of `image_types.py` and `frame_rendering.py`, `colormaps.colorize`, `hidden_notes`), their request fields (`blend_width`, `circle_unit`, `circle_memory`, `circle_notes`, `circle_radius`, `circle_resize`: they are no longer in the request or in the response; a request that still sends them has them ignored like any unknown field) and their tests, and the settings that only they used (Blend width and the five circle controls) from the page. What the pictures shared moved: `note_grid.py` has the 12 × 7 grid (`GRID_COLUMNS`, `GRID_ROWS`, `NOTES`, `RINGS`, `tile_edges`, `full_radius`) that Decay, Decay Exp, Chromatic Decay and the chord measurement use, `frame_saving.py` the number of threads that save pictures, and `colormaps.py` the middle color row. **An `image_type` that is not one of the eight is refused with a 400** (`The image type must be one of contour, decay, decay-exp, polar-chords, energy-graphs, chromatic-decay, rhythm-circles, chromatic-wireframe.`) and a request with none is a contour. The earlier paragraphs of this document that describe tiles, blended tiles, circles and concentric circles are the history of those features (the definitions are still in `specs/`).
- **Contour** (since feature 015) is the first image type (and, since feature 040, the default): the 12 × 7 grid of smoothed note values is drawn as a **filled contour map**, bands of color that flow from one note to the next like the elevation map of a landscape in which every note is a point on the grid and its strength is the height. It is drawn by matplotlib: `contourf` on the coordinates `np.linspace(0, top, 12)` by `np.linspace(0, top, 7)` (`top` is the largest value of the frame being drawn, worked out again for every frame; with the axes off this changes no pixel, the colors come from the scale below), with the selected colormap, the axis decorations off (`set_axis_off`), saved with `pyplot.savefig` from a figure that is exactly 600 × 400 pixels, so the contour fills the whole picture with no axes, border or margin. The picture has the same orientation as the tiles (lowest octave at the top, lowest note name at the left), the same frame count and timing, and is an opaque RGBA PNG (about 1 to 2 KB). **Directional smoothing** (`directionalSmoothing` in `backend/app/services/contour.py`) softens the hard edges: the grid of the frame (first row at the bottom, as it is drawn) is visited point by point, row by row, and each point, the first two rows and the first two columns excluded, is averaged with its predecessors in the first of three directions in which the last step is larger than the step before it: along the **diagonal** (the point, the diagonal neighbour and the one before it: the average of **three** values), along the **columns** (the point and its neighbour before it in the row: **two** values) or along the **rows** (the point and the neighbour above it: **two** values); if no direction qualifies the point is left as it is. The changes are made in place, so a point sees the smoothed values before it. The smoothing works on a copy of the frame's values (an earlier version smoothed the caller's own array, so drawing the same array twice smoothed it twice), the colors are those of the colormap at the smoothed value, and the scale still ends at the frame's largest value *before* the smoothing, so a lone loud note is drawn a little lower than its raw value. Things worth knowing: **the contour has 12 level edges (11 bands), evenly spaced from the smallest to the largest value of the smoothed grid of the frame being drawn** (`np.linspace(Z.min(), Z.max(), 12)`; matplotlib chose the levels before the number was raised), and **the color scale runs from 0 to the largest value of the frame being drawn** (so the loudest note of every frame is at the end of the colormap, and a given strength can have a different color in different frames; until 2026-10-12 it ran to `max`, the largest smoothed note value anywhere in the file, the four undrawn notes included, for the whole file); **the scale is linear** in the strength, unlike the tiles, which take the square root of the share of the peak, so a quiet note is closer to the start of the colormap in a contour than in the tiles; Smoothing, its window, the Threshold and the Colormap apply as for the other types (a note hidden by the Threshold counts as 0, so it does not raise the contour); a frame in which every value is the same (a silent file, a quiet moment, every note hidden) is one flat picture of the colormap's color for that value (the first color for 0), because matplotlib has no contour to draw there; the **Blend width does not apply** (a value sent with `image_type=contour` is accepted and ignored). A contour job takes longer than a tiles job: about 14 ms per frame on the development machine (a 60 second file, 1,800 frames, in about 25 s; 300 frames in about 4 s) while a whole tiles job of the same 60 second file, analysis included, takes about 1 s and a blended one about 1.3 s. matplotlib's `pyplot` is imported only when a contour is drawn (windowless Agg backend) and holds global state, so contour drawing runs one job at a time. The code is in `backend/app/services/contour.py`; the definition is in `specs/015-contour-image-type/data-model.md`.
- **Frame size** (since feature 021): every frame of every image type is **600 × 400 pixels** (3:2), where it was 252 × 168. The old frames were shown by the page at up to about 660 pixels with pixelated scaling, so every pixel was blown up more than two and a half times and the pictures looked blotchy; the pictures are now **drawn** at the larger size, not enlarged: the tile grid is spread over the whole frame (50-pixel columns, rows of 57 or 58 pixels, at every oversampling within one pixel), the soft edge of blended tiles keeps its width in proportion to a tile, a contour is drawn as a 600 × 400 figure and the circles have smooth edges at their real size. The frame count, the file names, the timing, the notes and the colors do not change (the colors at the centers of the tiles are exactly as before); the size is fixed, not a setting; frames that already exist are not converted. The frame player shows a frame at its own size, up to 600 pixels (a 1 pixel outline, no border, no pixelated scaling), and scales it down smoothly keeping 3:2 on a narrower window. Measured for a 60 second file (1,800 frames) at 252 × 168 and at 600 × 400: tiles 0.6 s and 1.0 s (7.1 s at oversampling 5), blended tiles 1.0 s and 6.4 s, contour 15 s and 20 s, circles 3.8 s and 18 s at the defaults and 9.6 s and 50 s at the largest settings; the frames take 1.3 to 3.6 times the room (blended tiles the most: 18 to 67 MB). The size is defined once, `IMAGE_WIDTH` and `IMAGE_HEIGHT` in `backend/app/services/frame_rendering.py` (with `REFERENCE_WIDTH`, the 252 pixels the circles are measured against); the definition is in `specs/021-wider-frames/`.
- **Decay** (since feature 027) is the seventh image type, `decay` (`backend/app/services/decay.py`): **the same 84 circles as Concentric, in the same places and with the same Note layout, but each circle is one flat disc that keeps points from frame to frame**. Every circle has **0 to 64 points**, 0 before the first frame. The points set the **size** (the smallest circle, one twelfth of the full radius, at 0 points; full size, just touching its neighbours, from 24 points on; linear in between) and the **color** (the colormap's first color at 0 points, its last color at 32 points; the disc is flat up to there). From **32 to 64 points the circle gets the 12 concentric rings** of Concentric: ring `k` (1 at the center) is at `b − s × (k − 1) / 11` of the way along the colormap, with `b = min(points, 32) / 32` and `s = (points − 32) / 32`, so at 32 points every ring is the last color and at **64 points the 12 rings run from the last color (the center) to the first (the edge)**; as a circle fades the outer rings come back to the last color first, so the decay is seen all the way down from 64. In every frame the **5 loudest notes** (the smoothed values, ties to the lower note, a note with no energy does not count) **gain** 24, 20, 16, 12 and 8 points in order of loudness, plus **8 × the frame's position in the local energy peak** (8 at the top of the beat, 0 at the bottom; the Local peaks measurement is made for every Decay job); the points are added to what the circle has and held between 0 and 64. Every **decay rate** frames (a number from **0.25 to 4** in steps of 0.25, default **1**; below 1 several smaller steps are taken in every frame, which is smoother, above all at higher frame rates; the one setting of this image type, counted from frame 1) there is a **decay step**: every circle gives points to each of the circles around it (the up to 8 cells around it on the grid, diagonals included, no wrap-around). **The rate depends on the points** (since 2026-11-01), per neighbour and per frame; **the four amounts are settings of the Decay group** (since 2026-11-01: **Low saturation**, **Medium saturation**, **High saturation** and **Saturated**, sliders from 0.5 to 3 in steps of 0.5; request fields `decay_low`, `decay_medium`, `decay_high`, `decay_saturated`; each checked for every image type before the file is read, `The <level> saturation decay must be a number from 0.5 to 3.`, and echoed in the response; the page calls the categories saturation levels and does not list their points), with the defaults: a circle with **1 to 8 points gives 0.5** (1 every 2 frames), **above 8 and up to 20 points 1**, **above 20 and below 64 points 2**, and a **saturated circle (64 points) 3** (24 in all), so a held note spreads faster the fuller its circle is. **A step moves `decay rate` frames' worth** (the setting says how often the decay happens, not how much: the average rate is the same at any setting; with a rate above 1 a circle with plenty of points gives most of what it has away in one step, so the spots disappear in jumps, and a rate below 1, which takes several smaller steps in every frame (0.25 takes four), is the smoothest). A circle on an edge or in a corner **decays as if it had 8 neighbours**: it gives the same amount to each neighbour it has (5 on an edge, 3 in a corner) and the rest is lost, so every circle loses the same total whatever its place. A circle with fewer points than it would give only gives what it has, in the same proportions, so no points appear from nothing; all circles give and receive at the same time from the points before the step; and a circle left with less than a hundredth of a point has none, so a faded circle is really at 0. The size and the color are antialiased. The settings that apply are the colormap, the analysis settings, **Decay rate**, **Note layout**, and **Local peaks** (Minimum distance, no checkbox); Threshold, Notes, Oversampling, Interpolate and Gaussian smoothing are accepted by the request and ignored. The request field is `decay_rate` (a whole number from 1 to 10, checked for every image type before the file is read, `The decay rate must be a number from 0.25 to 4 in steps of 0.25.`) and it is echoed in the response. The frames are 600 × 400, with the count, names and timing of the other image types; the other six image types are unchanged.
- **Decay Exp** (since feature 030) is the eighth image type, `decay-exp` (`backend/app/services/decay_exp.py`): **Decay with a different rate at which the circles take on and give away points**. Everything else is Decay: the same 84 circles, their size, color and rings by points, the 0 to 64 points, the 5 loudest notes of a frame gaining points with the beat bonus, the decay steps every **decay rate** frames (the same slider, 0.25 to 4, default 1, the one setting of this image type; request field `decay_rate`), the neighbours, the edge and corner rule, the Note layout and the Local peaks settings (measured for every Decay Exp job). Two amounts change. **The gain**: a note that would gain `g` points in Decay (24, 20, 16, 12 or 8 by rank, plus `8 × position`) gains `g × e^(−g/taper)`, so about 1.19, 1.64, 2.17, 2.68 and 2.94 points with no beat at the start, when the taper is 8: **the loudest note gains the least**. **The taper is not fixed**: it starts at 8, **rises by 0.01 in every frame up to 12** (the cut gets gentler, so the gains grow: at 12 they are about 3.25, 3.78, 4.22, 4.41 and 4.11), and **as soon as more than 10 circles have more than 32 points it falls by 0.01 in every frame until it is back at 8**, and then rises again; it never leaves 8 to 12. It changes the gain only. **The loss**: instead of the amounts of the four saturation levels, a circle with `p` points before a step gives **each neighbour** `sin²(π/2 × p/64)` points per frame (0 with no points; about 0.0006 at 1 point, 0.04 at 8, 0.31 at 24, 0.5 at 32, 0.85 at 48 and 1 at 64, so **the fuller a circle is the faster it drains**: 8 points a frame in all at 64), a step moving `decay rate` frames' worth and a circle never giving more than it has. The four decay amounts (`decay_low`, `decay_medium`, `decay_high`, `decay_saturated`) are still accepted, checked and echoed, and have no effect; they are not shown for Decay Exp. **What this looks like**: a single steady note starts at about 1.2 points a frame and its circle grows for a long time as the taper rises (about 20 points at frame 100, 32 at frame 400), settling near 34; a group of notes close together fills more than 10 circles over 32 points, which turns the taper down, so it swings between 8 and about 10 while the biggest circle reaches about 57 and settles near 50; nothing reaches 64. After the sound stops the charged circles drain quickly, but a faint circle hardly drains at all (the loss falls with the square of the points), so the tail is long: after a loud passage the largest circle is under 1 point after about 3,100 frames (1 minute 43 seconds at 30 frames a second) and exactly 0 only after about 228,700 (about 2 hours); by then it has long looked like the smallest dot. The request value is `decay-exp` (with a hyphen); the frames are 600 × 400, with the count, names and timing of the other image types; the other seven image types are unchanged.
- **Polar Chords** (since feature 032) is the ninth image type, `polar-chords` (`backend/app/services/polar_chords.py`): **a polar bar graph of the notes and the chord**, bars that start at the center of the circle and reach outward, on the colormap's middle color. Angles are measured from straight up. The notes have **84 equal arcs** (about 4.29 degrees each). **Clockwise, each of the 84 piano notes has its arc** (with the **Note layout** Rows, the default, A1 first in order of pitch; with Spiral the arc of a note is the cell in which the spiral layout of feature 026 draws it, so middle C is in arc 29 instead of 27), and the **loudest notes of the frame get a bar** that fills their arc: how many is the one setting of the image type, **Notes shown**, a whole number from **5 to 8**, default **5** (request field `polar_notes`, checked for every image type before the file is read, `The number of notes shown must be a whole number from 5 to 8.`, and echoed in the response; a note with no strength never gets a bar and ties go to the lower note). **Counterclockwise, the chord ring has 84 arcs (as wide as a note's), one for each root letter and chord type: the 7 chord types of A, then the 7 of A#, and so on through the 12 letters (a letter is a note without its octave)**; the types are `(7)`, `(4, 7)`, `(3, 7)`, `(4, 10)`, `(4, 11)`, `(3, 7, 10)` and `(4, 6)`, in this order, found with the chord interval measurement of feature 031 (one chord at most per frame: the longest that fits among the 4 to 6 loudest letters of the frame, octaves combined, then the loudest and then the widest; the notes of the chord are not always among the drawn note bars). The root letter and the type decide the arc (`7 x letter + type`, letters from A: a C major triad is arc 22, E major arc 50); the octave and the inversion do not matter, and a fourth is the fifth of its upper note (C with F above it is the fifth of F: it is recorded as an inverted fifth). **Every bar reaches out to `0.5 + 0.5 x p` of the full radius** (190 pixels on 600 x 400), `p` being the frame's place in the local energy peak (0 at the bottom of the beat, 1 at the top, 0 when no beat is known), so the picture breathes with the beat and all the bars of a frame are equally long; the loudness is shown by the color. **The note bars jump to their notes** (revised 2026-11-18; before that a bar moved one arc a frame toward a new note): every bar is in the arc of its note in every frame, so when a note changes its bar is in the arc of the new note at once, with the new note's color. **Colors**: the notes run from the **middle of the colormap (a faint note) to its start (the loudest)**, the chord from the **middle to its end**, by the square root of the strength as a share of the largest value of the file (for the chord the average of its notes); with a colormap with two different ends, such as Cool Warm, the notes and the chord have a color family each, and a faint bar is close to the background color. The chord is drawn over the notes where they cover the same angles. The edges of the bars are smooth. The settings that apply are the colormap, the analysis settings, **Notes shown**, **Note layout** (it changes only the arcs of the notes; the chord does not depend on it), and **Local peaks** (Minimum distance, no checkbox); Threshold, Notes, Oversampling, Interpolate and Gaussian smoothing are accepted by the request and ignored. The frames are 600 x 400, with the count, names and timing of the other image types; the other eight image types are unchanged.
- **Energy Graphs** (since feature 034) is the tenth image type, `energy-graphs` (`backend/app/services/energy_graphs.py`): **a running histogram of the 84 piano notes with two data sets**, on the colormap's middle color, in the usual 600 x 400 frame, with a title, a legend and the octave labels A1 to A7. Each note has a **pair of thin bars**, the lowest note (A1) on the left: the **frequency** bar (the start color of the colormap) and the **amplitude** bar (the end color). **Frequency**: in every analysis window the 84 notes are ranked by strength and each adds its **rank score** to its own total, **84 for the loudest, 83 for the second loudest, and so on down to 1**; a note with no strength (under the noise floor of feature 033) adds nothing, and neither do the notes ranked below it; equal strengths rank the lower note first. **Amplitude**: in every window each note adds its **quasi-decibel** value, `20 log10(amp) / (20 log10(max))`, where `max` is the largest amplitude of any of the 84 notes in any window of the whole file: 1 for the loudest note of the file and less for fainter ones; a silent note adds 0, a negative value (an amplitude under 1) is clamped to 0, and a file whose loudest amplitude is 1 or less adds nothing (the ratio of logarithms is meaningless there). Both totals **accumulate** from the start of the file to the frame (a window is counted once, in the frame it starts in, so the last frame holds the sum over every window). **They are not drawn as totals** (a total grows with the length of the file, and the two have different sizes): each data set is divided by its own largest total, so that it runs from 0 to 1, and then put through a **softmax** over the 84 notes (`exp(x) / sum(exp(x))`), which puts the two on the same scale, each adding up to 1. A softmax is never 0 and its values are close to each other, so **the smallest share of each data set is then taken off all its shares**: the smallest bar of each data set has height 0 (a note that has not sounded has no bar when others have) and the clear winners stand out. The bars are then scaled by the largest remaining value of the frame, so **the tallest bar is always the same height** (336 pixels). A data set with no total yet (before the first sound, or the amplitude of a file that is never above 1) or with all totals equal has no bars. It has **no setting of its own, no request field and no response field**: the analysis settings and the colormap apply; and every other setting (threshold, notes, oversampling, interpolate, Gaussian smoothing, note layout, Local peaks, Notes shown, decay) is accepted by the request, checked as for every type, and ignored; the beat is not measured for it. The frames have the count, names and timing of the other types and can be made into a movie (feature 029). The job costs about what Tiles costs plus the drawing (about 1.3 s for `backend/audio/sonata.wav`, 190 s at 5 frames per second). The definition is in `specs/034-energy-graphs/`; the first version of this type also had two pies (harmonic against non-harmonic energy, and loudness against the loudest window), which were removed on 2026-11-08.
- **Chromatic Decay** (since feature 035) is the eleventh image type, `chromatic-decay` (`backend/app/services/chromatic_decay.py`): **Decay Exp for the 12 chromatic tones only**. There are **12 circles, one for each letter** (a letter is a note without its octave, with its accidental, counted from A: A, A#, B, C, C#, D, D#, E, F, F#, G, G#, as in Polar Chords), on a **ring in circle-of-fifths order, clockwise from the top: C, G, D, A, E, B, F#, C#, G#, D#, A#, F**, 30 degrees apart, centered in the 600 x 400 picture (ring radius 150.9 pixels), with the full radius that lets two neighbouring full circles just touch (39.1 pixels). **The energy of a letter in a frame is the largest of the strengths of its 7 octaves** (not their sum), and the points are added as in Decay Exp with the 12 letters in the place of the 84 notes: the five loudest letters (ties to the lower letter, a letter with no energy not counting) gain 24, 20, 16, 12 and 8 points plus the beat bonus of up to 8, each cut back by `exp(-g / taper)` with the moving taper of Decay Exp (8 to 12). **The point levels (0 to 64), the size of a circle (one twelfth of the full radius at 0 points, full from 24), the colors and the twelve rings (from 32 points) are those of Decay and Decay Exp**, on the colormap's middle color. **The decay goes only to the two letters 5 and 7 semitones above** (letter `n` gives to `(n + 5) mod 12` and `(n + 7) mod 12`: C to F and G, F to A# and C, G to C and D), which on the ring are **the two neighbours of the circle's place** (7 above is the next one clockwise, 5 above the next one counterclockwise). A fourth and a fifth add up to an octave, so the receivers give back to the giver: a note decays to itself to some extent through the round trip (there is no direct share kept). **(Since 2026-11-10 the 8 below is `PRETEND_NEIGHBORS`, a constant of `chromatic_decay.py` that is 6: a circle gives away 6 times the loss, one sixth to each receiver and four sixths lost, instead of 8, one eighth and six eighths; Decay and Decay Exp keep `decay.NEIGHBOURS`.)** **How much is given is Decay Exp's**: a circle with `p` points gives away `8 x sin^2(pi/2 x p/64)` points per frame (the total a circle of Decay Exp gives, never more than it has), split as if it had 8 neighbours: **each of the two receivers gets one eighth of it, what a neighbour gets in Decay Exp, and the other six eighths are lost**, as for an edge or corner circle there (the ring has no edge: without this nothing would ever vanish, and the points would circulate and settle to an even level). All circles give and receive at the same time from the points before the step; points are held between 0 and 64 and a circle under a hundredth of a point has none, so a silent file ends with every circle at 0. **The decay rate of this type is a whole number of frames from 1 to 10** (default 1): a step falls at every rate-th frame and moves that many frames' worth of decay, so the average rate is the same whatever the setting (the levels are of the same order, not identical, because the loss is not a straight line of the points). It keeps the request field `decay_rate`, which is **validated for the image type**: a whole number from 1 to 10 for `chromatic-decay` (a value such as 2.5, 0, 11 or text is refused with 400 `The decay rate must be a whole number from 1 to 10.` before the file is read; 3 and 3.0 are accepted; the response echoes an integer) and, for every other type, 0.25 to 4 in steps of 0.25 as before. On the page it has its own control, **Decay rate** (1 to 10, in the group **Chromatic Decay**), whose value is kept separately from the Decay rate of Decay and Decay Exp. The settings that apply are the colormap, the analysis settings, the decay rate, and **Local peaks** (the beat always charges it, no checkbox); the Note layout (it has no meaning for a ring of letters), the four decay amounts and every grid setting are accepted by the request, checked as for every type, and ignored. No new field in the request or the response. **The Threshold (since feature 037)** works for Chromatic Decay: the existing Threshold setting (the request field `threshold`, 0 to 10 percent, 0 off and the default, the Threshold slider on the page, which sits in the Chromatic Decay group before the Decay rate, and the line of the result summary) now applies to this type, which used to accept and ignore it. In the points calculation (`circle_points(values, beat, decay_rate, threshold)`, and `circle_tapers`, which shares it) **every smoothed note value strictly below `threshold` percent of the largest of all the smoothed values passed in (every frame and every column: the whole file, as for Tiles) is set to 0** before the energies of the letters are worked out, so a faint note adds nothing to its letter, a letter with no note above the floor does not count among the five loudest and gains nothing in that frame, and the points, the taper and the picture follow; a value exactly at the floor is kept, and with the threshold off (or a silent file) nothing changes. The values are the averaged frames. The decay, the beat and the rings are not changed by it, and the circles that already have points keep decaying (a letter that is faint can still be lit by the decay of the loud letters next to it on the ring). Library: `chromatic_decay.apply_threshold`, `check_threshold` (the message is `The threshold must be a number from 0 to 10.`, the same as for the other types). **The rings of the beat (since feature 036)**: in the empty middle of the ring of letters there is a **target of 12 concentric rings, 140 pixels across** (a radius of 70 pixels on 600 x 400, scaled with the picture size, 5.8 pixels a ring) that shows where the music is in its beat. For each frame the beat gives its position in the local peak (0 far from a peak or between peaks, 1 at the top of one, the measurement of the Local peaks settings that already charges the circles) and the distance from the peak is `1 - position`. **The center ring is the distance of the current frame `t`; ring `k` outward, from 2, is the average of the distances of the two frames `t - (2k - 3)` and `t - (2k - 2)`** (ring 2 is frames `t - 1` and `t - 2`, ring 3 is `t - 3` and `t - 4`, ring 12 is `t - 21` and `t - 22`), so the newest moment is in the middle and a flash at the top of a beat spreads outward one ring every two frames; the moments before the first frame count as far from a peak. A ring is colored from the colormap by its distance, **from the first (left) color at the top of the beat to the last (right) color at the bottom of the beat, using the whole colormap**: the position in the local peak is 0 to 1 in principle but inside the peaks of real music it hardly goes below about 0.55, so the distance is **stretched over the range of the beat of the file** (`beat_distances`: the highest position is distance 0 and the 1st percentile of the positions inside the peaks, `PEAK_BOTTOM_PERCENTILE`, is distance 1, in a straight line between and held at the ends; a frame outside every peak is 1), the colors between at the same share. The rings are always drawn for Chromatic Decay, with no setting and no new request or response field (the Local peaks settings change them as they change the charging); with no beat known (`write_chromatic_frames(..., beat=None)`) no target is drawn. The middle of the ring of letters is 224 pixels across, so the target never touches a circle. **Known consequence of keeping the point levels**: the taper only falls when more than 10 circles have more than 32 points, which with 12 circles hardly ever happens (in tests with five letters fed at the top of the beat the largest circle reaches about 33 points), so in practice the taper rises to 12 over 400 frames and stays there, and the circles are mostly small and in the first half of the colormap; the user asked to keep the levels for now, so it is a candidate for a later change. The frames have the count, names and timing of the other types and can be made into a movie (feature 029). The definition is in `specs/035-chromatic-decay/`.
- **Rhythm Circles** (since feature 038) is the twelfth image type, `rhythm-circles` (`backend/app/services/rhythm_circles.py`): **how rhythmic the music is, as six concentric circles that turn** (eight until the second version of the local tempo finder, four from feature 040 to feature 047). Since **feature 047 (the tempo voting)** four of the circles show the **average and the raw best-voted tempo of the notes**, found by `backend/app/services/tempo_votes.py`, and two the **local peak** of the whole file (the Local peaks measurement above), unchanged. The tempo finder of feature 040 (`tempo_finder.py`, still used by Polychord's color) is no longer drawn here. **The voting**: a **start** is a frame in which a sounding note enters the selection of the **5 loudest notes held while they last** (the Extra notes setting k of feature 044: a sustained note is one start, notes that enter in the same frame are one start, a note that drops out and returns starts again). At every start after the first, the **note length** is the time since the previous start, and the tempos are the **18 metronome markings `72 + 4n` from 76 to 144 beats per minute**. A tempo is **possible** for a length when the length can be a half, quarter, eighth or sixteenth note, any of those dotted (1.5 times as long), or a triplet (1/3 or 2/3 of a beat) at that tempo (`60 b / T` seconds for `b` beats at tempo `T`; 10 note values): the tempo that the length implies, `60 b / L`, is within half a bin (2 beats per minute) of the tempo, **or** the note's length at the tempo is within half the time resolution of the starts (the 60 ms analysis step) of the length, the comparisons inclusive. **One vote is taken from every tempo (never below 0) and each possible tempo gets its points (never above the Vote limit): 2 if the length fits it as a half, quarter, eighth or sixteenth note, 1 if only as a dotted note or a triplet**, the most of the note values that fit and not their sum (a tempo that only dotted notes or triplets fit stays at 1 vote while the spacing is steady), so a tempo that stops fitting is forgotten in at most as many starts as the limit and the tempos can change as the music does. After each start the tempo with the most votes is the **first** (raw) tempo and the next the **second** (ties go to the lower tempo; a place without votes holds the starting tempo 120; the second is no longer drawn). The **average tempo** after a start is the **straight average of the first tempo after it and after the 4 starts before it** (5 in all, `AVERAGE_COUNT`; fewer at the beginning of the file), to steady the first tempo, which jumps from start to start. For every event there are six speeds, in revolutions per minute, in three layers (a level and, inside it, the rate of change of that level), **from the outside in: (1) the average tempo**, one turn for each beat, **(2)** its rate of change, **(3) the raw (first) tempo**, **(4)** its rate of change, **(5) the local peak**, the rate of the peak in beats per minute (60 for the first peak, and before it), and **(6)** its rate of change. A rate of change is the difference between the level at this event and at the one before divided by the seconds between the two events (**per second**: a tempo that rises by 6 beats per minute in half a second is 12, and the circle turns that many revolutions per minute) and 0 at the first event; the events are the note starts for circles 1 to 4 and the peaks for 5 and 6. Before the first start the first four speeds are 120, 0, 120 and 0, before the first peak the last two 60 and 0. A positive speed turns a circle **clockwise**; a rate of change is negative when the tempo slows down, and then the circle turns the other way. Every speed holds from its event until the next one, and the angle of a circle is the running total of its speed (divided by 60, in turns) from the start of the file, so the circles never jump when an event comes; the angle of a frame is read in its middle, at `(f + 0.5) / frame rate` seconds. The picture is 600 × 400 on the middle color of the colormap: six rings centered in the picture, the outer one 190 pixels from the center, all of the same width (a sixth of the radius) with a 4 pixel gap inside each ring and smooth edges. Ring *k* (1 outer to 6 inner) has the color at position `(k - 1) / 5` of the colormap and a **notch of an eighth of the circle** (45 degrees) in the color at the opposite position `1 - (k - 1) / 5`; the notch is what shows how far the ring has turned: at angle 0 it is straight up and it moves clockwise. **Settings**: the **Vote limit** (a whole number from 1 to 100, default 20: the most votes a tempo can have; a low limit follows the music quickly, a high one makes a tempo stay; the request field `vote_limit`, echoed in the answer for every picture, refused with `The vote limit must be a whole number from 1 to 100.` before the file is read; the page slider in the Rhythm Circles group), the **Extra notes (k)** (1 to 5 for this type, default 2, in the Held notes group) and the **Minimum distance** of the Local peaks group (default 350 ms; the peaks are measured once for this type with the fixed prominence of 20%: the beat is not measured for it); the colormap sets the colors, and every other setting is accepted, checked and ignored. The starts are found in the 60 ms analysis windows and not in the frames, so the voted tempos do not depend on the frame rate (the rate only decides at which moments the finished tempos are sampled). **Measured** (`specs/047-rhythm-note-voting/tools/verify_votes.py`, resolution 60 ms, the starts after the first 10 seconds; reported and not gated): the first version (starts found in the frames at 30 frames a second, every fitting tempo 2 votes, Extra notes 2, limit 20) put the first tempo within 10% of the target for 64% of the starts of `sonata.wav` (target 116) and 14% of `almost2.wav` (target 90). With the points above the frame-based starts give 23% on `almost2.wav` and 42% on `sonata.wav` (Extra notes 4, limit 10); with the starts from the 60 ms windows (the current code) 2% and 31%, because on the raw windows 64% of the gaps between starts are one window (the same note counted twice as a neighbouring column or the same column re-enters the selection) and a 0.333 s note is measured as 0.30 or 0.36 s on a 60 ms grid; 15 frames a second looked right on `almost2.wav` because a 90 bpm eighth note is exactly 5 frames there. **The average of 5** (the straight average, the baseline; Extra notes 4, limit 10) puts the tempo within 10% of the target for 14% of the starts of `almost2.wav` (2% raw) and 33% of `sonata.wav` (31% raw), and for the three computer-generated piano files (`piano-108bpm.wav`, `piano2-108bpm.wav`, `piano-120bpm.wav`) 74%, 59% and 24% (58%, 44% and 30% raw): it cuts the change from one start to the next from about 6 to 2.5 beats per minute but pulls every file toward 100 to 107 beats per minute, so it steadies the circle and does not fix the tempo; even on those steady files about half of the gaps between starts are one window. The tolerance is wide (a length of 0.335 s fits 13 of the 18 tempos at 60 ms), so the voting separates tempos only weakly on real music; the levers if it should do better are the tolerance, the note values, the points and, above all, how the starts are found (onsets from the energy rise of each register). The definition is in `specs/047-rhythm-note-voting/`.
- **Chromatic Wireframe** (since feature 039) is the thirteenth image type, `chromatic-wireframe` (`backend/app/services/chromatic_wireframe.py`): **the points of Chromatic Decay drawn as a ridge plot in three dimensions** instead of a ring of circles. The data is exactly that of Chromatic Decay (the same simulation, with the same decay rate, Threshold and beat; `chromatic_decay.circle_points`); only the drawing differs. **The 12 letters are spread evenly over the width**, in chromatic order from A (A, A#, B, C, C#, D, D#, E, F, F#, G, G#; not the circle-of-fifths order of the ring), each with a share `xmax` pixels wide (the width less a 10 pixel margin on each side, over 12: 48.33 pixels on 600 × 400) that starts at `start = b x xmax`. **The line is one function, the sum of the 12 letters' waves** (since 2026-11-12; before, each letter drew its own piece and the line jumped where a letter started): **every letter adds its own wave to every point `u` of the line**, with its own **frequency, amplitude and phase**. The wave of a letter is **the radius of its circle (the circle of Chromatic Decay for `p` points: a twelfth of the full radius at 0 points, the full radius from 24) as a share of the full radius, times `sin(2 pi x (p / 16) x u / width of the plot + 2 pi x start / width of the plot)` squared**. **The frequency comes from the points**: the angle makes `p / 16` turns across the whole width, so none at 0 points and **4 turns at a fully charged letter (64 points)**; as the wave is the sine **squared** (so the letters only add to each other and never cancel) a turn is two humps, 8 humps across the width at 64 points; **the amplitude is the radius of its circle**; **the phase is that of the letter's start** (2 pi times its share of the axis: a letter that starts a quarter of the way along adds pi/2). The sum of the 12 waves divided by 12 (`S`, from 0 to 1) is then **stretched**: the height above the base is `A x clip((S - 0.05) / (0.8 - 0.05), 0, 1)`, `A` being **two fifths of the picture's height** (160 pixels), because real music only reaches `S` of about 0.28 to 0.78 (measured on four files), so the stretch makes the tallest waves fill the room (`FLOOR_SHARE` and `CEILING_SHARE` in `chromatic_wireframe.py`; the floor is low so that one steady note, `S` of 0.04 to 0.12, is still a moving line). The floor of loud music stays: louder music rides higher above the base. The letters interfere in a way that need not mean anything musically. Letters with equal points have the same frequency and amplitude and phases spread round the circle, and their sines squared add up to a constant, so **a silent frame, and a frame in which all 12 letters have the same points, is a flat line**; the line has shape where the letters' points differ. **One line for each frame** (each analysis window position): the current frame's line is in front, **its base on the bottom margin** (10 pixels from the bottom; a line is never below its base), and the lines of the earlier frames are behind it, each **4 pixels higher and smaller** (the oldest at 75 % of the width and height, about the middle), **as many as fill the picture up to the top margin (66 on 600 × 400: `floor((390 - 10 - 0.75 A) / 4) + 1`, so that the highest height of the oldest line stays inside the 10 pixel margin)**, so the plot scrolls as the music goes on; at the start of the file there are only as many lines as frames so far. **Nearer lines hide the lines behind them** (the area under each line down to the bottom of the picture is filled with the background (**black**, not the middle color of the colormap as for the other types) before the line is drawn, and the lines are drawn from the back to the front), so the plot reads as a landscape of ridges; the lines are 1.5 pixels wide (never under 1 pixel), smooth (the picture is drawn at three times the size and reduced) and never leave the picture. **The color of a line is one color along its whole length**, taken from the colormap by **the place of its frame in the beat** (the Local peaks measurement, stretched over the range of the file as for the rings of Chromatic Decay, `chromatic_decay.beat_distances`): **the last color of the colormap at the top of a peak and the first at the lowest point of the beat** (the reverse of the rings of Chromatic Decay, where the peak is the first color); a frame outside every peak, and every frame before the first peak, has the first color. The color belongs to the frame, so it moves back with its line, and a repeating beat shows as repeating bands of color going back through the plot. The settings that apply are those of Chromatic Decay: the colormap, the analysis settings, the **decay rate as a whole number from 1 to 10** (the same request field and message as Chromatic Decay, `chromatic_decay.CHROMATIC_TYPES`), the **Threshold**, and **Local peaks** (always shown, without the checkbox); on the page it has its own settings group, **Chromatic Wireframe**, with the Threshold and the Decay rate, whose value is shared with Chromatic Decay. The Note layout, the four decay amounts and every grid setting are accepted, checked and ignored. There is no new request or response field; the frames and the movie export work as for every type. The definition is in `specs/039-chromatic-wireframe/`.
- **Polychord** (since feature 042) is the ninth image type, `polychord` (`backend/app/services/polychord.py`): **the loudest notes of each frame as a rosette of tapering links that bend by the circle of fifths**. Each of the loudest notes (as many as **Number of notes**, 5 to 8, default 6, with the same letter in two octaves counting twice) is a **link**, a straight piece of line: the first starts at the center of the picture for the loudest note, and every next link starts where the one before it ended and **turns by 22.5 degrees for every step of a fifth** between its letter and the previous link's letter (the 12 steps of the circle of fifths make 270 degrees: a fifth up +22.5, a fourth up -22.5, the same letter straight on, a tritone 135, backwards but not all the way); every link is then squeezed to 2/3 of its width and 1/2 of its height, because the picture is wider than it is high (the links are 1.4 times as long as the room that would just fit them all going straight on, as a figure bends at almost every link); links get thinner from the center outward (each is drawn as a few short pieces of a matplotlib `LineCollection`, so that the width steps down without a jump where two links meet). The figure is drawn again, turned another 30 degrees each time, **as many times as the beat says**: **Copies (maximum)** (1 to 12, default 12) at the top of a local peak and **Copies (minimum)** (default 3) at the bottom of the beat, so the rosette opens on every beat; the first copy of frame `t` starts at **Rotation** (-360 to 360 degrees a second, default 15) times the time of the frame, so the whole picture turns. Every link of a frame is **one color of the colormap taken from the current tempo** (the tempo finder of feature 040: the first color at 60 beats a minute, the last at 156). The background is black. The beat and the tempo come from one measurement of the local peaks (**Minimum distance** applies); the colormap applies; the Threshold, the decay rate and the Note layout do not. The four settings are the form fields `polychord_notes`, `polychord_min_copies`, `polychord_max_copies` and `polychord_rotation` (refused with a message before the file is read when not allowed). Its code follows the documentation standard of feature 041.
- **Spirograph** (since feature 046) is the tenth image type, `spirograph` (`backend/app/services/spirograph.py`): **the loudest notes of the last few frames drawn as the classic spirograph pattern, a circle rolling inside a circle**, on black. In every frame the loudest notes (as many as **Number of notes**, 5 to 12, default 8; held notes, so **Extra notes (k)** applies, 1 to the smaller of the number of notes and 8) are tracked, loudest first, with their **value** (the square root of the strength over the loudest strength of the whole file, 0 to 1: the square root pulls the quiet notes up, so the pictures are larger) and their **index** (0 to 83): one frame's values and indices are a *history entry*. The picture of a frame draws the last **History length** entries (5 to 12 frames, default 8, the frame itself the newest; in the first frames, those that exist), **each one multiplied by the History fade** (0.4 to 0.85, default 0.7) **once for every frame it is older** (`fade ** age`; the frame's own entry is whole, so the newest picture is the most prominent, and an older curve is smaller, with narrower loops and a lower color): the outer loop goes through the entries, the oldest first, the inner loop through their notes, the loudest first, and each step `(i, j)` draws one curve from the value `j` and the index `j` of entry `i` and from nothing else. **The curve** (revised 2026-11-24) has 1000 points, `X = val (rc cos c1 + loops cos c2)` and `Y = val (rc sin c1 + loops sin c2)`, with `val` the value, `loops = (index mod 12) val` (the letter of the note, not its octave), `c1` going in 1000 steps from 0 to 2 pi and `c2` from 0 to 2 pi `turns` (the small circle turns `turns` times while the pen goes once round the big one): a louder note is a bigger curve and a later letter has wider loops; a value of 0 draws nothing. **The place in the local peak** of the entry's own frame, `pct` (1 at the top of a local energy peak, 0 at the bottom: one minus the beat's distance as stretched over the range of the file, as in Chromatic Decay's target; the Minimum distance of the Local peaks group decides the peaks), sets `turns = 2 x 7 x pct + 6` (6 to 20, not rounded) and the radius of the big circle `rc` = 5 when `pct` is above 0.5, else 4; without a beat every frame is at the top (20 turns, `rc` 5). **The color**: only 13 colors of the colormap are used, at the positions `sqrt(k / 12) * 256` (the last is the last color), and a curve takes color number `min(floor(12 val), 12)`, so quiet notes are near the start of the colormap and the loudest note of the file has the last color. **The size** (revised 2026-11-24): the farthest point of a curve is its first, `ext = val (rc + (index mod 12) val)`, and the largest `ext` over the file is the file's extent; every curve is drawn **between half and the whole of the full size**: its farthest point is `smallest + (full - smallest) * ext / extent` pixels from the center, `full` the room from the center to the nearer edge less the 10-pixel margin and the widest line (3 pixels), `smallest` a quarter of the smallest side of the picture (so the smallest curve is always half of the smallest side across and the loudest of the file fills the picture); the pattern is centered and round. **The line** is 3 pixels wide for the picture's own frame (`MAX_LINE_WIDTH`, a constant, whatever the History length) and `2 - (age - 1) / (history - 2)` pixels, rounded to a whole number of at least 1, for the older entries (2 down to 1 for the oldest place of the history), so the newer curves are thicker and a thick line does not cover the thin ones. It measures the beat only (no tempo; **Minimum distance** of the Local peaks group applies), draws one `matplotlib` `LineCollection` for all the curves of a frame (a few threads, the same files whatever the number), and the pictures are the same for the same file and settings. Request: the form fields `spirograph_notes` and `spirograph_history` (whole numbers 5 to 12; not sent is 8) and `spirograph_fade` (a number 0.4 to 0.85; not sent is 0.7); a wrong value is a 400 with `The number of spirograph notes must be a whole number from 5 to 12.`, `The history length must be a whole number from 5 to 12.` or `The history fade must be a number from 0.4 to 0.85.` before the file is read; the answer has both keys for every picture. Tests: `backend/tests/test_spirograph.py` (the curve against the formula, the colors, the scale, the tracked notes, the window), `test_spirograph_rendering.py` (the pictures: black, history, edges, threads, time), `test_spirograph_api.py` (the job); in `frontend/src` the tests of `validation`, `groups`, `help`, `api`, `SettingsForm` and `App`. The definition is in `specs/046-spirograph/`; `tools/verify_spirograph.py` checks a synthetic file and prints the hash of every picture.
- **Note layout** (since feature 026) says **which note is drawn in which cell of the 12 × 7 grid**, for the pictures with one shape for each note: **Decay** and **Decay Exp**, and, as the arc of each note, **Polar Chords** (the other pictures ignore it; Tiles, Blended tiles and Concentric, which also used it, were removed in feature 040). **Rows** (`rows`, the default) is the layout that always was: the notes in order like text, twelve to a row, the lowest note (A1) at the top left. **Spiral** (`spiral`, `backend/app/services/note_layout.py`) is a fixed arrangement around **middle C** (C4, the 28th of the 84 notes), which is in the **3rd row and the 6th column**: the next note up is in the cell to its right and the next note down in the cell to its left, the notes above C wind **clockwise** outward from it and the notes below it **counterclockwise**. It is made by two walkers that start at C's cell, each on a square spiral (legs of 1, 1, 2, 2, 3, 3, … cells): the high one goes east first and turns right after every leg, the low one goes west first and turns left; they take turns (the high one first), each putting its next note in the next cell of its own spiral that is on the grid and not yet taken, and the high walker (56 notes) goes on alone when the low one (27 notes) is done. The result, as the distance in semitones from middle C (`C`), is:

```text
 49 -21 -13  11  12 -12 -11 -10  13  22  36  50
 48 -22 -14  -5   4  -4  -3   5  14  23  37  51
 47 -23 -15  -6  -1   C   1   6  15  24  38  52
 46 -24 -16  -7  -2   3   2   7  16  25  39  53
 45 -25 -17  -8  -9  10   9   8  17  26  40  54
 44 -26 -18 -19 -20  21  20  19  18  27  41  55
 43 -27  35  34  33  32  31  30  29  28  42  56
```

Thirteen semitone steps are not between neighbouring cells, where a walker had to skip a cell that is off the grid or taken: -21/-20, -13/-12, -10/-9, -5/-4, -3/-2, 3/4, 4/5, 10/11, 12/13, 21/22, 35/36, 42/43 and 49/50. The layout is **a reordering of the 84 values of every frame into cell order** (`arrange_notes`), applied after the note selection and before the grid is interpolated (Tiles, Blended tiles) or before the circles are drawn (Concentric): the threshold hides the same notes, Notes keeps the same strongest notes (spread in pitch order along the spiral), the colors, the beat, the smoothing, Interpolate and Gaussian smoothing work on the notes as before, and **Oversampling blends the tiles that are next to each other on the screen**. With Rows the frames are exactly those made before this feature. The request field is `note_layout` (exactly `rows` or `spiral`, default `rows`; otherwise 400 "The note layout must be one of rows, spiral.", checked before the file is read for every image type), echoed in the response. On the page it is the dropdown **Note layout** (Rows, Spiral) in a group of its own, titled "Note layout", shown for Tiles, Blended tiles and Concentric after the group of the image type (after Image type for Concentric) and before Local peaks, and the result summary names it.
- **The settings page** (since feature 020) is a list of **titled groups**, each a section that can be folded and unfolded on its own (the browser's own disclosure element, so it works with the keyboard and tells assistive technology whether it is expanded; every group starts open, the state is not remembered, and a folded group keeps every value and still sends it). Inside a group the controls are laid out **two to a row** (a flex row that wraps; an odd last control takes the whole row; on a very narrow screen, below about 26 rem, one to a row), with the readout of a slider next to its label; labels and group titles are set in **Roboto Slab at 0.9 rem** (the variables `--label-font` and `--label-size` in `App.vue`; the font is loaded from Google Fonts by `index.html` and falls back to Georgia or another serif when offline). From the top: **Analysis** (Window size, Frame rate), **Colormap**, **Image type**, then the group of the chosen image type, then **Image smoothing** (Oversampling, Interpolate, Gaussian smoothing; shown for Contour only). The group after Image type is the one of the chosen type: **Contour** (Threshold, Notes, Wave count), **Decay** (Decay rate and the four decay amounts), **Decay** for Decay Exp (Decay rate), **Polar chords** (Notes shown), **Chromatic Decay** or **Chromatic Wireframe** (Threshold, Decay rate), **Rhythm Circles** (Vote limit, since feature 047); Energy graphs has none (Tiles, Blended Tiles, Circles and Circles paint had one each until feature 040). A control that the chosen type does not use is **not shown** (before, it was greyed out); its value is kept, so choosing the type again finds it as it was, and it is still sent. A folded group that contains a value that is not allowed says "needs attention" in its title, and Create frames stays disabled as before. Four controls were renamed in the form, the info texts, the messages and the result summary: Unit to **Movement**, Size to **Radius** (now a real radius, see Circles), Circles per frame to **Notes** and Resolution to **Oversampling**; the request fields `circle_unit`, `circle_notes` and `resolution` keep their names, and `circle_size` became `circle_radius`. Nothing about how frames are made changed except the circles' radius. The group model is in `frontend/src/utilities/groups.ts`, the section in `frontend/src/components/SettingsGroup.vue`; the definition is in `specs/020-grouped-settings-ui/`. The layout was checked by tests of the group model, by server-side rendering of the form for each image type and by reading the styles; the look in a browser is the manual step of that feature's quickstart.
- **Oversampling** (since feature 016, called Resolution until feature 020; the request field is still `resolution`) makes the picture finer without changing the music: a whole number from **1 to 5**, default 1. Every frame is drawn from a grid with one value per drawn note (12 columns by 7 rows); resolution *r* draws it from a grid of **12 r by 7 r** values instead (12 × 7, 24 × 14, 36 × 21, 48 × 28 or 60 × 35), made from the original one by linear interpolation: evenly spaced positions from the first to the last column and row (`np.linspace`) are read from the smoothed note values with `np.interp`, along every row and then along every column. The four corners keep their original values, every new value lies between the original values around it (never louder than the loudest note or quieter than the quietest one) and the end of one row never mixes with the start of the next. The interpolation works on the averaged frames, and the **Threshold and the colors work on the new values** (a tile is hidden when its own interpolated value is below the threshold's share of the file's loudest note; the colors' scale and that reference are the file's largest original smoothed value at every resolution, so at a higher resolution the strongest tile can be a step short of the colormap's last color when the loudest note falls between two sample positions, only the four corners are exact). The picture keeps its size, **600 × 400 pixels** (252 × 168 before feature 021), so a higher oversampling means smaller tiles: 50 × 57 or 58 pixels at 1×, 25 × 28 or 29 at 2×, 16 or 17 × 19 or 20 at 3×, 12 or 13 × 14 or 15 at 4× and 10 × 11 or 12 at 5×. **Tiles** are then up to 2,100 flat tiles; a Tiles frame has more colors than an indexed-colour PNG can hold above 1×, so frames at 2× and above are true-color PNGs (about 1.4 KB at 3× and 2.3 KB at 5×, against 0.9 KB at 1×) and a Tiles job takes about 2 to 3 times as long (a 60 second file: 0.8 s at 1×, 1.9 s at 3×, 2.3 s at 5×). **Blended tiles** keep the blend width as a share of the (now smaller) tile, so the fade shrinks with the tiles: at 5× a width of 25% is about one pixel at each edge (the reach is a quarter of the mean tile width, 4.2 pixels), and below about 24% at 5× (or 12% at 4×) it is narrower than the pixels' centers and changes nothing, so Blended looks like Tiles there; the middle of every tile stays flat. **Contour** is drawn from the finer grid (finer steps, a smoother outline) at the same cost per frame (about 8 to 15 ms). At resolution 1 everything is exactly as without the setting, byte for byte. On the page it is the **Oversampling** slider in the Image smoothing group (1 to 5 in steps of 1, starting at 1, with the readout "1×" or for example "3× (36 × 21)"), after the Blend width, with an info button and a line in the result summary; it works with every image type and is disabled while a job runs. In the API it is the optional `resolution` form field (a whole number from 1 to 5; leave it out for 1; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The oversampling must be a whole number from 1 to 5."), and the response adds `resolution`. The code is in `backend/app/services/resolution.py`; the definition is in `specs/016-interpolated-resolution/data-model.md`.
- **Notes** (since feature 017) builds the picture from only the strongest notes: a whole number from **12 to 84**, default 84 (all drawn notes). The **energy** of a note is the sum of its smoothed values over all frames of the file, and the **n notes with the most energy** are chosen **once for the whole file**, so the same notes are used in every frame (a choice made in every frame would flip at the margin); only the 84 drawn notes can be chosen, and notes of equal energy are ranked by pitch, the lower one first. The chosen notes keep their order of pitch, and for each frame their n values are **spread over the 84 values of the original grid**: evenly spaced positions from the first to the last chosen note (`np.linspace`) are read from the n values with `np.interp`, so the first chosen note keeps its value at the first position, the last at the last, and every value is between its neighbors. The 84 values then take the place of the 84 note values in everything else: the Oversampling step, the Threshold, the colors and the contour works on them as before, and with 84 notes the spread is the identity, so nothing changes, byte for byte. Smoothing comes first, so the energy and the values are the smoothed ones. Things worth knowing: **a note that is not chosen has no effect on any picture**, even in a frame where it is the loudest; with fewer than 84 notes **a position in the picture no longer stands for one fixed note** (it is a stretched view of the chosen notes from the lowest pitch to the highest, each covering a larger part of the picture); the **colors' scale and the Threshold's reference are still the largest smoothed value of the whole file over all 88 notes**, so the same strength has the same color at every number of notes, and a picture without the loudest note can look dimmer; the notes with no energy still count among the n when a file has fewer than n sounding notes. **It is not always steadier**: fewer notes remove the flicker of faint notes, but each remaining note covers more of the picture, so a note that changes now changes a larger area. Measured through the API on a 20 second synthetic file at 10 frames per second (Tiles, `hot`, the average change of the colors' position on the scale between consecutive frames, 84 / 48 / 24 / 12 notes): sustained tones with strong noise 0.058 / 0.056 / 0.053 / 0.045 (steadier: about 23% less at 12 notes), sustained tones with little noise 0.043 / 0.054 / 0.050 / 0.042 (about the same), and notes that start and stop twice a second 0.038 / 0.052 / 0.060 / 0.068 (less steady: about 77% more at 12 notes). The choice and the spread cost a few hundredths of a second, so job times do not depend on the number of notes (a 60 second file: tiles 0.8 s at 1× and 2.3 s at 5×, blended about 1.0 s and 1.5 s, contour about 16 s at 5×, at 84, 48 or 12 notes alike). On the page it is the **Notes** slider (12 to 84 in steps of 1, starting at 84, with the readout "All 84 notes" or for example "36 of 84 notes"), after the Threshold, with an info button and a line in the result summary ("Notes: All 84" or "Notes: 36 of 84"); it works with every image type and is disabled while a job runs. In the API it is the optional `note_count` form field (a whole number from 12 to 84; leave it out for 84; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The number of notes must be a whole number from 12 to 84."), and the response adds `note_count`. The code is in `backend/app/services/note_selection.py`; the definition is in `specs/017-top-energy-notes/data-model.md`.
- **Interpolate** (since feature 018) draws fewer pictures and makes the frames in between by **blending** their neighbors with the **Pillow** image library. It is a whole number from **1 to 5**, default 1 (every frame drawn): only every n-th frame is **drawn** from the music, and the others are **interpolated**. With the frames numbered from 1 as in the request (the files are `frame_000000.png` and up), interpolate 5 draws frames 1, 6, 11, 16 and so on and always the **last frame** of the file, so every frame in between has a drawn frame on each side (when the number of frames does not fit, the last gap is shorter). The drawn frames are made exactly as at interpolate 1, so their files are **byte-identical** to those of an uninterpolated job; the notes, the resolution, the threshold and the colors are still worked out for every frame and only the drawing is skipped, so everything else behaves as before. The number of frames, the file names, the size (600 × 400) and the timing do not change, so the player plays an interpolated job at the same speed. A frame at position k of a gap of g frames (g is n, or less at the end) is `Image.blend(earlier, later, k / g)`, the weighted mix of the two drawn pictures: frame 2 of 5 is four fifths of frame 1 and one fifth of frame 6. Only blend is made. (The first version also offered `soft_light`, `hard_light`, `overlay`, `screen` and `subtract`, the Pillow `ImageChops` operations, applied between the earlier frame and the blend, with a dropdown and an `interpolate_function` field; they were removed because they did not work well: they take no weight, `screen` brightened and the others darkened the frames in between so that the animation pulsed back to the plain frame at every drawn frame, and `subtract` gave almost black frames. A request that still sends `interpolate_function` is accepted and the field is ignored, like the other removed fields.) An event that happens between two drawn frames (a note that starts and stops within a gap) is not drawn at all. In-between frames are 8-bit RGB PNGs (the drawn ones keep their kind: indexed-colour Tiles at the original grid, true-color for finer Tiles and Blended tiles, RGBA for the contour) and are made from the drawn frames' files on a few threads. **The speed gain is real for the contour only**: for a 60 second file (1,800 frames, resolution 5) the contour job takes 15.7 s at interpolate 1, 6.2 s at 3 (0.39 of the time) and 4.0 s at 5 (0.26); Tiles and Blended tiles cost about as little to draw as to blend, so there is nothing to save there: a Tiles job at the original grid takes 0.79 s at 1, 1.00 s at 3 (1.25 times) and 0.86 s at 5, Blended tiles 0.93, 1.08 and 0.98 s, and at resolution 5 (where Tiles frames are the larger true-color pictures) Tiles take 2.29, 1.68 and 1.43 s and Blended tiles 1.36, 1.65 and 1.38 s. Peak memory is the same as without interpolation (about 315 MB for that file, set by the analysis). On the page it is the **Interpolate** slider (1 to 5 in steps of 1, starting at 1, with the readout "1" or for example "(1/5 frames)"), after the Oversampling, with an info button and a line in the result summary ("Interpolate: 1" or "Interpolate: 5"); it is disabled while a job runs. In the API it is the optional `interpolate` form field (a whole number from 1 to 5; leave it out for 1; an empty, non-numeric, fractional or out-of-range value is refused with a 400 saying "The interpolate value must be a whole number from 1 to 5."), and the response adds `interpolate`. The code is in `backend/app/services/frame_interpolation.py`; the definition is in `specs/018-interpolated-frames/data-model.md`.
- **Beat coloring** (since feature 024, and since feature 040 for the contour only) is the group **Local peaks** of the settings page for **Contour** (after its own group): a checkbox **Beat coloring** (off by default) that turns on the beat wave of the next paragraph, **Minimum distance** (100 to 2000 ms, default 350, step 50 on the page): the setting of the Local peaks measurement above (the **Prominence** it had was removed by the local tempo finder, spec 040: it is fixed at 20 percent, not on the page and not in the request). **Off, the beat is not even measured for the contour.** (Before feature 040 it also colored Tiles and Blended tiles: half of a tile's place on the colormap came from the note's strength and half from the frame's position in the local peak. The pictures that always use the beat, Decay, Decay Exp, Polar Chords, Chromatic Decay and Chromatic Wireframe, show Minimum distance without the checkbox.) Worth knowing: the measured energy runs in a **straight line from one peak to the next**, so the position follows **how strong the beats are** (it rises and falls from beat to beat, relative to the smallest and largest energy of the surroundings), not a dip inside each beat: between two equally strong beats it stays near 1. The request has two optional fields (three until spec 040): `beat_coloring` (`true`, `false`, `1` or `0` in any case; default `false`; otherwise 400 "The beat coloring must be true or false."), and `peak_distance` (milliseconds, default 350), checked before the file is read whether the box is on or off, with the message of the measurement ("The minimum distance must be a number from 100 to 2000 milliseconds."); the response adds the two values. (Until the local tempo finder, spec 040, there was a third field, `peak_prominence`, percent, default 50, with the message "The prominence must be a number from 0 to 100 percent."; it is gone: a request that still sends it has it ignored, and the response no longer has it.) `write_frames` takes the positions as `beat` (one number from 0 to 1 per frame, or `None`).
- **Beat wave** (since feature 028) lets the local peak show in the **Contour** picture. With the **Beat coloring** checkbox on (it is the one of the Local peaks group, which Contour now has too; off by default, and then **the Contour frames are exactly what they were**, with no beat measured), every frame's grid of values `Z` (7 × 12 values, or 7r × 12r at Oversampling `r`) is multiplied by a **modifier** before the contour is drawn: `Z = Z × (1 − pattern × sin(π × k))`. The `pattern` is a set of concentric rings, `(sin(waves × 2π × sqrt(distance ÷ largest)) + 1) ÷ 2`, a number from 0 to 1 (the square root makes the rings close together near the center and wider towards the outside): `distance` is the distance in grid points from the **center** of the grid (the center of `n` points on an axis is at `(n − 1) ÷ 2`, so it is half way, 0.5, at an exact center), `largest` is the larger of the grid's columns and rows (12 at the original grid), and `waves` is the **Wave count**. `k` is the frame's **position in the local energy peak** (feature 024: 0 at its minimum, 1 at its maximum, 0 when no beat is known), passed through a sine from 0 to π so that the effect swells and fades smoothly. **At the minimum of the beat the modifier is 1 everywhere and the frame is the plain contour** (nothing is multiplied: the file is byte for byte the same); as the beat rises the rings, where the pattern is 1, are dimmed by the factor `1 − sin(π × k)` and are cut away completely half way up the beat (`k = 0.5`), and as the beat goes on to its maximum they fade out again (at `k = 1` the frame is the plain one to within rounding), while the places between the rings are never touched. The color scale is still the one of the frame **before** the wave (from 0 to the frame's largest value), so the dimmed rings are drawn darker; a frame that the wave leaves with nothing to draw is one flat color. The pattern is worked out once per job (`backend/app/services/beat_wave.py`) and the wave is applied in `contour.py` after the grid smoothing and before the levels are chosen. **Wave count** (the request field `wave_count`, a whole number from **2 to 10**, default **4**, a slider at the end of the Contour group, echoed in the response and shown in the result summary when the beat coloring is on) is checked for every image type before the file is read (`The wave count must be a whole number from 2 to 10.`) and has no effect except for Contour with the box on. The beat is measured for a Contour job exactly when `beat_coloring` is true, with the Local peaks setting (`peak_distance`; the prominence is fixed at 20 percent). Interpolate and Gaussian smoothing work on the frames with the wave.
- **Gaussian smoothing** blurs the finished pictures: a number from **0 to 5**, default **0**, in steps of one half on the page. At 0 nothing is done and the frames are exactly what they were (the original tile grid keeps its indexed-colour files). Above 0 every drawn frame is blurred with Pillow's `ImageFilter.GaussianBlur`, whose radius is the standard deviation of the Gaussian in pixels; because the frame is 3:2 the radius is **3:2 as well**, so that the smoothing looks the same in both directions: a setting of *v* blurs by **1.5 *v* pixels across and *v* pixels down** (a setting of 4 is a radius of 6 in x and 4 in y, a setting of 5 is 7.5 and 5; the radii are in pixels of the 600 × 400 frame, not of the 252-pixel reference frame of the circles). It rounds off the edges of tiles, contour bands and the soft edges of blended tiles. It applies to **Tiles, Blended tiles and Contour** (it is in the Image smoothing group, which the two circle types do not show; the server accepts it for them and ignores it). The blur is applied to the frames that are **drawn**, after they are written and before the in-between frames of Interpolate are made, so an in-between frame is a blend of blurred frames; a flat-colored tile frame, which is saved with a palette, has many more colors once blurred and is saved as a true-color picture (compress level 1). In the API it is the optional `gaussian` form field (a number from 0 to 5, default 0; an empty, non-numeric, non-finite or out-of-range value is refused with 400 and "The gaussian smoothing must be a number from 0 to 5.", for every image type, before the file is read), and the response adds `gaussian`. On the page it is the **Gaussian smoothing** slider, the third control of Image smoothing (alone on its row), with the readout "Off" or its number, an info button and a line in the result summary. Measured for a 60 second file (1,800 frames of 600 × 400) at 0, 2.5 and 5: tiles 1.0, 5.9 and 7.2 s (the room of the frames 5, 51 and 107 MB), blended tiles 8.3, 15.6 and 15.9 s (67, 80 and 134 MB), contour 35, 43 and 42 s (10, 145 and 191 MB); the cost is about 5 to 8 s of time, but the **files grow a lot** because a smooth gradient compresses badly. The code is in `backend/app/services/gaussian.py`.
- **Threshold** (since feature 011) hides faint notes. It is a slider from **Off** (0, the left end, exactly as before) to 10 (the right end) in steps of 1: the percentage of the **largest note value in the whole file** ( the same value the colors are scaled against, including the four undrawn notes) below which a note is not shown. A drawn note whose smoothed value in a frame is *strictly below* that level is **0** in the contour (and, for Chromatic Decay and Chromatic Wireframe, silent before the letters are charged: feature 037); a note exactly at the level is shown, and the note with the largest value is never hidden. (Tiles drew a black tile there and Blended tiles left the background: both were removed in feature 040.) The level is one fixed level for the whole file, not one per frame, and the comparison is made on the unrounded smoothed value, so the colormap never changes which notes are hidden. In the API it is the optional `threshold` form field (a number from 0 to 10, leave it out for 0; an empty, non-numeric or out-of-range value is refused with a 400 saying "The threshold must be a number from 0 to 10."), and the response adds `threshold`. The page shows it as the Threshold slider with a readout ("Off", or for example "5%"), an info button and a summary line. The definition is in `specs/011-note-threshold/data-model.md`.
- A submission may create at most 60,000 frequency buffers (`MV_MAX_WINDOWS`; one every 60 ms, so about an hour of audio); a longer file is refused before any analysis.
- Frontend tests: `cd frontend && npm test`.

## 3D export (Wavefront OBJ files, feature 045)

For **Contour** and **Chromatic Wireframe** the page has a group **3D export** with a checkbox **Export 3D files (.obj)** (off by default). With it on, the job writes, besides the usual PNG frames (which are unchanged, byte for byte; the frame player and the video work as before), **one `.obj` file for each frame**, `frame_000000.obj` and up, numbered like the pictures, and the result shows a link **Download 3D files (.zip)**.

- **What a file is**: plain text, complete in itself: a few `#` comment lines, `o frame_NNNNNN`, one `v x y z r g b` line for each point (the position in grid units and the color as three decimals from 0 to 1, for example `v 3.0000 2.0000 6.1234 0.2667 0.0039 0.3294`) and one `f a b c d` line for each face: the four corners of one cell of the grid, counted from 1, counterclockwise seen from +Z, so that the face points up. The surface is **not curved**: the points are the only points and the curve is left to the modifiers of Blender (import the file, then add for example a Subdivision Surface modifier). Numbers have four decimals, a dot and no exponent, so the same music and settings give the same files byte for byte. Z is up, X to the right and Y away from the viewer (Blender's default for OBJ files).
- **Contour**: the 12 x 7 grid of the notes: **84 points and 66 faces** in the XY plane, X the note name (0 to 11, A first), Y the octave row (0 to 6, the picture seen from above has the picture's orientation), Z the height from 0 to 12: the value of the cell after the picture's own smoothing (and the beat wave when Beat coloring is on) over the largest value of the whole file, times 12 (so the heights of different frames compare; the smoothing averages a note with its neighbours, so a lone loud note stays under 12). The color of a point is the colormap's color at its value on the scale the picture of that frame uses (0 to the frame's largest value). Number of notes and Threshold apply; Oversampling, Gaussian smoothing and Interpolate change the pictures only.
- **Chromatic Wireframe**: the file of a frame holds the line of the frame and the lines of the **11 frames before it** (fewer for the first frames): each line is **12 points**, one for each letter (A first) along X, at Y = the age of the line (0 for the frame itself, 11 for the oldest); Z is the amplitude of the letter (the radius of its circle in Chromatic Decay over the full radius, so 1/12 to 1) times 12, from 1 to 12. A full file has 144 points and 121 faces; the file of frame 0 has 12 points and no faces. The 12 points of a line have the color of the picture's line for that frame. The sine curve of the picture is not exported. Decay rate, Threshold and Extra notes apply.
- **API**: the form field `export_obj` (`true`, `false`, `1` or `0`; not sent is `false`; anything else is a 400 `The 3D export must be true or false.`; on for any other picture is a 400 `The 3D export is only available for Contour and Chromatic Wireframe.`, before the file is read); the answer has `export_obj` and `obj_url` (`/api/jobs/{job_id}/obj`, or `null`). `GET /api/jobs/{job_id}/obj` downloads all the files of the job as one ZIP (made on the first request into the output folder, `MV_OUTPUT_DIR`); a job without the export gets a 404 `No 3D export was made for this render.`
- **Code**: `backend/app/services/obj_export.py` (the meshes, the text, the ZIP), `contour.smoothed_grid()` (the smoothing shared with the picture), `frame_rendering.write_frames(..., export_obj=True)`. The definition is in `specs/045-obj-export-mode/`; `tools/verify_export.py` checks a synthetic export with an independent reader (`tools/read_obj.py`).
- Tests: `backend/tests/test_obj_export.py` (the meshes, the text, the ZIP), `test_obj_export_rendering.py` (`write_frames`: the settings, the pictures unchanged, the time), `test_obj_export_api.py` (the job field, the refusals, the download); in `frontend/src` the tests of `api`, `validation`, `groups`, `help`, `SettingsForm` and `App`.

## Video (silent MP4 from the frames)

Since feature 029, under the frame player there is a **Create video** button. It joins the frames of the render, in order, into one **silent H.264 MP4** with ffmpeg (no audio: the uploaded file is not used) at the render's frame rate, so the video lasts as long as the music. The file is saved as `backend/output/<job_id>/video.mp4` (one directory per render; creating it again replaces it; `backend/output/` is git-ignored), and the page shows where and gives a **Download** link.

- `POST /api/jobs/{job_id}/video` makes the video and answers `{job_id, file_name, path, size_bytes, frame_count, frame_rate, duration_seconds, url}`; `GET /api/jobs/{job_id}/video` downloads it. Errors are `{"detail": "..."}`: 404 when the frames are gone (render again), 409 when a video is already being made for the render, 503 when ffmpeg is not found, 504 on a timeout, 500 otherwise. A failure leaves no partial file.
- ffmpeg must be on the PATH, or set `MV_FFMPEG_PATH` to its full path (for example `C:fmpeginfmpeg.exe`). `MV_OUTPUT_DIR` moves the output directory and `MV_VIDEO_TIMEOUT_SECONDS` (default 600) limits a conversion.
- To add the music afterwards: `ffmpeg -i video.mp4 -i song.wav -c:v copy -shortest with-music.mp4`.
- Tests: `backend/tests/test_video.py` (the service, with a fake ffmpeg), `backend/tests/test_video_api.py` (the endpoints; the tests with the real ffmpeg are skipped when ffmpeg and ffprobe are not installed), `frontend/src/components/VideoExport.test.ts`.
